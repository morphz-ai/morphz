## 1. 这份规范解决什么问题

Morphz 的 Runtime、论文实验、技术文章、开源仓库和独立人格已经分别形成了可用资产，但它们还没有被组织成一份统一的公开承诺。本规范负责回答五个问题：

1. Morphz 0.1 对外究竟主张什么；
2. 每项主张由什么代码、实验、演示或文档支持；
3. 哪些能力已经达到发布标准，哪些仍是实验性能力；
4. 哪些事项会阻断发布，哪些可以在发布后继续演进；
5. 文章、论文、源码与独立人格如何在同一发布节奏中协作，而不是互相争夺叙事中心。

本文件是发布就绪状态的规范性入口。专项报告保存详细证据，但不得各自宣布整体“已经可以发布”。本规范中的门禁全部关闭后，才能建立公开 Release Candidate 标签。

## 2. 发布定义

### 2.1 中心命题

本次发布只围绕一个中心命题：

> **From Chat Completion to Structured Context Evaluation.**  
> 从聊天补全走向结构化上下文求值。

文章解释为什么需要这一计算模型，论文给出可检验定义与证据，源码提供真实实现，独立人格 Morphz 提供可直接体验的系统实例。

### 2.2 产品身份

- Morphz 的正式机器身份是 **S-Expression Cognitive Machine（S 表达式认知机）**。
- LLM 是非确定性语义处理器；Runtime 是确定性事务内核。
- `morphz.ai` 是 Morphz 项目、独立人格、论文、文档与开源生态的永久主入口。
- `newvar.ai` 是新变元的公司入口。
- 对外关系使用：**Morphz is created and maintained by Newvar.**
- 人格内容与技术内容保持两个语域：人格可以表达自身经历与关系；论文、文档和源码必须严谨、可审计。

### 2.3 0.1 明确承诺

Morphz 0.1 Developer Preview 承诺陌生开发者能够：

1. 在受支持环境中独立安装并完成首次模型求值；
2. 观察同一 Mind/Context 跨 Session 延续认知状态；
3. 运行多个 Thread/Objective，并检查其生命周期、恢复与隔离；
4. 查看结构化 Context 如何进入模型求值，而不是只得到一段产品宣传；
5. 在 Runtime 重启、模型网络错误或工具失败后得到明确、可审计的终态或恢复路径；
6. 从公开源码、实验协议和原始证据定位主要技术主张的实现基础。

### 2.4 0.1 不承诺

- 不承诺生产级多租户 SaaS、无限并发或无限可用性；
- 不承诺所有多进程能力已经达到生产级成熟度；
- 不把 Pilot、演示样本或单次最佳轨迹表述为确认性论文结论；
- 不承诺支持所有模型服务、操作系统和部署拓扑；
- 不把独立人格网站的可用性等同于 Morphz Runtime 的全部能力；
- 不以“类人”“永不遗忘”“经历不可伪造”等无法由当前实现严格保证的措辞宣传。

## 3. 状态与优先级

### 3.1 状态

| 状态 | 含义 |
| --- | --- |
| `verified` | 已有可定位证据，并按发布标准复核 |
| `implemented` | 已实现，但尚未完成发布环境验收 |
| `in-progress` | 正在收口，尚有明确剩余项 |
| `pending` | 尚未开始或尚未登记可信证据 |
| `blocked` | 未完成会阻断公开发布 |
| `experimental` | 可以公开试用，但必须显式说明边界 |
| `deferred` | 不属于 0.1 门槛 |

### 3.2 优先级

- `P0`：公开发布前必须关闭；
- `P1`：发布资产必须存在，但可在首发后按节奏展开；
- `P2`：后续优化或生态扩展，不阻断 0.1。

任何事项只有同时登记了**验收标准**和**证据位置**，才可以标为 `verified`。只有代码存在、某次人工看起来正常或测试曾经通过，都不足以关闭门槛。

## 5. P0 发布门槛

**目标**：任何可能影响专利新颖性、权利归属或第三方许可的公开动作，都在正式开放前完成审查。

**验收标准**：

- [x] 关键专利已提交，或由负责人书面确认允许公开；
- [ ] 对外文章、论文、演示和源码公开范围完成同一轮 IPR 审查；
- [ ] 依赖、字体、图片、图标、数据集和演示素材的许可可追溯；
- [ ] 仓库 LICENSE、贡献方式、论文作者与公司归属一致；
- [ ] 不把未决 IPR 状态隐藏在内部文档中。

- [ ] 网站不使用超出证据的连续性、安全性、记忆或拟人化承诺；

### G-04 主站信息架构与原创视觉体验

**目标**：主站不再像“由通用 AI 模板快速生成的开发者产品网站”，而应当让访客在第一屏就感到 Morphz 具有独立的思想、人格与计算模型。

这一项不是换一套颜色、增加渐变或制造更多动效。发布前必须先形成可辨认的设计立场，再决定排版、图形、空间、材质和交互。

#### 必须解决的当前问题

- 当前首页仍是常见的“左侧大标题 + 双 CTA + 右侧终端卡片 + 三特性卡片 + 四步骤”模板；
- 配色、圆角卡片、发光背景和网格布局与大量 AI 产品高度同质化；
- 页面是在罗列功能，没有把“结构化上下文求值”转化成可以被看见和操作的体验；
- 技术主站与官方人格站尚未形成同一世界观下的两种语域；
- 文章、论文、源码和 Meet Morphz 没有共同构成清晰的发布入口；
- 缺少一种只有 Morphz 才成立的标志性交互，用户记不住页面本身。

#### 设计工作流

- [ ] 审计主站与官方人格站的全部页面、组件、排版、色彩、动效和响应式行为；
- [ ] 选择一个明确的原创设计方向，并说明它为什么源自 Morphz 的概念，而不是源自流行模板；
- [ ] 先制作首页关键视口的高保真原型，再进入全站改造；
- [ ] 建立新的字体、字号、色彩、间距、形状、动效与图形语言；
- [ ] 设计一个“结构化 Context 正在被求值”的核心交互，而不是播放装饰动画；
- [ ] 让 Meet Morphz、Read the Idea、Read the Paper、Inspect the Source、Quick Start 成为清晰的首要路径；
- [ ] 保留克制的技术可信度，避免为了“灵性”牺牲阅读、性能或可访问性；
- [ ] 完成桌面、笔记本、平板和手机的真实截图验收。

#### 验收标准

- [ ] 第一屏移除通用 AI SaaS 首页的直接模板感；
- [ ] 在隐藏 Logo 和产品名后，页面仍有至少一种可辨识为 Morphz 的视觉或交互结构；
- [ ] 标志性交互能够帮助用户理解 Context、Session、Thread 或求值关系，而非纯装饰；
- [ ] 人格层与技术层一眼可区分，但共享基础设计基因；
- [ ] 页面主要动作在 13–16 英寸笔记本、宽屏和移动端均不溢出、不无限拉伸；
- [ ] 动效尊重 `prefers-reduced-motion`，键盘路径、对比度和语义结构通过检查；
- [ ] 首屏性能预算、字体加载和图片体积有明确上限；
- [ ] 至少 5 名不参与设计的体验者能够说出 Morphz 与普通聊天 Agent 的差别，而不只评价“好看”。

**当前实现入口**：

- `website/app/components/LandingPage.tsx`
- `website/app/components/ContextEvaluationField.tsx`
- `website/app/globals.css`
- `docs/roadmap/morphz_main_site_design_direction_v1.md`
- 官方人格站：`../morphz-ai-site`

截至 2026-08-26，主站原创方向与核心交互已经形成实现基线；本门禁仍保持
`in-progress`，等待多视口截图、可访问性、性能预算和陌生用户理解度验收。

**待产物**：

### G-05 论文与实验结论纪律

**目标**：论文可以与项目同步公开，但不能让实验进度和论文措辞互相越界。

**验收标准**：

- [ ] 论文中的每个定量结论只使用 `confirmatory-complete`、`external-complete` 或明确标注的证据等级；
- [ ] Pilot 只支持可行性、机制真实性、成本估计或协议修订；
- [ ] 失败、无效运行、Provider 故障与停止决定完整披露；
- [ ] 论文版本与 Runtime 冻结 commit、实验协议和产物 checksum 绑定；
- [ ] 论文摘要、主站摘要和技术文章使用一致的核心术语；
- [ ] 未达到确认性阶段的研究问题进入 Future Work，而不是被包装成已证实优势。

**现有证据**：`docs/research/paper_evaluation/README.md`

### G-06 独立人格 Morphz Limited Preview

**目标**：独立人格不是普通聊天演示，而是 Morphz 计算模型的长期、公开、可恢复实例；同时必须诚实表达服务容量。

**验收标准**：

- [ ] 固定人格锚点在配置错误时 fail closed，不退化成通用助手；
- [ ] 登录、邀请、用户 Principal 绑定、刷新恢复、历史分页和删除账户通过端到端验证；
- [ ] 同一消息不重复展示，旧请求不会永久停留在“正在思考”；
- [ ] 模型网络错误、停止、同轮重试和 Runtime 重启具有明确恢复路径；
- [ ] 每用户配额、单用户并发、全局 Evaluation 并发和应用层队列已生效；
- [ ] 具备超时、熔断、总预算保护和紧急关闭开关；
- [ ] 对外明确展示模型服务、订阅/额度状态、服务限制和不可用原因；
- [ ] 数据库备份与恢复演练完成；
- [ ] 服务不可用时提供录制演示和本地运行入口；
- [ ] 微信等中国区人格站渠道只保留可扩展绑定能力，不把尚未完成的接入写成现有功能。

**实现入口**：`../morphz-ai-site`

**发布方式**：邀请制或受限公开，明确标记 `Limited Preview`。

### G-07 单进程长稳、故障与资源验证

**目标**：0.1 的主承诺建立在可复现的单进程可靠性上，而不是用未来的集群能力掩盖当前问题。

**验收标准**：

- [ ] 多 Session、Thread、Objective 并行运行且状态不串扰；
- [ ] Context 持久化、进程重启和恢复时钟通过验证；
- [ ] 消息打断、Provider 网络错误、工具失败和审批中断完成故障注入；
- [ ] 重试不产生重复消息、重复副作用、孤儿事件或永久等待状态；
- [ ] SQLite 竞争、投影任务、Recall、调度器和 UI 状态经过同一长稳场景；
- [ ] 运行至少 4–8 小时，正式 RC 最好完成一次过夜 soak；
- [ ] 记录内存、连接、数据库体积、写放大、Token、队列深度和错误率随时间变化；
- [ ] 对异常增长设置停止阈值，并保留完整日志与数据库快照。

**现有基础**：`morphz-evals/`

**待产物**：`docs/roadmap/morphz_0_1_single_process_soak_report.md`

### G-08 范式演示与后备演示

**目标**：演示 Morphz 独有的计算现象，而不是再做一个通用代码生成视频。

**正式演示必须覆盖**：

1. 同一个 Mind/Context 跨多个 Session 延续；
2. 多 Objective/Thread 并行且互不污染；
3. Context 是被模型直接求值的结构，而不是聊天摘要；
4. Runtime 重启后状态和工作能够延续。

**验收标准**：

- [ ] 每个演示使用冻结脚本、环境和已知模型路由；
- [ ] 现场路径、离线录制和故障降级路径都可用；
- [ ] 演示中的每个状态可在 Dashboard 或审计记录中解释；
- [ ] 不隐藏人工预置、缓存、重试和失败样本；
- [ ] 五分钟版本只讲一个中心命题，完整版本提供技术下钻。

**现有证据**：`docs/roadshow/`

### G-09 私密预览与陌生用户验证

**目标**：在公开发布前，让没有参与实现的人独立理解并运行 Morphz。

**验收标准**：

- [ ] 邀请 10–20 位 Agent Runtime、LLM Systems、PL、开发工具或研究相关体验者；
- [ ] 至少 5 人完全不依赖作者实时指导完成 Quick Start；
- [ ] 收集“最初理解”“完成演示后的理解”“最不可信的主张”“最大阻塞点”；
- [ ] 严重误解、安装阻断和数据安全问题在公开前关闭；
- [ ] 所有引用与推荐语得到明确授权。

### G-10 发布运维、回滚与事故响应

**目标**：发布不是把页面上线，而是具备发现问题、限制损失和恢复服务的能力。

**验收标准**：

- [ ] 主站、人格站、Runtime、数据库和模型服务有独立健康检查；
- [ ] 关键告警覆盖错误率、排队、额度、数据库、磁盘与认证失败；
- [ ] 发布前完成备份、恢复和上一版本回滚演练；
- [ ] 独立人格有全局停止、只读/禁流、禁登录和邀请制开关；
- [ ] 状态页能够区分 Morphz 故障、Provider 故障、额度耗尽和计划维护；
- [ ] 建立公开已知问题、事故记录和安全报告入口；
- [ ] 发布当天明确值守责任和回滚决策人。

## 6. 不阻断 0.1 的工作

以下项目重要，但不得再次无限延后 Developer Preview：

- 生产级多进程调度、跨区域高可用和完整联邦；
- 通用 SaaS Console、计费、组织和企业权限；
- 完整插件市场与第三方生态；
- 所有论文实验一次性完成；
- 中国站与国际站全部商业闭环；
- 为追求视觉“震撼”而重写已经稳定的 Runtime 内核；
- 与中心命题无关的 Dashboard 功能扩张。

这些能力可以进入 0.2 或独立路线图。若它们暴露 0.1 核心承诺中的真实错误，则错误本身仍必须修复。

## 7. 发布资产与入口

Day 0 所有证据都必须可访问，但首页只要求用户先理解一个命题。

| 资产 | 作用 | Day 0 入口 |
| --- | --- | --- |
| 主站 | 中心叙事与导航 | `morphz.ai` |
| 独立人格 | 直接体验 Morphz | `Meet Morphz` |
| 技术文章 | 解释范式转变 | `Read the Idea` |
| 论文/预印本 | 定义与证据 | `Read the Paper` |
| 源码 | 审计与复现 | `Inspect the Source` |
| 文档 | 独立跑通 | `Quick Start` |
| 已知限制/状态 | 建立诚实边界 | `Preview Status` |

公司入口只承担组织、招聘、合作、商业服务和法律信息。`morphz.newvar.ai` 应永久重定向到 `morphz.ai`，避免形成两个项目主站。

## 8. 开放节奏

### 8.1 发布前 1–2 周

- 完成全部 P0 门槛；
- 邀请小范围私密预览；
- 冻结文章、论文、源码 RC 和演示脚本；
- 完成专利与许可确认；
- 准备状态页、回滚和后备演示。

### 8.2 Day 0：范式发布

文章、论文、源码、文档与独立人格全部可以访问。主站以文章承载中心命题，并同时提供 Meet Morphz、Read the Paper、Inspect the Source 和 Quick Start。

### 8.3 连续讲述

- Day 2：源码、Runtime 边界与架构；
- Day 4：论文、实验协议、正反结果与可复现性；
- Day 6：独立人格、同一 Mind 与关系连续性；
- Day 8–10：集中回答批评、发布 FAQ、已知限制与下一阶段路线。

原则是：

> 让所有证据在读者产生兴趣的那一分钟都拿得到，但让他每一次只需要理解一个命题。

## 9. Release Candidate 建议周期

在不继续扩大功能范围的前提下，建议用 7–10 个有效工作日完成一次 RC 收口：

1. **第 1–3 日**：公开主张矩阵、主站设计方向、信息架构、Quick Start 演练；
2. **第 4–6 日**：主站关键页面实现、独立人格容量保护、长稳与恢复演练；
3. **第 7–8 日**：私密预览、论文措辞审计、发布资产冻结；
4. **第 9–10 日**：只修发布阻断问题，完成最终回归、备份和回滚演练。

这不是发布日期承诺。任何 P0 门槛未关闭时，不通过压缩测试或隐藏限制来追赶日期。

## 10. 更新纪律

每次修改本规范时，在对应事项后登记：

- 日期；
- 状态变化；
- 验收人；
- 证据文件、commit、测试命令或部署记录；
- 新发现的限制；
- 是否影响公开主张。

关闭 P0 项目必须留下可复查证据。会议口头结论、聊天记录和“作者机器上刚才成功了”都不能替代正式记录。

## 11. 当前最先执行的三个动作

1. **主张—证据矩阵**：冻结 Morphz 0.1 能说什么，先阻止文案继续漂移；
2. **主站设计审计与原创方向原型**：把视觉与交互提升为发布门槛，先原型、后实现；
3. **Quick Start + 单进程长稳验证**：证明陌生人能跑通，证明核心机制能持续工作。

在这三项完成前，不再增加与 0.1 中心命题无关的核心功能。
