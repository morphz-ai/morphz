## 已实施的隔离候选

候选代码在 `morphz/src/session_io/native.rs`，已接入新构建的新请求 admission 和
全局 Context；旧冻结绑定按其原载体恢复。原应用配置与正在运行的二进制没有切换。

- 原生工作调用保持其真实名称和 ID；模型侧参数一次性增加可选 `_morphz` 显示字段。
  Runtime 去除该字段后，将业务参数交回原验证器；不放宽未知业务字段或权限。
- 注解开关和工作续接不增删、重排或修改工具定义。开启时明确要求适用的步骤意图、
  标题、进度；接收端兼容缺失及无效显示字段，不新增注解专用工具或修复推理。
- 本候选将物理返回格式冻结在独立绑定中，不根据正文的首字符或字段名猜测协议。
  普通 Chat 是原样文字。工作后的 Chat 曾按较小 `{body,annotations}` Schema 交付；
  **这个分支的多步工作门禁仍失败，不能因单步通过而采用。**
- 类型化值维持调用方的原始 Schema，不在读完工具结果后再改变业务记录的形状。
  原 Yao/注册业务验证器仍是类型准入边界，不用较小 IO Schema 子集假装验证全部类型。
- 旧冻结输出禁止直接送入候选 `prepare`；没有修改、重放或重新解释旧任务。

## 阶段 A 确认的适配缺口及本轮修复

连续读取的真实上游响应同时包含：

1. message：`review.txt 已读取，现在读取 progress.txt。`，最终 `phase=commentary`；
2. function_call：真实 `read(progress.txt)`，参数与同调用注解均存在。

请求确实带 `text.format.type=json_schema`、`strict=true`。因此这不是漏上传 Schema，
也不能将这条工作进度认定成“模型没能力返回 JSON”。它不是最终答案。
当时 Provider 虽保存消息 item 用于补全内容，向 Runtime 返回时却只拼接为
`Response.content`，丢失了进度/最终答案的区别；候选随后按最终 Schema 解析，
产生 `Invalid JSON at byte 0`。

同一消息在 `response.output_item.added` 里先标 `phase=final_answer`，在
`response.output_item.done` 和完整响应里变为 `phase=commentary`。所以只读流开始
的 phase 仍不充分。解析失败后把字符串当正文、扫描 JSON 字段、禁止所有后续工具、
或追加一个修复模型请求，都不是此缺口的正确处理。

候选现在保留原生消息的真实 index、id、phase 及终态文本。开始阶段仅是临时
显示提示，item.done / response.completed 才确定消息分类。工作进度不再送给最终
类型解码；最终仅提交真实 final body。阶段修正只替换同一临时草稿，不新增答案。
缺终态、身份冲突、最终文本改写仍拒绝；不根据文本内容判断 phase。
原始 SSE 已逐字节离线重放通过，相关阶段变更与结束边界测试通过。

修复阶段信息后，曾出现一组 9/9 通过，紧接着重复又失败：完成两次读取后提出
第三次实际 `read`，注解却写“占位校验（不执行）”。Runtime 不得把这句话当成
取消动作的控制协议。同一原请求的诊断中，显式 auto、缩短提示、强调禁止占位
都仍出现过额外调用。移除最终 Chat Schema 的对照 4/4 通过仅是候选证据，
随后取得用户批准并实施了上面的完整正文路径测试，没有把这个对照当作交付。

另一个尚未解决的 live 反例是完成一次读取后，上游提出新的 `progress.txt` 调用。
它不是 JSON 解析丢数据；原始响应就包含这个调用。不能把它忽略掉并伪造答案，
也不能通过放宽“只读一次”的验收来消除失败。它需要与进度分流问题分别检查。

## 自动化与未完成项

### Runtime 接线与持久化边界

沿用已经 review 的原生候选，不引入另一套正文协议。新的 Runtime 构建在新准入
返回绑定上明确记录 `native_v3` 载体；历史没有此标记的绑定保留原解释，不按内容
或当前设置升级。实际物理请求冻结原业务绑定、生成 Schema、工具目录摘要，并保存
原生 message 的身份/最终 phase；这些事实和原始响应一起属于 Runtime 的既有
assistant-call Event，不由模型生成，不新增业务实体、数据库或权限来源。

新增信息随同原有注解 bundle 在同一 Event 写入中原子持久化，以原 Event、Attempt、
Execution generation 为身份和恢复边界。恢复只按这个源重建归一结果，不能重新调用
模型、重放已经提交的工作或用当前 Provider 能力替换原绑定。读取仍经过既有 Session/
principal 授权，原生 phase 不提供执行权限；元数据先拆分，原工具参数/权限再次校验。
SQLite/PostgreSQL 仍使用既有 Event JSON 持久化与相同事务，不新增索引或 JSON 快照
数据库；Event 生命周期、删除与幂等冲突规则不变。新旧冻结记录和崩溃恢复必须各自
有回归证据。

工具目录独立于当前可执行权限。只有既有 Runtime 权限确实为空（如纯 infer）时，
才把“无动作”传入上游 API；这不是按输入用词分类，也不是读完一次就禁用后续工作。
可执行权限非空时保留原生工作选择，所有调用仍走原执行校验。正文、注解、状态分别
由已绑定正文、同调用元数据、真实执行回执负责，不能相互冒充。

阶段变化只修改临时草稿。Runtime 的草稿存储和 Desktop 消费者必须使用同一有序
替换语义，最终提交仍只有一个真实正文；内部 typed infer 的父回复只采用既有证明
路径投影。完整隔离构建通过前不替换原应用或运行中的 Runtime 二进制。

- Session IO 定向库测试：95 通过，0 失败，4 忽略。
