# ME-08 Prefix Cache 命中率分析

日期：2026-08-29

## 结论

本轮缓存率暴露的是已确认的请求封装缺陷，不能作为 Structured Context 的成本结论。Runtime 在启用显式缓存模式后，仍把追加式 Inbox 每轮重新序列化为单个传输内容块，并只在本轮 Inbox 末尾设置断点；新增 Observation 会移动该断点，而显式模式又关闭了服务端自动选择断点。结果是逻辑上追加式的 Inbox 没有在传输层形成可持续增长的缓存链。

本轮 Morphz 输入缓存率为 24.81%，高于上一轮的 16.32%，但明显低于 Codex 的 93.12%。差距来自请求形态，而不是服务端整体不可用。

1. Morphz 为每个独立 Context 生成由 `context_id` 派生的 `prompt_cache_key`。89 题因此被分散到不同缓存组，减少了跨题共同前缀的复用机会；不过每题首次冷请求在总输入中占比较小，这不是 24.81% 与 93.12% 差距的主要来源。
2. 每题首次请求均为冷请求。具有模型 usage 的 86 个任务中，第一次请求 0/86 命中；第二次仅 6/86 命中；第三次 79/86 命中。
3. 命中后的常见缓存量是 11,776 词元，对应固定 System/协议前缀。随着工具结果和 Context 尾部增长，缓存量没有同比增长，单次缓存率由第三次调用的 39.87% 逐步下降，长任务后段通常只剩 10%～20%。
4. 当前第二个显式断点位于整个 Inbox 内容块的末尾。Inbox 每追加 Observation，断点位置和该内容块都会改变；请求没有保留上一轮 Inbox 末尾的旧断点，因而没有形成可逐块复用的增量缓存链。这与轨迹中缓存量长期停留在约 11,776 词元相符。
5. 本轮 1,187 条 `runtime/model_usage` 事件中的 `cache_write_input_tokens` 合计为 0。当前 CLIProxyAPI/订阅线路不报告写入量，但独立真实探针已经通过后续 `cached_tokens` 证明显式断点能够生效，因此不能把写入量为零解释为没有缓存写入。
6. Codex 同样按题建立 89 个独立会话，但使用追加式消息轨迹。即使每题首次请求是冷请求，后一轮仍可保留前一轮的大部分完整前缀，因此题内缓存范围会随轨迹增长。这是其 93.12% 总命中率与 Morphz 的主要结构差异。

## 独立可行性证据

- 在同一 GPT-5.6 Sol／CLIProxyAPI 路线上，把一条 User Message 划分为稳定块和动态块，并在稳定块后设置显式断点；首次请求冷启动后，只改变动态块的两次请求均命中 23,296/24,115 个输入词元，即 96.6%。
- 在 `qwen3.8-max-preview` 上保持约 18 万字符历史和 480 条 Observation 的语义内容不变，只调整 Context 的物理顺序；排除 Warmup 后每组七次请求，Inbox-first 布局命中 493,568/560,974 个输入词元，即 87.98%，原布局为 6.39%。

两组验证的模型和工作负载不同，不能用来重算 ME-08 成本；它们证明的是单条消息内部的稳定前缀可以被缓存，并且结构化 Context 可以采用缓存友好的物理布局。

## 后续优化方向

- 将跨 Context 相同的 System Prompt、工具合同和协议层放入公共缓存域，避免由 `context_id` 造成缓存碎片。
- 把 Inbox 表示为不可变的增量内容块，并保留历史块末尾的缓存断点，使新增 Observation 不移动既有断点。
- 对官方 OpenAI API 与 CLIProxyAPI 分别进行显式断点能力测试；只有响应中出现缓存写入和后续扩展命中，才把该线路标记为支持显式断点。
- 用请求规范化哈希记录各段内容，直接测量每轮第一个发生变化的分段，而不是只依赖服务端返回的缓存词元数。
