# Morphz 数据库选型深度评估与混合双轨存储架构设计

> 历史选型记录：本文描述的 LanceDB 路径已从默认 Runtime 移出。当前 Core 只保留 SQLite Event History/Session/Context，检索后端由 Extension 提供。

在重构智能体底座时，数据库的选型是决定系统**部署摩擦力、单机吞吐量以及未来扩展性**的最核心工程决策。

针对“用 SQLite 还是换”的命题，我们站在资深系统工程师的角度，从智能体的核心运行特征出发进行深度审视，评估 SQLite 的瓶颈，对比替代方案，并提出一套优雅的“嵌入式混合双轨存储”架构。

---

## 1. 智能体系统的存储与检索特征

智能体（Agent）系统的读写行为具有极强的不对称性：
1.  **高频、高精度检索（读为主）**：每一轮 Agent 决策与 Fold 计算，都必须进行多次向量近邻搜索（RAG 召回）、关键词全文检索以及事件流的时序查询。
2.  **低频、高安全性持久化（写为辅）**：仅在生成新的 Event、写入 Snapshot 或 Curator 产生少量图谱关系时写入，要求强 ACID 保证以防止脑区数据损坏。
3.  **零摩擦部署要求**：智能体非常强调单机运行、边缘端部署及“开箱即用”的能力。如果强行要求用户本地运行一个繁重的 PostgreSQL 加上独立的 Milvus/Elasticsearch，会导致极高的集成门槛。

---

## 2. 三大选型路线对比分析 (Trade-offs)

### 路线 A：坚守并深度榨干 SQLite (单机嵌入式)
*   **方案**：在 WAL 模式下，引入 `FTS5`（全文检索）与 `sqlite-vec`（零依赖向量检索，支持静态链接 Rust）。
*   **优势**：
    *   **零部署成本**：单文件存储，无额外后台 daemon 进程，零网络网络调用开销。
    *   **极高的单机读取性能**：通过开启 WAL 并分离“单写多读”连接池，读性能在万级数据内极其优异。
*   **劣势**：
    *   **向量搜索瓶颈**：SQLite 缺乏原生的 **IVF-PQ (倒排乘积量化)** 或 **HNSW** 高性能索引支持，在节点规模达到百万级时，暴力扫描性能会严重下降。
    *   **不适合分布式集群**：无法实现多机共享大脑。

### 路线 B：升级为专业的分布式数据库 (PostgreSQL + pgvector)
*   **方案**：外置 PostgreSQL 作为核心存储，结合 `pgvector` 插件进行向量搜索，`GIN/FTS` 进行全文检索。
*   **优势**：
    *   **工业级保障**：拥有顶级的事务隔离性，高并发写入及多机集群水平扩展能力。
    *   **向量检索成熟**：pgvector 提供了工业级的 HNSW 索引，查询速度极快。
*   **劣势**：
    *   **灾难性的部署门槛**：用户必须本地安装、配置和运维 PostgreSQL 服务，极大地伤害了智能体“开箱即用”的高雅体验。

### 路线 C：升级为专为 AI 打造的本地嵌入式混合存储 (SQLite + LanceDB)
*   **方案**：
    *   **关系型数据 (EventHistory/Snapshot)**：依然使用 **SQLite** 承载（发挥其强事务和关系查询的优势）。
    *   **图谱记忆与检索 (向量/全文)**：引入 **LanceDB**。LanceDB 是一个基于 Rust 编写的、无服务器（Serverless）嵌入式向量数据库，支持单目录存储。
*   **为什么选择 LanceDB**：
    *   **顶级 ANN 算法支持**：底层采用 `Lance` 柱状文件格式，原生支持 IVF-PQ 和 HNSW 索引，向量检索在百万规模下达到微秒级。
    *   **集成顶尖全文检索**：LanceDB 内部集成并使用了 Rust 最顶级的全文搜索引擎 **Tantivy**（Rust 编写的类似 Lucene/Elasticsearch 的引擎，单机性能超越 ES 且资源占用极低），直接支持向量与文本的 **Hybrid (混合检索) 与 Rerank 重排序**。
    *   **依然零安装部署**：和 SQLite 一样，只需在 Cargo.toml 引入依赖，无需启动任何后台进程，完美保持了零摩擦的架构美学。

## 3. 最终架构抉择：嵌入式混合双轨存储 (Hybrid Embedded Storage)

我们重新思考后的最终抉择是**采用“SQLite + LanceDB”的本地双轨引擎混合存储方案**。这套架构完美兼顾了关系事务性、全文与向量检索性能，并且对用户保持了 100% 的“开箱即用”无缝体验。

```
              ┌────────────────────────────────────────────────────────┐
              │                Morphz 混合双轨存储底座                 │
              └──────────────────────────┬─────────────────────────────┘
                                         │
                ┌────────────────────────┴────────────────────────┐
                ▼                                                 ▼
   [ 轨 1: 关系与时序数据 (SQLite) ]                 [ 轨 2: 图谱记忆与高阶检索 (LanceDB) ]
   • EventHistory (不可变事件流)                     • 语义向量实体 Node (IVF-PQ 索引)
   • Context Snapshots (脑区快照)                    • properties 文本字段 (Tantivy 全文索引)
   • Session 元数据与状态                            • 语义/文本 Hybrid 混合检索与重打分 (Rerank)
   ──────────────────────────────                    ───────────────────────────────────
   优势: 保证 ACID 事务，关系查询便利                   优势: 微秒级 ANN，工业级分词，零部署摩擦
```

### 3.1 读写分流逻辑：
1.  **写入操作 (Write Pipeline)**：
    *   当产生 `chat/user_message` 等事件时，写入 SQLite 的 `events` 表（写单线程）。
    *   当 `Curator` 提取到实体和技能时，写入 SQLite 的关系表（进行实体关系关联），同时将实体的 Name/Description/Embedding 向量实时写入本地的 `LanceDB` 目录。
2.  **检索操作 (Retrieve Pipeline)**：
    *   Orchestrator 被唤醒时，直接调用 `LanceDB` 驱动，在内存/磁盘目录级进行 Hybrid 混合检索（向量距离 + Tantivy 全文检索），取得最匹配的 Nodes，再到 SQLite 中根据 ID 查询最新关系，保序拼装入大脑。
