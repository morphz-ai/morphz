# 事务对象与生命周期草案

日期：2026-09-06  
状态：设计提案；不冻结数据结构、协议或 Runtime 映射

## 术语与范围

本文将需要执行、回应、决定或交付的具体事务称为“工作事项（Work Item）”，以区别于数据库事务和上下文事务。这是设计术语，最终界面名称待验证。

Work Item 表达需要执行、回应、决定或交付的一件事。它不是一条聊天消息，也不直接等同于 Runtime 的 Objective、Thread 或 Schedule。后续需要核对和设计映射，避免另建与 Runtime 相矛盾的调度权威。

## 一个事项需要表达什么

| 维度 | 拟表达的信息 |
| --- | --- |
| 身份与来源 | 稳定标识、来源目标／会话、发起 Principal、谁创建、为什么创建 |
| 工作要求 | 要做什么、约束、预期产物、完成标准 |
| 责任 | 负责人类型与稳定标识、指派者、参与 Principal、分派权限；明确区分人和 Agent |
| 模型策略 | Agent 执行时的模型选择或自动选择策略、预算 |
| 时间与顺序 | 优先级、截止时间、预计耗时、依赖和可运行条件 |
| 进度 | 当前执行状态、等待什么、谁可以解除等待 |
| 交付 | 产物、版本、接收 Principal、关联 Session 与可信回执 |
| 变更记录 | 分派、模型与范围调整的修订及生效点 |

这不是要求用户填写上述所有字段的表单。Agent 应根据上下文形成安排，用户只在需要时查看或调整。

## 负责人、模型和交付位置分离

负责人回答“谁对这件事负责”；模型策略回答“Agent 用什么能力执行”；交付位置回答“结果送到哪里”。

同一个 Agent 可以用不同模型处理不同事项。切换模型不应导致事项历史重置，也不意味着自动更换负责人。模型能力、工具兼容性、数据发送范围和成本约束需要共同检查。

人的负责人和结果接收者通过 Principal 标识，Session 与 Edge 只是交互和送达入口。一个事项还需区分发起人、当前负责人、批准人和授权来源：转交任务不自动转移原负责人的凭证或权限。具体身份和交接契约见[Principal 与团队协作](./06-principals-and-team-collaboration.md)。

## 生命周期：先区分三组状态

不把接收、执行和交付混在一个状态字段里。

1. **分派关系**：待接受、已接受、拒绝、转交等。是否需要显式接受由协作规则决定，不要求所有事项逐项人工确认。
2. **执行进度**：已计划、可执行、执行中、等待、暂停、成功结束、失败、取消等。
3. **交付情况**：尚无结果、待交付、已交付、需要验收等。哪些结果必须验收取决于事项契约。

这些是概念分组，枚举与命名待验证。Inbox 的未读／已读属于呈现状态，不能替代上述业务状态。

## 形成与分派

Agent 在授权范围内自主创建和安排正式事项；一般讨论也可以保留为未承诺的建议。用户应能辨别二者，并调整自主规划的范围。

指派给人的工作应提供足够材料和完成要求。发出分派请求不等于已经取得接受确认；团队预先授权的直接分派则可采用不同规则。

用户可以重新分派，但应保留历史责任和交接材料，避免旧负责人继续提交时无声覆盖新进度。

## 执行、等待和恢复

事项开始需要满足依赖、权限、可用资源和必要的接受条件。等待应指向明确对象：某人的决定、工具结果、其他事项、定时器或资源。

一个事项等待，不应阻塞无依赖的工作。恢复由相关条件满足触发，结果必须回到正确事项及其有效执行版本；迟到结果需要识别，不得误唤醒已取消或已换代的工作。

暂停不等于取消，取消也不能撤销已经发生的外部操作。

## 人工调整与模型切换

用户可以修改负责人、模型、时间、优先级和范围。界面需区分已保存的安排与正在执行的实际情况。

初步提案：尚未开始时使用新安排；已经执行时展示可选择的生效方式，例如下一次模型调用生效，或中断并交接后重启。具体默认规则待决定。

不能悄悄终止已经发出的模型请求，也不能为切换模型随意重复带副作用的工具操作。交接材料应引用最新有效的上下文和产物，同时遵守接收者权限。

## 结果与完成

执行者报告“完成”不自动证明满足了事项要求。根据约定，需要核对产物、检查结果、接收者确认或外部成功回执。

例如，在浏览器填写推文不等于已发布；点击发布但没有确认结果，也不等于成功。无法确定时进入结果待核对的处理路径，避免重复发布。

完成后，相关依赖才按其契约解除。验收退回属于明确的返工或新一轮执行，不应抹除原交付记录。

## Inbox 是事项的参与视图

提议将 Inbox 作为中心工作对象面向某个参与者的视图，而非另一份任务数据库。可呈现待处理、待决定、等待他人、相关更新等类别；具体信息架构待原型验证。

同一个事项在负责人、协调 Agent 和相关协作者的视图中可以呈现不同重点，但保持同一身份和权限边界。不同 Edge 展示中心视图并提交操作，不各自维护独立业务真相。

## 必须覆盖的交互验证

- Agent 分派工作给人，人拒绝、转交或说明受阻。
- 人在不同 Edge 调整同一个事项，出现版本冲突。
- 事项等待时切换负责人或模型，随后旧结果到达。
- 模型不可用或不满足能力要求，安排如何继续及提示。
- 网页内容包含指令性文字，但不具有改变用户授权的权力。
- 手机离线后重复提交审批／修改，中心能识别有效操作。
- 发布成功但确认信号丢失，系统不会盲目再次执行。
- 协作者或 Edge 权限被撤销后，交付与读取范围正确收缩。

以上是待执行的验证场景，不是测试结果。
