# Context 提示与执行契约审查

既有 20 类冲突的自动回归、真实 DeepSeek／GPT 路由及原应用重开证据对应
`3ae7cdfc6e3b`。后续实际工作又发现第 21 类：工作轮次缺少步骤注解。
下方保留前一轮证据；本轮补充的实现、验证与限制单独列出，不用历史成功
冒充新路径通过，也不以纯文档提交号冒充运行二进制版本。

## 审查范围

检查的是最终请求的组成，不仅是一个 System 字符串：三个已有 System profile、
Reality/Epistemic 公共契约、Yao Language Card、Context protocol 与动态 evaluate、
Context 操作和工具说明、Custom 规则、Harness profile/binding、infer 类型指令、
Session IO 格式、工作续接、维护／收尾／日程回执／拒绝恢复及协议纠正提示。
另沿实际来源 Event 和原生调用回执核对提示所承诺的行为是否可实现。

## 已确认的冲突与整改

| 问题 | 当前整改 |
| --- | --- |
| 旧的正文 JSON 封套、尾段与专用 reply，和正常正文规则并存 | 移除执行解析及专用工具；正文与独立类型化注解使用现有 Session IO |
| 通用规则称正文只回当前 Session，infer 指令却要求返回父 Plan | 明确实际 caller；内部 infer 有独立的模式、类型返回说明，不冒充第二次用户回答 |
| IO 载体 `morphz.chat` 容易被误当成返回类型，普通讨论规则可能遮蔽内部 record 返回 | 明确 caller/type 优先；即使嵌入的用户话题是普通讨论，infer 也必须返回完整声明值，由父 Plan 确定性投影，不能先抽出 reply 字段 |
| 虽允许隐式正文，后文却优先要求两个原生工具消息，把长正文再次放进 JSON 参数 | 原应用多段正文验收确实触发该路径，完整原响应已捕获；取消这个不必要偏好，默认普通正文＋同响应独立注解，保留等价显式 IO，而不放宽 JSON 校验 |
| 纯 infer／不调用外部工具／只返回声明 JSON 的要求，可能被读成连 Session IO 注解都禁止 | 区分业务效果、业务正文与通信消息；共同契约和内部 infer 的动态 tool-gate 同时明确启用时同响应交付注解，不额外工作或补推理；真实验收曾抓到省略，未按“正文没报错”冒充注解成功 |
| “工具调用后总再推理”把消息载体与工作混淆 | 工作才有必要工具往返；绑定返回与伴随注解提交后直接结束 |
| Delivery／维护／收尾分支移除 IO 工具，而提示仍要求交付注解 | IO 保留；阶段可执行权限与工具定义分开 |
| 临时阶段重建提供给模型的工具列表 | 同一能力路由的工具定义固定，当前阶段由 Runtime admission 强制检查 |
| 每次返回绑定被放进 Context 前缀，会破坏长前缀复用 | 移至 evaluation-environment 动态尾部；新增相同前缀／Inbox 字节与 cache key 回归 |
| 文本声明的 Context 顺序漏掉实际 Custom／格式定义／能力区 | 按实际编码顺序说明，不另造布局规则 |
| 语义 System profile 后又追加裸文字，破坏单 S 表达式 | 公共 IO／回执规则只装入 System 对应节点一次；Custom 规则也在根内 |
| “结果后必须再维护一次”与无多余推理、Mind 已准确的情形冲突 | 只有确需保留的状态变化才做 context_tx，不为结束回复或注解额外往返 |
| critical 先维护与 finalizing／维护额度用尽的指令互相阻塞 | 明确后两种 Runtime 阶段优先，不能再陷维护循环 |
| 恢复、冷却、收尾和中断续接仍使用“另一个工具／只返回剩余正文”等过宽排他要求；VM 注释核也残留只回 Session 与必须维护后结束 | 全部统一到实际 caller、业务／控制边界和独立通信消息；续接只补正文后缀但仍同响应交付注解，VM 核不再强制多做一轮维护 |
| evaluate.thread.id 使用了 Session／root 路由；部分协议路径不存在 | 使用真实 Thread ID，未知不猜；修正当前线程／交付模式的路径说明 |
| context-tx 的 reason-required-for 漏 retire-session | 与操作实现及工具说明对齐 |
| 新消息可以生成，但部分原生续接会过滤掉其调用或遗漏回执 | 按真实 call ID 保留调用／回执，不把显示元数据变成 Observation、Job 或工作唤醒 |
| 原生 IO 回执被通用工具回执错误赋予 Observation 引用 | IO 回执只关闭自己的调用；不生成 Recall 引用，也不允许作为工作结果注解来源 |
| 模型流事件没有实际 model_attempt_id，Session IO 草稿关联无法建立 | 从真实物理请求携带该 ID；用真实 DeepSeek 的提前到达增量核验，不以终态重放代替流式显示 |
| 把语义上的最终返回与 Provider 的 final 文本频道混用，模型把正文留到注解工具回执后 | 明确同一响应内先产生完整 assistant commentary/text 正文，再交付独立注解；只有通信调用伴随时，该可见文本就是隐式返回，不是工作进度。上游合成捕获确实见过仅注解调用或仅正文调用；不是解析器丢失文本。统一提示后真实 GPT 单次请求实际返回流式正文及两项注解，无修复推理 |
| 后续真实工作发现：先完整正文的要求没有限定返回阶段；步骤 calls 只写语法，缺失检查只覆盖最终标题／结果 | 将正文先行限定为值返回；开启时每个工作调用都必须在同响应的同一 Session IO 注解中说明，补齐逐调用缺失诊断。内部 infer 的请求和动态 tool-gate 也同步说明中间工作响应，不能只在 System 要求后仍在当前指令中强调最终值。调用 index 只属于同一响应；已完成调用用本执行的真实 observation 解释，不把父执行结果计入本执行。不为显示元数据阻断业务、补推理或修改工具列表。原 20 类审查没有覆盖此实际工作轮次，是验收遗漏，不是模型能力结论 |

另查到提示承诺与应用实际接线不符：Host 原本仍依赖 WebSocket 的一次性 started，
订阅稍晚便丢弃 infer 后续正文。已改用现有 Session IO 完整快照与增量作为唯一
正文直播来源；工作和持久事实继续沿原事件流。新增真实 Runtime＋Host 的迟订阅
测试：先生成正文前缀，再订阅应用，断言完整前缀和后续文字都在生产 Activation
仍运行时可见，终态只保留一份回答，不补推理。
IO 的建立也不再等待 WebSocket 握手成功；两个传输独立，授权仍在读取和呈现前复核。

原窗重发验收另发现历史投影丢弃原输入的模型／推理设置，导致重发偷偷采用当前默认。
已从不可变 Runtime 输入 Event 的实际准入字段恢复设置，并让客户端历史契约保留它们；
重发仍是一次显式新请求，使用原正文、引用与范围，不读当前输入框来猜原选择。
已有记录不改写，后续授权、资料版本和模型可用性照常重新检查。

对原应用当前启用的 Agent Custom（revision 87）也作了只读核对：人格、表达和
主动性要求没有注入退役回复协议；其约束明确不改变权限、事实或协议。没有替用户
改写自定义资料。本次也未修改 script-studio 2.3.0 的工具能力或另加讨论特例。

discuss-script 源码仍为一个逻辑 infer，后面确定性投影 reply；没有加入第二次模型
润色。现有应用呈现依赖经授权的 Harness 声明，不从任意模型字段猜业务语义。
正常资料读取产生的物理往返须与重复 infer 分开计数。

## 不以提示代替的边界

工具可见不等于当前允许执行；Principal、静态能力、Thread generation、资源导入、
返回类型、目标结算、取消与幂等均由代码和真实持久状态检查。
注解不能改变这些事实。公开正文没有新的文本分隔符、关键词或隐藏可执行协议。

- 开关 on/off：稳定 System／工具定义相同，仅冻结的动态绑定和格式数据不同。

- 草稿增量、恢复、终态去重；真实 DeepSeek 同响应交付正文和注解，不补推理。

## Session IO 完整候选设计：一次类型化求值结果（待 review，未实施）

### 1. 结论与需要明确审阅的变化

建议把「一次求值产生了什么」收敛为一个类型化结果，再由 Runtime 将
正文、注解和工作提案分别交付。不能继续要求模型同时选择两个互不
约束的 API 输出通道，却把它们当作有生成保证的一个返回值。

这不是多写一段提示词，也不是现有 Session IO 已经具备的完整能力。
现有 Session IO 可复用的是 Message／Format 注册、类型校验、来源绑定、
流式 publication、持久回执和幂等；需要新增的是 Provider 边界上的求值
结果契约及其适配。**这会改变模型响应的传输表示，尤其工作调用的表示，
属于架构变更，不在本轮修复中擅自实施。**

首选候选是一个原生结构化 Evaluation 结果，而不是正文中的标记、尾段、
Markdown 代码块、一个注解专用工具，或多个靠提示维持顺序的 IO 调用。
如果其能力／成本验证不通过，应退回 review，不自动换另一套文本协议。

### 2. 现状和故障证据

当前 `llm::Response` 只有 `content` 与 `tool_calls`。普通 content 是
隐式返回，另一个 `deliver_message` 调用承载注解；Session IO 在模型
返回后分流校验，而不是厂商端强制同时生成这两部分。Context 使用
S 表达式不等于 Provider 输出也在受约束地生成同一个 S 表达式结果。

16:16 原始捕获属于 adapter 输出层：正文为空、合法注解存在。它不是
解析器截掉一篇已存在的正文；但也不证明旧厂商 HTTP 原包一定相同，
因为那一层当时没有保留。新隔离复测另有正文成功、注解错误嵌套、
重复字段和注解遗漏。重复字段样本从 SSE 增量、done、completed 到
Runtime 记录一致，没有发现该样本的拼接器篡改。保留这些不同证据层级。

### 3. 一套语义，不按模型或执行层级发明例外

候选的逻辑结构如下；这是设计类型，不是让用户或模型在普通正文里
书写的标记语法，也不是已经注册的现成 format 名称：

```text
EvaluationOutput
  disposition: work | return | silent
  body: optional existing Session IO Message
  annotations: optional existing typed annotations Message
  effects: ordered existing work/control proposals
```

- `body` 只承担正文／业务返回值。用户回答按原格式显示，内部 infer
  返回调用方声明的完整值，不能抽一个 reply 字段冒充完整 record。
- `annotations` 仍是独立类型化消息。执行、调用意图、观察结果是同一
  Schema 的不同作用域，不为 infer 创建第二套实现。它不能承载隐藏
  推理，不能授权工具，不能把模型自称成功变成执行事实。
- `effects` 不是新的工具库：名称、参数和权限仍来自原有唯一工具目录，
  转成现有工作提案，经原来的校验、审批、调度和幂等路径处理。
- Runtime 在请求创建时固定真实 Evaluation／Thread／generation／
  attempt 与调用方、返回格式、注解开关。模型不填写这些权威身份。
- 正文和注解以同一 Runtime 绑定关联，调用注解以本结果 effects 序号
  关联；观察解释只接受当前请求实际提供的 observation ref。

### 4. 中间步骤、最终回复、静默与开关

| 结果 | 正文的含义 | 注解要求（on） | Runtime 行为 |
| --- | --- | --- | --- |
| work | 可选的可见进展，不是最终答案 | 每个实际工作／控制提案有意图；只解释实际引用的观察 | 接纳合法提案，原调度器执行；业务需要才续推理 |
| return | 调用方声明的完整值／完整回答 | 当前执行标题、结果；必要观察解释 | 同次返回与注解提交后结束该 Evaluation |
| silent | 没有用户正文 | 不编造回答；保留实际控制语义 | 只在现有 no_reply 适用的绑定中接受 |

`return` 不得同时包含工作提案；`work` 不能靠 execution.result 结束
执行；空 body 的 return 不能用注解摘要代替。定时工作无新增而静默是
silent 的业务决定，和“执行记录应存在”分开。

开关仍只有 on／off，在新 Evaluation 开始时固定，对外层、infer、
子代理及步骤同样生效。off 不要求、不生成、不展示注解，body／effects
的业务校验不变；on 不等于事后多调用一个模型补元数据。切换不改变
进行中 Evaluation 的冻结绑定，也不改变工具目录。

### 5. 原生结构化传输到底能做什么

需要把「合法 JSON」「符合 Schema」「语义正确」分成三层，不能混称
结构化输出就一定可靠。DeepSeek 官方 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/)
说明 json_object 模式约束 JSON 语法，但可能返回空内容；官方
[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)
只列出 text／json_object 两种 response_format。不能据此假设当前路线
已经支持严格的完整结果 JSON Schema。

官方 [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)
有 beta strict 模式，需要对应端点与所有 function 的严格 Schema；
它保证被生成调用的形状，不保证模型一定选择通信调用。Chat 的
required／指定工具选择又不支持 thinking。不能为了强制元数据偷偷
关闭 max 推理、换代理、清空工具或改变用户模型。

因此候选分两道准入，而不是两个长期兼容版本：

1. 验证当前真实 Provider 路径能够生成一个完整结构化结果，并保持
   用户原来的模型、max、流式和使用记录；代理必须真实透传相关约束。
2. 对仅保证 JSON 语法的路径，Runtime 仍须验证字段、正文与注解覆盖。
   若真实续接仍遗漏或返回空内容，**此路径不通过验收**，不凭一次成功
   宣称有严格生成保证，不在普通正文中补标记或偷偷自动重试。

候选若采用 JSON 表示，正文依然是结构化字段中的字符串／类型化值。
不能把它宣传成“根本没有 JSON 封套”：与旧做法的区别必须是厂商原生
结构约束、单一明确载体、字段路径解码与独立消息投影，而非自由生成
一段 JSON 后靠修补解析。如果你不接受正文成为这个字段，这个候选
不成立，必须另选传输设计，不能以“用了 Session IO”绕过你的决定。

### 6. 工具稳定及工作调用的重大取舍

单独给最终正文启用 response_format、工作轮次继续要求原生调用加伴随
注解，仍然留下同一失败点，不能作为本方案的统一实现。

要让整个 EvaluationOutput 成为同一个原生结构化结果，候选需要将
工作提案也放在该结果的 effects 中；不再同时接受第二条原生工作调用
通道。Provider 适配层将它们交给原执行路径，不直接调用 shell／Host。
这会改变模型端工作提案的载体，而不仅是 UI 或注解补丁，须明确批准。

原有唯一工具目录的名称、Schema、顺序和语义保持，不新增 annotation
tool，不往每个业务参数里加注解。若原 API 工具清单需要一次性调整，
必须在 review 时列出确切清理范围与 cache 影响，不能先实施后解释。
不能把同一目录换个工具名再复制一份。原生工具结果历史也不能伪造：
新的提案结果按原 Runtime observation 进入 Context；不得在不支持
插入工具消息的 Provider 中塞入伪造的 assistant.tool_calls。

### 7. 流式呈现与提交边界

1. Provider 层按已固定的结构化结果契约解码，只向现有 Session IO
   output 流发布 `body` 对应的可见文字叶子。正文里谈到协议、JSON、
   deliver_message 或括号都只是字符串，不触发解析状态切换。
2. 字段必须先被结构边界识别；允许键乱序，不能要求靠模型先写某几个
   字段才能保证正确性。临时缺失信息时有界缓冲，不整篇等待终态。
3. JSON 转义、Unicode 拆包、乱序、重复键和大小／深度预算显式校验。
   注解与 effects 不流进正文，工作参数不在生成过程中执行。
4. 结束时完整验证 body 格式、返回类型、effects 和注解覆盖。使用
   同一 attempt 的持久接纳事务／幂等键发布独立消息与调度决定；崩溃后
   补投影已有提交，不重推理、不重发工作、不重放模型文本。
5. 中途断线保留已经公开的正文前缀并标记未完成；终态不能把前缀冒充
   完整答案。当前已有的 public-output、publication 去重与权限边界复用。

字段顺序不受 Schema 保证，长注解先到可能延迟首字；这是实际测试指标，
不能把单个正文优先例子称为流式时延已保证。

### 8. 不多调用一次模型，以及 discuss-script

纯讨论最终值与注解同次提交，不把通信消息当物理工作或等待工具回执
再推理。真正工作必须读取实际结果时，下一次推理仍是业务需要，不是
元数据修复。Runtime 应分别记录物理请求数、工作提案数和 IO 提交数。

`discuss-script` 的 infer 返回声明 record，仍由父 Yao 的确定性表达式
提取对话文字／其他字段；父级没有额外业务需要时，直接将该值作为
顶层最终返回，不再二次 infer 改写。infer 的可读叶子进入既有 evaluation
流，后续同源最终回复就地接替，不重复一份正文。子执行注解仍属于子
执行；不能为省推理把子标题冒充父标题。尾调用真正返回同一求值时可以
传播该返回包；父级另有业务执行时，父注解由实际父 Evaluation 产生。

能否解决原问题的判断：这个结构消除了“只有注解却等待下一轮答案”
的通道选择空间，但**不证明 DeepSeek 已经可以稳定生成它**。讨论的
重复 infer 与流式归属可以靠 Runtime 确定性机制验证；模型输出覆盖率
仍必须通过下述真实验收，不以设计推导代替结果。

### 9. 错误策略：不再以元数据破坏已有答案

正文独立有效、只有显示注解缺失／不合规时，保留并交付正文，记为
“回答已交付、注解不合规”，不能说开关注解验收通过，也不能把整轮
变成英文协议异常；不伪造标题／步骤、不自动补推理。

正文不存在、业务类型不合规、结构边界歧义或越权工作提案时，不执行
未接纳的工作、不捏造答案。保留已提交工作与实际错误，普通用户只见
一处可理解的说明、可按需展开的详情和明确的重新发送入口。下一轮
Context 说明原问题尚未成功交付，不靠匹配“继续”触发特殊重试。

### 10. 数据归属、验证与更新

Runtime 拥有求值绑定、接纳回执、工作状态与完整来源；Format Registry
拥有类型定义；Host／Desktop 仅投影获授权正文、元信息与实际执行。
优先复用现有 IO／Event／Plan 表与事务，不建 renderer 消息库或第二份
活动库。若现存事务不能承载原子接纳，则必须先列出 SQLite／PostgreSQL
数据模型与迁移供 review，不能顺带加存储。模型生成 result 不是业务
结论、数据质量或外部操作成功的权威证明。

批准之后才进入以下实施门槛：

- 离线重放：本次各类真实失败捕获、合法完整响应、零正文、空注解、
  混合工作、错索引、越权 ref、字段乱序／重复、任意字节拆包、引号与
  换行、正文讨论协议、超限、截断、取消和崩溃恢复。无付费模型调用。
- 集成：SQLite／独立 PostgreSQL、真实 Runtime＋Host／Desktop，on／off、
  普通回复、infer、子代理、工作续接、context_tx、no_reply、discuss-script；
  检查实际请求数、同源流式更新、业务工具权限与稳定目录摘要。
- 真实模型：先用目前有效 DeepSeek 路径验证普通、工作、记忆三类场景，
  公开每类次数与失败，先低成本隔离场景再验证真实长 Context 形状；
  GPT 作为已配置对照。调用预算和停止条件先明确，不调用过期订阅。
  千问／Kimi／GLM 矩阵按用户要求后补，不能记作已通过或不存在需求。
- 任一真实关键续接仍遗漏正文／必需注解或破坏 max／工作能力，就不把
  该路径交付到原应用。没有“只要最后没报错就通过”的验收条件。
- 只在没有在途任务、远离日程到期时清洁切换；旧事件／会话／回执只读
  保留，不迁移重放，不并存两套可执行文本协议。确有在途旧绑定则等它
  结束，而不是为了兼容修改或终止它。
- 更新原 Runtime、原 Host 和原安装，核对精确构建、身份、草稿、资料、
