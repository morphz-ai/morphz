## 证据与决定

原生 Responses 的 `text.format` 约束消息内容，不保证工具调用轮一定
包含一条消息。2026-10-20 的真实 DeepSeek 探针在强要求步骤注解后仍只
返回 function_call；最终答案才出现 calls[0].intent，已不指向当前调用。
因此不能把“最终正文与注解同值成功”当作“工作中注解已解决”。

统一结果包含 body、effects、annotations：工作提案与其 intent 在同一
effect 中，整体标题/进展/结果和已完成 observation 说明在 annotations。
不再生成独立注解 deliver_message，不生成正文标签。Runtime 决定调用
ID、归属、结果关联、授权和终态；模型没有状态提交权。

## 生成与接收是两套职责，不是两个交付通道

- 生成：启用时明确要求实际工作提供适用标题、进度、步骤意图和结果。
  普通聊天不要求活动摘要。关闭时不要求或使用注解。
- 接收：缺失、null、错误类型、过长或多余的显示字段仅产生有界诊断，
  不否定独立有效的正文或工作。模型原始返回保留，绝不伪造显示信息。
- body 的业务类型、工作名称与参数、权限及 typed infer 仍严格校验。
  缺少正文且没有实际工作/合法等待不能视为成功；注解不是正文。
- 完整普通回复可由 Runtime 构造为无注解的隐式返回。不得扫描正文中
  的 XML、Markdown 或协议示例来提取注解或执行提案。
- 不能同时执行同一响应里的原生调用和 effects 两组提案。只存在原生
  调用的兼容返回可以按原动作执行，不因缺少注解失败；未知参数不修补。

## 原生 API 和弱保证入口

Schema 必须按实际绑定发送给已验证支持的物理入口，不能从模型名字推断
支持。借助已有 route candidate capabilities 冻结能力声明；未声明的
入口不擅自携带可能被拒绝的新 API 参数。所有路径使用同一语义解码。

Schema 是生成要求，Runtime 校验是提交条件。不得把 HTTP 200、strict
参数回显、一次成功当作强保证。开放的现有业务参数 Schema 不应为迁就
某供应商 strict 子集而重编码或裁剪；在不能无损编译成 strict 子集时，
必须明确记录非 strict 原生请求，不宣称强制解码或悄悄降级。

effects 是单次 Evaluation 的工作提案。选择统一生成路径时，原生工具
目录及顺序保留，原生 tool_choice 的禁用是显式稳定的返回载体选择，不
由注解开关决定，也不由 Provider 看到 schema 后自行推断。调用权限仍
取自原准入与 Runtime 工具校验，提案不会绕过任何授权。

## 流式与结束

按冻结的输出结构增量解码 body，支持转义、Unicode、任意 chunk 边界；
草稿与正式提交分开。只投影可见正文，不能将元数据或 typed child 的
内部值直接送给用户。最终完整值通过校验即结束，不增加补注解、修复
推理或答案中继请求。实际工具完成时才因新结果续接。

## 交付门槛

需要分开通过：冻结旧值恢复、缺失/错误注解容错、严格业务参数与权限、
普通回复、工作首轮 title/intent、结果关联、开关两态稳定工具目录、
无正文拒绝、公开正文流、typed infer 与 discuss-script 无重复推理。
隔离真实 DeepSeek 完整 Runtime 通过后，才可安全更新并验收原应用。
