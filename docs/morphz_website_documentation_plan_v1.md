# Morphz 官网与文档总体规划 v1

> 状态：执行中
>
> 公开文档入口：`website/content/docs/{zh,en}`
>
> 官网实现：`website/`

## 1. 目标

Morphz 官网首先是产品文档，其次才是品牌展示。它必须让新用户完成第一次真实模型响应，让 Operator 能定位运行问题，并让开发者理解 Runtime 的稳定领域边界。

文档同时承担三种职责：

1. **操作指南**：用户可以按步骤完成任务；
2. **产品契约**：只声明当前可以验证的行为；
3. **测试输入**：命令、配置、链接和关键流程可以进入自动验证。

## 2. 当前材料盘点

规划启动时，仓库中有 105 篇 Markdown、约 2.8 万行内容，另有 250 行 README。现有材料并非不足，而是缺少出版边界：README 同时承担定位、架构、安装、配置、运维和状态说明；`docs/` 同时包含当前设计、早期架构、研究、评测和实现记录。

现有材料按以下规则处理：

| 类型 | 位置 | 是否直接发布 | 处理方式 |
|---|---|---|---|
| 公开权威文档 | `website/content/docs/` | 是 | 中英文同构，描述当前行为 |
| 架构与产品设计 | `docs/` | 否 | 作为公开文档的来源，保留状态说明 |
| 研究与论文材料 | `docs/research/` | 后续选择性发布 | 明确标注研究性质，不作为产品承诺 |
| 评测与实验记录 | `docs/`、`morphz-evals/` | 后续汇总发布 | 发布方法与可复现实验，不直接暴露临时记录 |
| 历史或失效设计 | `docs/` | 否 | 标记历史，后续集中归档 |

第一阶段不批量移动旧文档，避免破坏交叉链接。完成逐篇分类后再整理目录。

## 3. 信息架构

```text
官网
├── 首页
├── 文档
│   ├── 开始使用
│   ├── 核心概念
│   ├── 使用指南
│   ├── 运维与故障排查
│   └── 参考
├── 架构与研究（后续）
├── 版本、迁移与能力状态（后续）
└── Changelog（后续）
```

首批公开文档覆盖：构建与 Setup、模型选择、核心概念、Context 与 Recall、执行生命周期、Provider 与模型路由、远程 OAuth、配置、Execution Target、运维、安全和 CLI。

## 4. 内容规范

每篇公开文档必须包含：

- 稳定 slug；
- 中英文对应页面；
- 一句话描述；
- 信息架构分区和顺序；
- `current` 或 `preview` 状态；
- 可执行命令中的真实参数，虚构物理模型名必须明确标为结构示例。

写作规则：

1. 先说明用户要完成什么，再解释内部原因；
2. 当前事实、限制和未来设计分开；
3. 不使用“内部记录”等面向实现者的界面语言；
4. 不猜测模型名、容量、价格、账号身份或服务能力；
5. 一个概念只有一篇权威定义，其他页面链接引用；
6. 产品术语以 `认知帧 / cognitive frame` 为准；
7. 时间示例使用带明确 offset 的 RFC 3339；
8. 文档不能为产品缺陷寻找操作借口。

## 5. 中英文策略

中英文共享 slug、分区、状态和测试。中文是当前主要编写语言，英文不是机器占位翻译，必须保持相同事实边界。

发布规则：

- 新的关键页面没有对应语言版本时，不能标为双语完成；
- 行为修订必须同时检查两种语言；
- 代码、配置键、状态名和稳定 ID 不翻译；
- UI 术语需要与 Dashboard、TUI 和 CLI i18n 目录一致。

## 6. 技术结构

```text
website/
├── app/                         # 官网与文档路由
├── content/docs/{zh,en}/        # Markdown 权威正文
├── lib/docs.generated.ts        # 构建时生成，不手工编辑
├── scripts/generate-docs.mjs    # 内容编译和元数据校验
└── tests/                       # 路由、内容和渲染验证
```

官网与主代码保存在同一仓库，但拥有独立构建和部署流水线。这样 CLI、配置和 API 变化可以在同一个 Pull Request 中更新文档。

## 7. 自动验证计划

### 第一阶段

- 中英文 slug 一一对应；
- Front matter 必填字段与状态合法；
- 站内链接目标存在；
- 首页、文档首页和文章路由能够服务端渲染；
- Starter 元数据和占位内容完全移除；
- 生产构建通过。

### 第二阶段

- 从 Clap Schema 生成 CLI 参考并检查文档命令；
- 从配置结构生成字段参考和示例；
- HTTP API/OpenAPI 参考自动生成；
- 文档代码块加入可执行或语法验证标签；
- Playwright 验证导航、搜索、语言切换和移动布局；
- 术语 lint 防止“认知框架”等旧称重新出现。

### 第三阶段

- 真实空环境完成 Setup 的端到端测试；
- API Key、自定义端点、设备码和远程回调分别建立流程测试；
- 每个发行版本生成能力状态与迁移页面；
- 文档版本与二进制版本建立明确对应关系。

## 8. 首版验收标准

1. 新用户可以从空环境开始，在不阅读内部设计文档的前提下获得第一次真实模型回复；
2. 用户可以解释模型选择器中的名称来自别名、物理模型还是路由；
3. SSH 用户可以选择设备码、手工回调交接或端口转发完成 OAuth；
4. Operator 可以沿模型路由、账号、调度和存储边界定位常见问题；
5. 中英文页面具有同样的导航、slug 和当前状态；
6. 所有公开页面均来自 `website/content/docs/` 的唯一权威正文；
7. 官网生产构建和内容测试通过。

## 9. README 收口

官网首版稳定后，根 README 应收缩为：

- Morphz 的一句话定位；
- 三个核心能力；
- 最短构建与 Setup 路径；
- 官网文档入口；
- 当前开发状态和贡献入口。

架构、配置、Provider 细节和运维说明从 README 移入对应权威文档，避免同一事实存在多份副本。
