# Morphz 混合沙箱运行环境设计方案

为保证下一代智能体 `Morphz` 在执行由 AI 自动生成/修改的代码与技能（Skill）时的绝对安全，我们结合 OpenClaw 与 Hermes 的沙箱隔离及增量同步机制，设计了如下的**三层混合沙箱隔离与增量状态持久化架构**。

---

## 1. 混合沙箱执行架构 (L1 -> L2 -> L3)

Morphz 系统设计了渐进式、低延迟的分层隔离机制，以求在性能、安全和生态完备性之间达成完美平衡：

```
                    [ AI 生成的 Skill / 代码 ]
                                |
                                v
+---------------------------------------------------------------+
| L1: AST 静态白盒审计 (yao-parser 扫描高危外部 FFI / syscall)   |
+---------------------------------------------------------------+
                                |
                                v (通过审计)
                  是否为纯 yao-lang 技能计算？
                     /                    \
                   YES                     NO (需要 Python/Bash 等重型依赖)
                   /                        \
                  v                          v
+-----------------------------+    +-----------------------------+
| L2: WASM 进程内微秒沙箱     |    | L3: 重型隔离容器            |
| (Wasmtime 运行 yao-vm)     |    | - 备用: 本地 Docker         |
| 纯数据过滤/交互UI逻辑       |    | - 首选: 远程 Serverless     |
+-----------------------------+    +-----------------------------+
```

### L1 层：AST 静态白盒审计 (前置防线)
在任何代码执行前，利用 `yao-parser` 将 AI 输出的 `yao-lang` 源代码解析为抽象语法树（AST）。
*   **黑名单扫描**：遍历 AST 节点，严禁导入未经报备的 C FFI 接口或外部库。
*   **权限约束**：检查是否包含外部文件读写、系统命令派生等高危动作，不通过则直接终止执行，在编译前阻断恶意逻辑。

### L2 层：WASM 进程内微秒沙箱 (本地高效运行)
很多人认为“纯计算任务”不需要沙箱，这是极危险的。如果直接运行不可信代码（如 Python 的 `exec` 或 JS 的 `eval`），大模型可能因为代码幻觉写入恶意死循环或 OOM 耗尽内存锁死宿主进程。
WASM（WebAssembly）在设计上天然就是为了执行不可信二进制代码而生的进程内沙箱（In-process Sandbox）：
*   **沙箱编译与硬隔离**：宿主使用内置编译器将 `yao-lang` 代码直接编译为标准的 `.wasm` 字节码。WASM 运行于严格隔离的线性内存空间中，**默认没有任何系统调用接口（No Syscall）**——它甚至没有指令可以进行网络请求、访问磁盘文件或派生进程。
*   **L2 核心应用场景**：
    1.  **自进化数据过滤与清洗**：AI 提炼并高频调用的无状态数据处理器（如字符串正则切割、API Response 规整），需要微秒级响应。如果为这类高频短任务拉起一个 Docker，光容器启动延迟（秒级）就会拖死整个智能体。
    2.  **UI 交互映射控制器**：在 Canvas 画布上，用户触发的交互逻辑需要高速过滤和计算，L2 沙箱是天然的进程内执行屏障，既能防范注入攻击，又能保证极致响应。

### L3 层：重型隔离容器 (远程 Serverless 与本地 Docker 配合)
**有了 L2 为什么还要 L3？**
因为 WASM 的隔离性太彻底，它**完全无法兼容现有的庞大二进制软件生态**。如果 AI 需要执行诸如“运行 `npm run build` 进行前端打包”、“调用 Python 的 NumPy/Pandas 进行复杂的数据分析与绘图”或“使用 `git` 提交代码”，这些操作必须依赖完整的操作系统（Linux）以及复杂的第三方依赖库。此时，系统自动升级至 L3 重型容器：

*   **为什么要设计“远程沙箱”？本地 Docker 不行吗？**
    1.  **轻量部署与跨平台**：如果 Morphz 运行在用户的个人 Mac/Windows 电脑上，**强制依赖本地 Docker 是极其沉重的**。用户很可能没有安装几 G 内存开销的 Docker Desktop。远程 Serverless 沙箱（如类似 Daytona/Modal 的托管容器）可以实现客户端“零环境配置、开箱即用”。
    2.  **物理级零信任物理安全**：本地 Docker 与宿主机共享内核与物理网络，如果配置不当或容器逃逸，仍有可能危及宿主。云端远程沙箱提供了**绝对的物理防线**，即使大模型写出恶意逃逸指令，也只能破坏云端临时容器，对用户本地物理资产 0 危害。
    3.  **算力与 GPU 弹性**：大算力任务可动态利用远程 Serverless 强大的多核 CPU 或 GPU 运行，不受用户本地硬件上限的瓶颈制约。
*   **双向通信与本地 Docker 备用**：
    *   在企业内部或用户网络受限场景下，宿主支持 Fallback 回退到**本地 Docker 隔离执行**。
    *   宿主与 L3 沙箱通过统一的文件增量同步管理器（FileSync）及加密长连接维持执行一致性。

## 2. 远程沙箱执行流与 CWD 维持设计

为了避免 L3 沙箱在执行复杂多轮命令时状态丢失，我们参考 Hermes 的 `BaseEnvironment` 采用如下执行流：

1.  **统一单次派生模型 (Spawn-per-call)**：
    *   不维持易 hang 死的交互式长 Shell 进程，每一次代码运行都向 L3 容器派生一个 `bash -c` 子进程。
    *   在容器初始化时，将环境变量与别名 dump 到容器内的 `{TMPDIR}/morphz-snap.sh` 快照中，每次派生前先 `source` 快照。
2.  **CWD 维持与剥离**：
    *   在派生执行链尾端，强制输出 `printf '\n__MORPHZ_CWD__%s__MORPHZ_CWD__\n' "$(pwd -P)"`。
    *   宿主机端解析并抽取该 Marker 更新 local 任务的当前工作目录 `self.cwd`，并在给前端/LLM 返回结果前清洗掉该 Marker 行。
3.  **自适应轮询与排水 (Drainage)**：
    *   轮询子进程退出时，初始间隔设为 5ms（优化微型命令延迟），若未返回则回退至 200ms。
    *   采用非阻塞 `select` 监听 `stdout`。当主 Bash 进程退出且管道在 3 个周期内无输出时自动关闭，彻底解决后台孙子进程挂起管道导致工具超时的隐患。

## 3. 增量状态持久化与文件同步 (`FileSyncManager`)

由于 L3 云端容器随时会被释放销毁，宿主机与沙箱间必须有一套秒级同步的机制以保证代码文件的修改实时写回本地：

1.  **增量文件检测**：
    *   维持一张同步记录表，存储 local 文件的 `(mtime, size)`。
    *   每次执行命令前，仅对发生变化的文件加入 `to_upload` 列表。
2.  **内存 Tar 管道流传输 (Pipe Streaming)**：
    *   针对批量更新，严禁通过循环多次 HTTP 请求或大体积参数传递。
    *   在宿主内存中将 `to_upload` 列表打包并 gzip 压缩成 Tar 流，将其 Base64 编码流式写入容器进程的 `stdin`，容器端接收管道并同步执行 `base64 -d | tar xzf - -C /`，实现增量秒级挂载。
    *   容器退出时，执行反向 `tar` 归档输出到 `stdout`，宿主读取并增量回写。
3.  **安全防护与锁机制**：
    *   **2GB 大文件防御**：回写解压前校验归档大小，超标则报错，防御容器内恶意的磁盘撑爆攻击。
    *   **SHA-256 校验回写**：在同步回收（sync_back）时，仅对 SHA-256 哈希发生改变的更新文件进行解压写入。
    *   **信号延迟屏障**：在将文件写回宿主阶段，宿主进程通过列表延迟排队 `SIGINT` (Ctrl+C)，写完后再分发信号，确保本地代码目录不被中途打断造成文件半写损坏。
    *   **排他性 flock**：本地工作目录增量写入加 `flock` 文件锁，杜绝多 Agent 任务并发回写引起的文件覆盖踩踏。
