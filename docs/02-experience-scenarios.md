# 需求与交互场景

日期：2026-09-06  
状态：交互设计草案，不代表已发布功能

## 场景一：把推广计划变成共同执行的工作

**需求**：用户希望推广项目。Agent 提出联系作者、投稿、准备演示等安排，但不能让后续执行全靠用户记住聊天内容。

拟议流程：

1. 用户说明目标、约束和授权范围。
2. Agent 自主形成相关事务，安排负责人、时间、优先级和依赖。
3. Agent 可以自己准备材料，把需要用户或协作人员处理的事务送到相应 Inbox。
4. 人可以调整分工、切换某项工作的模型、改变时间或撤销安排，不必先逐项批准才开始全部工作。
5. 执行者提交结果；Agent 根据结果继续推进、修改计划或提出新的协作需求。

观察重点：用户是否减少了自行整理待办和重复催问；Agent 是否清楚地区分已执行、等待他人和未获授权的操作。

## 场景二：在网页输入框里根据最新进度写作

**需求**：用户正在浏览器准备发布内容，此时应能直接调用了解项目最新进度的 Agent。

拟议流程：

1. 用户打开发布输入框，从扩展发起“根据最新进展写一条推文”。
2. 浏览器 Session 在授权范围内取得当前页面场景，使用中心的共享认知及相关工作进度。
3. Agent 当场生成内容并在用户要求时填入输入框；存在多个可能关联的项目时，提供轻量选择。
4. 用户可以编辑。填写与发布分别处理，发布遵守明确授权。
5. 能取得可信成功回执时，将最终内容和链接关联回原事务；不能确认时保留待确认状态。

内容根据请求发生时的相关状态生成。浏览器标签页与 Session 的对应关系仍需设计。

适用延伸：邮件、投稿表单和其他网页操作。默认不推导为浏览器全部页面的持续采集。

## 场景三：Agent 主动协调协作人员

**需求**：有些工作必须由人判断或行动，且承担者可能不是用户本人。

例子：Agent 准备好技术投稿材料，请用户检查公开范围，请协作者确认署名，再根据确认结果完成获准的提交步骤。

每个参与者应能知道自己要做什么、需要哪些材料、何时需要结果，以及结果会解除什么依赖。拒绝、转交、受阻和补充说明应有正常处理路径。

需要验证：团队规则下何时可直接分派，何时需要接受；外部协作者尚未使用 MorphzWork 时如何参与；避免把发送通知当成对方已接受任务。

## 场景四：用户只有一小段可用时间

**需求**：用户不想遍历所有聊天记录寻找最值得先做的事情。

用户说明“我现在只有五分钟”后，Agent 结合优先级、耗时、截止时间和依赖，提出此时适合处理的事项。例如先确认一个影响其他工作的选项，再审阅一段短文。

用户仍可选择别的事项。系统需要说明推荐依据，承认耗时只是估计，避免凭一个不准确的数字强行安排。

## 场景五：在桌面、手机和浏览器之间持续工作

**需求**：同一项工作会经过不同设备，聊天历史和实际进展都不能断开。

用户在桌面开发项目，在手机查看同步的对话并调整安排，在浏览器完成投稿。不同 Edge 都连接同一个中心；交互可以发生在同一个 Session，也可以发生在共享认知的不同 Session。

需要验证：离线或网络缓慢时如何标识未同步操作，重复提交如何处理，设备撤销访问后如何阻止继续读取。离线 Edge 不应悄悄成为另一份权威中心。

## 场景六：工作期间改变方向

**需求**：用户的新决定应影响实际执行，而不只是收到一句“明白”。

用户将“宣传产品”调整为“先讨论架构”时，Agent 应识别相关事务和产物，说明哪些安排继续、暂停或需要修改。已发布的内容、未发布的草稿和正在进行的操作分别处理。

需要验证：变更如何生效，哪些影响可自主处理，哪些涉及不可逆动作而需要额外授权；避免无关任务被一并修改。

## 场景七：人的编辑进入后续协作

**需求**：人在网页、桌面或文档中作出的修改，不能随后被 Agent 用旧内容覆盖。

拟议体验是保存已识别的最终产物及版本，让后续任务引用合适版本。一次具体修改与长期偏好不同，不默认把每次编辑都提升为永久规则。

## 场景八：团队成员与同一个 Agent 协作

**需求**：团队希望同一个 Agent 理解项目整体进展，同时能识别每位成员、与他们分别沟通并安排不同工作。

例如，成员甲向 Agent 提出发布目标，成员乙在自己的 Session 中补充技术进展。Agent 使用允许共享的项目认知，向甲分派公开文案审阅，向乙分派验证任务，自己继续准备其他材料。甲、乙分别从个人 Inbox 处理事项，Agent 根据各自的交付推进共同目标。

同一成员换设备后仍是同一个 Principal；两个成员即使同名也不能混为一人。任务指派和交付使用稳定身份关联，不能仅依靠模型在自然语言中提及姓名。

需要验证：身份识别、跨 Session 结果关联、成员退出后的任务交接、不同成员请求冲突的处理，以及私密消息和产物不会通过共享认知泄露给无权访问者。详见[Principal 与团队协作](./06-principals-and-team-collaboration.md)。

## 端到端验证样本

“项目推广”可以串起以上场景：目标 → 自主规划 → 分派 → 准备材料 → 人在网页行动 → 结果回流 → 调整计划。

这一流程用于检验跨角色、跨应用的协作设计；产品范围不限于推广工作。

评估应观察复制粘贴次数、重复解释次数、人工追问次数、错误交接、完成时间和用户掌控感。具体指标和目标值待建立基线后确定。
