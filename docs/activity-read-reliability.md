# 活动读取与连接诊断边界

2026-10-25 的局部修复。Runtime 仍是任务、问题和执行状态的唯一权威；
本次不增加业务表、调度器或第二份任务状态。

## 已确认的失败链

原应用私有诊断日志记录了活动历史、当前活动及会话增量读取的 `TimeoutError`。
一次现场 GET 中，运行状态约 29 ms，而 `include_terminal=true&limit=200`
返回约 9.09 MB、耗时约 9.08 s，超过 Application 的 8 s 读取上限。
这是单次在线观测，不是性能保证或完整性能基准。

旧轮询把某个 Session 增量读取的失败也当作整体连接失败；检查连接成功后，
界面又没有保留上一次失败信息。另一个独立问题是 Dashboard 用近期历史页
代替当前工作清单：仍待答的老 Thread 会被较新的终态记录挤出分页。

## 读取模型

- 消息保持原 `after_sequence` 游标增量，不重读完整聊天，不改消息 ID／时间。
- Application 单次增量页为 100 条，每轮有界推进；失败不推进原游标，也不重发输入。
- 当前活动独立读取非终态库存。历史不参与证明当前任务是否存在、是否可控制。
- Application 后台不每轮拉终态历史；启动、已提交的终结／Objective 变化及显式刷新
  才读取历史页，每页 50。未重读的终态事实使用 `historyRetained` 明确区分，
  不把缓存伪称为本轮新读，权限／读取域变化仍撤销缓存。
- 显式刷新如果碰到后台读取，等待后真正执行本次历史读取；在历史读取中到达的
  新失效通知不能被旧读取清掉。
- Dashboard 独立取得当前库存，历史沿用原分页大小和加载更多入口；日常刷新不
  重拉无变化的历史。终态通知、连接恢复、加载更多、显式刷新，以及已知开放
  Thread 消失会触发历史更新。历史完成后再读小型当前库存，旧历史不能覆盖
  待答问题、实时控制、审批或权威汇总。缓存按 Context、Principal 和页界隔离。
- 一次 Session 增量失败不推翻已成功的运行状态检查，也不阻止其他 Session 和
  当前活动读取。认证失败仍不能被当成可用状态。

当前库存仍是有界快照读取，Dashboard 保留既有 15 s 兜底；本修复不宣称已经
把所有产品数据改造成全量事件流或消除了所有轮询。

## 诊断数据与安全

`ConnectionDetails.lastReadFailure` 是 Host 生命周期内的最近读取证据，不是
执行状态、日志全文或业务记录；不建表，不改变授权、命令身份或重试语义。
它只包含固定操作类别、白名单错误代码／HTTP 状态、时间和等待上限，健康重查
仍保留该条证据并可标记恢复。界面显示失败项、代码、模板化读取位置和时间。
任意异常消息、请求／响应正文、Token、Context／Session 原始 ID 均不进入该字段。
私有原始运营诊断沿用已有有界日志和权限，不上传。

排队、读取中的失效通知、历史不能挤掉待答任务，以及健康重查后的错误展示。
