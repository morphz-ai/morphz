# 事项：共享顺序、清单与看板

2026-09-13 更新。用户方向：传统软件已经解决的基本问题应采用成熟交互，AI 改善录入、整理与执行；尽可能让人少操作、不操作。所有操作接口都应对 Agent 友好，不因为技术上能做就增加产品概念。本轮实现清单与看板，不重建项目管理套件。

## 调研依据

官方文档能确认产品采用的交互模式，不能证明存在适用于所有人的“最优形态”。以下是本轮借鉴与不照搬的部分。

| 产品与官方说明                                                                                              | 成熟模式                                           | Morphz 的取舍                                                                    |
| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------- |
| [Things：安排事项](https://culturedcode.com/things/support/articles/2803579/)                               | 区分哪天开始做与截止日期，按时间组织清单           | 当前只有截止日期；显示“今天到期”，不把它叫“今天要做”，不凭空增加日程系统         |
| [Todoist：使用入门](https://www.todoist.com/help/todoist/get-started/get-started-with-todoist-OgNNJR)       | 事项旁直接完成，可重新打开；自然语言简化创建       | 本人事项可直接勾选与撤销，新建继续复用已有 AI 输入                               |

## 明确的问题与实现

1. 原筛选把“待我处理”与“进行中”并列，切状态会扩大负责人范围。改为“我的／Agent／全部”和“未完成／进行中／等待／已完成／已取消／全部状态”独立筛选。
2. 原行首勾图标只是装饰，实际完成要打开详情。本人普通事项现在支持行内完成、撤销和重新打开；失败不先消失，版本冲突不覆盖之后的修改。
3. 新增看板不能改掉原清单。清单保留已逾期、今天到期、之后到期、未设截止日期、已完成、已取消分组与紧凑行；不平铺成多行表单、不改成字段列式表格。排序在各组内呈现，日期分组和排序是两个维度；拖动不隐式改日期。看板独立按待处理、进行中、等待、已完成分列。
4. 顺序就是优先级，不再填写高／普通／低或数值。Human 与 Agent 共用持久顺序，各视图在其分组内按此顺序呈现。筛选下调整只替换这些事项的位置，不打乱其他事项。截止日期可修改，逾期单独标记，不擅自延长或创建提醒。已完成和已取消不标逾期；日期按本地日历判断。搜索标题、描述和项目名，不新增全文索引。
5. 标题、筛选、搜索、计数、新建留在同一顶栏。窄窗把筛选与搜索收进一个有当前条件摘要的弹出层，不增加第二层工具栏；详情返回和刷新保留筛选。
6. 项目、负责人和日期可在清单行的安排弹层、卡片和详情里修改并撤销；清单不默认展开所有字段。当前负责人只有已有的本人和 Morphz；指派不会自动执行。移项目保持对象 ID、历史版本和原会话；涉及跨权限或已有依赖／成果关联的移动明确拒绝，不复制对象或破坏引用。
7. Agent 事项的开始、重试、停止、等待和结果来自真实 Runtime。拖动不能把 Agent 伪装成正在执行或已完成；本人事项可拖动改状态，有后续依赖的完成仍需提交真实答复。看板固定四列；已取消事项在下方独立保留，不加入第五列或混称已完成。
8. 状态操作按视图分工：本人事项在清单行内直接显示状态下拉，不藏进安排弹层；看板以跨列拖动改变状态，卡片不再重复放状态下拉。非拖动／键盘操作和取消等低频状态仍可在既有事项详情中修改。清单拖动只改变同日期组内顺序，不改变日期或状态；Agent 进度不能手动指定。两种视图与详情复用同一状态命令、版本校验和撤销机制，不增加另一套状态或布局。

### 状态与当前操作（2026-09-13 继续优化）

保留上述视图，不增加状态列或另一种清单。执行失败、执行已结束但事项未完成、连接／执行安排异常属于待处理，不再混入等待。等待前置事项时显示具体负责人、事项名称及缺少答复／尚未开始／执行失败等原因；依据真实依赖与有效人工答复判断，不从错误文本是否含有“依赖”猜测。待审批使用准确的当前 Thread。旧的单独 waiting 标记若没有可核实原因，明确显示“未说明原因”，不从标题或描述编造依赖。

Agent 卡片突出一个当前操作：未开始→开始，需人工交接→查看前置事项，待审批→处理确认，执行中→查看进度，失败→重试，已有交付→查看结果。运行中停止／尚未提交调度的撤回保持直接可见；其他可用操作收入该事项菜单。单一成果直达对象，多份成果打开事项中的成果列表。查看结果不重执行，打开审批不授权。任务的对象声明、实际执行和成果仍为不同事实，不用重新排版掩盖状态问题。

## 操作接口

界面和 Agent 使用同一领域操作与存储回执。`list-tasks` 读取顺序、版本和安排；`reorder-tasks` 使用顺序版本；`arrange-task` 修改指定字段；`start-task`、`cancel-task`、`task-status`、`control-task`、`finish-task` 提供实际执行与交付操作。创建、读取、修订及成果复用既有对象工具。

每次调用根据真实执行输入确定身份与项目范围，不接受模型冒充身份或扩大范围；读写均校验权限。对象修改校验对象版本，排序校验独立顺序版本；重复命令复用持久回执，冲突需重新读取，不能静默覆盖人的调整。Agent 单次调用不跨出执行项目，即使界面可在本人授权项目间移动对象。

任务读取与安排结果同时返回可读的项目名、负责人和与界面共用的实际状态说明；排序结果返回这些事项在已保存顺序中的当前摘要。持久命令回执与当前状态分开：重读不重复执行，不能把安排保存说成工作已完成。

应用负责存储、执行与反馈，不另加固定 AI 排序规则。用户说“把 A 放到 B 前面”或“安排本周工作”时，由 Agent 理解要求并调用接口。纯安排不自动开始，不增加确认表单；需要额外权限或人工确认时保留边界。实际执行未结束时，不能重复开始或通过改派绕开。

## Human、Agent 与应用的边界

- 清单是事项的直接投影；人工查看、筛选、搜索、勾选不需要模型，也不发消息。
- 只有当前负责人的 Human 事项可直接完成。Agent 工作显示真实状态，不能用一个勾号伪装执行成功；他人的事项也不能代为勾选。
- 有未结束后续事项依赖的人工事项，必须通过既有“提交结果并完成”交接。清单显示提交结果入口，服务端也拒绝绕过，不能生成假的人工答复。
- 完成和重新打开追加修订，保留原结果、历史与执行账本。撤销只恢复事项状态，不撤回已经产生的后续执行，也不静默复活旧安排。
- 新建按钮只准备“安排事项”输入意图，不自动发送。AI 的价值是把用户要求整理成实际事项、按已有授权执行、交付结果，以及必要时请求人的处理。

## 本轮不做

不新增成员管理、多 Agent 接入、甘特图、日历、团队周期、自动排程、通知策略、另一个创建表单或默认 AI 建议清单。未来指派他人需求保留，不据此扩张当前界面。是否需要“今天想做”的计划日期，必须有独立于截止日期的真实需求再讨论。

## 验收要求

组合筛选、共享排序、安排／撤销、旧版本拒绝、人工交接、实际执行／停止、刷新与原草稿保持，都需真实命令和持久化验证。窄窗口、键盘、明暗主题和正式 Electron 200% 缩放单独检查；隔离自动化夹具不冒充原用户窗口验收。结果见[实施记录](./13-implementation-status.md)。
