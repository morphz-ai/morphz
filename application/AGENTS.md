# Morphz application work

This application now lives at `application/` in the Morphz repository. Run its npm commands in
this directory (or use `npm --prefix application` at the repository root). Runtime stays in
`../morphz/`; use `scripts/runtime-path.mjs` for integration-test binary discovery. Do not rely on
the former sibling MorphzWork checkout. Keep Runtime/Dashboard builds independent of Electron.
The old checkout is historical fallback, not a second development source. The repository root's
license/provenance rules apply; existing data paths and legacy protocol names remain compatible.

Before changing desktop UI or interaction, read `docs/16-ui-design-standard.md` and the current implementation notes in `docs/13-implementation-status.md`. For application hosting and workspace/Session routing, also read `docs/15-cognitive-application-host.md`.

The user-confirmed 2026-10-01 UI target is left navigation, center content, right Morphz subject information, and a shared bottom Agent-first input/application Dock region. The first implementation now includes bounded Runtime thread activity, a compact single-row composer, application quick access, and four subject information tabs; check `docs/13-implementation-status.md` for verified capability limits. Keep withdrawn subject/Logo experiments withdrawn; do not mistake the new sidebar for a complete personality editor, complete Runtime schedule directory, or full activity history. Read the design boundary before extending it.

The current Web/Desktop hosting target is `docs/24-shared-application-host.md`: share plain application logic, embed it in Desktop, and expose it through HTTP only for Web/remote clients. Desktop must not require a local application HTTP server or Vite. Runtime remains separate; its local object-tool callback must not reintroduce that HTTP dependency. Preserve existing data and authorization when changing transports.

Before implementing a new project or feature that persists data, design and review its production data model first. Specify the authoritative owner (Runtime, Platform, or Cognitive App), entity identity and relationships, relational versus object bytes, authorization, transaction/revision/idempotency boundaries, lifecycle and deletion, expected queries and indexes, SQLite/PostgreSQL behavior where Morphz owns the store, and migration/test strategy. Do not ship a whole-workspace JSON snapshot, renderer-owned database, temporary dual-write path, or demo schema as the production model. Test the actual Client and Agent write paths against that model before calling the feature complete. Development test data alone is not a reason to retain compatibility code or delay a clean cutover.

The continuous exchange frame still overlays the unchanged application canvas, including when pinned or in a short window; pinning prevents auto-collapse, not canvas resizing. The 2026-10-01 target replaces the old input-tool Dock definition: application shortcuts/Launcher belong in the floating application Dock, media/attachment tools belong to input, and history/pinning controls belong to the exchange panel. - Human and Agent are equal participants. Keep identity, authorization, object revisions and actual execution receipts visible where relevant; never simulate success.
- Agent-first: creation shortcuts must use the shared intent input, not a required form. The Agent persists artifacts through real tools. Keep direct result editing and explicit authorization; never interpret a shortcut click as permission to send or execute.
- All product operations must be Agent-friendly: expose typed domain operations and readable state, shared by Human UI and Agent tools, with the same authorization, revision checks, durable retry identity and verifiable receipts. Do not make an Agent simulate clicks to access an application capability. Keep human-only confirmations and approvals human-only; API access is not additional authority. New features must include this interface, not defer it as an optional integration.
- Task priority is the persisted order, editable by Agent or Human drag/keyboard controls. Do not add priority numbers or high/normal/low selectors. List and board share that order and the same objects. Arranging dates, order, project or assignee does not itself authorize starting execution. Current assignment supports the existing Human and Morphz only; member management and multi-Agent onboarding remain future scope.
- Adding a task view must preserve the accepted existing view: the list retains its date groups and compact rows; the board is a separate four-status-column projection. Shared order is presented within each view's groups. Do not remove grouping, turn every list row into an expanded form, or invent a table redesign in response to unrelated ordering/API work. Feedback about a regression calls for restoring the agreed interaction, not replacing the design.
- Files sent for Agent processing use the existing message attachment flow. Do not add generic Open File/Open Folder browsers or implicitly attach a visible file to every input. The distinct supported capability is explicit Agent read-write directory authorization: show its persistent scope by the composer, bind it to the human, center, workspace and conversation, and snapshot authorized grant IDs into each new input. Native selection must state read/write consequences; selection never sends a message, scans/indexes/copies content or starts work. Agent tools resolve the actual persisted input, check live grants on every call and operate on original files; revocation blocks future calls even for existing work. Old read-only references never gain write authority. Versioned writes preserve conflict and durable retry semantics; no shell/delete permission is implied. Only Agent-created, non-imported Artifacts enter the app's full-text index; manual edits do not change their origin. Asset visibility and legacy objects, annotations, drafts and history remain independent of search eligibility. Keep old source sync disabled without deleting data. Managed-copy/import workflows require an agreed scenario and lifecycle, not available backend primitives.
- Use the shared interaction model, modal focus hook and UI tokens. Keep the four Dashboard accent palettes; use accessible foreground shades rather than inventing new brand colors.

Run geometry regressions for wide/tall/small media, narrow windows, errors, keyboard access and 200% desktop zoom; don't refresh away an unconfirmed screenshot to demonstrate a fix.

This does not authorize unrelated destructive actions, publishing, purchases or changes to other apps' permissions.
- The UI standard includes future targets. Check implementation status before claiming a feature exists. Professional application interfaces and the experimental UI package must not be described as a stable Runtime standard.
- Own professional UI judgment and pre-delivery review; do not wait for the user to supply designer-level pixel instructions. Start from established platform practice and the product's confirmed workflows, state the source and rationale of material decisions, and review complete relevant pages for hierarchy, typography, optical icon weight, spacing, control states, accessibility and motion. Source values, functional tests and rendered demos are not aesthetic validation. Unreviewed or withdrawn visual explorations must not constrain production or become adopted numerical standards merely by appearing in a document. Preserve confirmed interactions; isolate proposed visual changes and record their review status. Keep frontend architecture design, implemented boundaries, automated enforcement and actual-app verification separate when reporting completion; a proposal or diagram does not mean a refactor is done.

User direction takes precedence over these product defaults. Numerical layout baselines are adjustable design decisions, not mandatory Apple dimensions.
