# Desktop 事件驱动读取修复

## 用户要求与边界

健康连接期间不轮询、不全量读取历史；首屏只读选中对话最新页，上滚才补旧页。修复频繁“智能体连接异常”的读取路径，不停止、重发或回答正在执行的业务任务。沿用原 Runtime、Platform 授权和提交账本，不增加另一份消息权威。

## 已确认的原因

- RuntimeBridge.start 保留每 1.2 秒的协调循环，重复读取状态、Session 增量和活动。
- 工作状态 invalidation observer 首次连接沿用旧 Host 游标，可能从 0 回放整个 Session；它只需要当前投影与连接间隙，不需要历史账本。
- Session 最新事件查询按 rowid 排序，但既有 Session 复合索引不能满足追加顺序。真实数据库隔离快照中，最新 1 条查询出现临时排序；单次修复前 8470.659 ms，建立 `(session_id)` 索引后 0.227 ms，返回 1270 bytes、相同摘要。此处是隔离数据库查询，不是原应用首屏或全面性能验收。
- 历史页/head 失败会直接写全局 connected=false，未独立确认健康状态，造成单个慢查询被展示成整个智能体断开。

## 修复

- 一次启动恢复、显式命令唤醒、提交事件唤醒；健康空闲没有协调定时器。事件按 Session 合并，忙碌期间的唤醒排队，不因界面取消订阅而丢失后台协调。
- invalidation 首次抓最新 head；订阅后只补连接间隙。重连沿用此进程已接受的游标；实时通知没有序号时，由同一 Session 已核验的 HTTP 增量推进，空页或旧持久游标不推进。不把 ephemeral invalidation 游标当执行回执。
- SQLite 创建按 Session/隐式 rowid 排序的索引，保持原事件身份和序号，覆盖尾页与前后 keyset。一次性建索引是 schema 升级，不是反复的请求扫描。
- 分页错误记录 `conversation-history` 的具体诊断，仅在失败时独立确认健康；401/403 仍保守处理。失败页不作为新鲜历史发布，不从缓存制造成功。
- 选中消息历史继续使用现有成熟的最新页、重叠合并、显式 loadEarlier 和阅读位置逻辑，不改成全历史预载。
