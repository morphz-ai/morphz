# 技术选型

日期：2026-09-06

| 范围 | 结论 | 状态 |
| --- | --- | --- |
| Desktop | 采用 Electron，内置浏览器是核心工作区之一 | 已确定 |
| 内置浏览器 | 支持用户登录、保留登录态，以及人和 Agent 在同一页面交接操作 | 产品要求已确定，具体实现待验证 |

## 决策依据

### 以内置浏览器的实际需求为依据

Morphz 应用需要允许用户登录自己的网站账号，在保留登录状态的页面中，让 Agent 协助填写内容、读取信息和执行获准的操作。用户能够随时接管，并在完成后把操作交还 Agent。

这使浏览器成为持续工作的执行环境，而不只是链接预览、文档展示或一次性网页截图。需要统一处理页面生命周期、标签页、浏览器配置、权限、下载和人机接管。

Electron 提供可嵌入的网页视图、持久化浏览器会话和网页控制接口，同时随应用交付 Chromium。对于以浏览器协作为核心能力的桌面应用，这套基础具有直接价值。应用团队可以选择和验证引擎版本，并随应用更新交付修复。

这些接口不是完整的成品浏览器。账号兼容性、地址与安全信息展示、导航和弹窗管理、下载、安全隔离等仍需要实现与验收。

### AI 开发改变成本权重，不代替交付验证

主要由 AI 完成开发，会降低多套代码编写和常规适配的成本。因此，不能单凭人类开发繁复、团队熟悉某种语言，或一套代码覆盖更多端就决定选型。

实际体验、系统约束、故障可修复性、权限边界和版本交付仍然需要评估。AI 能编写适配代码，不意味着能够直接更新用户机器上的系统组件；生成代码也不能代替真实平台和真实账号流程的测试。

本次选择不基于“主流应用都使用 Electron”，也不基于未经测试的性能判断。安装体积、运行内存、启动时间和长时间工作的响应性，均需在 Morphz 应用的实际场景中测量。

## 替代方案与取舍

| 方案 | 适用价值 | 本次未选为桌面主方案的原因 |
| --- | --- | --- |
| Tauri 2 | Web 界面与原生能力结合，不必随应用携带完整浏览器引擎 | 依赖各平台 WebView；完整浏览器协作成为核心需求后，统一并可随应用维护的浏览器环境权重更高 |
| 各平台原生界面 | 可围绕平台控件、窗口和操作习惯设计，适合深度原生体验 | 原生同样可以嵌入浏览器，但仍需建设浏览器宿主、控制与更新集成；当前未提出足以优先采用多套原生桌面 UI 的明确体验要求 |
| Flutter／React Native 等 | 可用于跨平台应用界面，尤其值得在移动端评估 | 不会消除本产品对完整浏览器宿主和控制能力的需求，目前不作为桌面主方案 |

Tauri 的 Windows WebView2 与 macOS WKWebView 并非同一种更新机制，不能笼统说所有系统 WebView 都必须随整机系统升级。Electron 也不消除操作系统、驱动、输入法和网站本身的差异。

原生界面没有被能力上否定。若后续出现决定性的原生交互需求，或测量证明当前方案不满足资源与体验要求，应基于具体现象重审。局部调用原生能力与桌面采用 Electron 并不矛盾。

## 浏览器与中心的职责边界

中心 Agent 负责理解任务、规划和协调；页面操作由浏览器所在的 Edge 执行。浏览器断开后，中心不能把其他环境中的同名标签页当作原页面继续执行，也不能把未送达的动作报告为成功。

浏览器控制接口应表达页面读取、定位、输入、点击、导航和结果获取等操作，并携带目标 Edge、浏览器配置、标签页、任务和主体身份。具体接口和幂等、超时、重试规则另行设计。

内置浏览器与扩展共享操作语义和权限要求，不强求实现相同。能力缺失应显式报告。扩展依然是具有当前页面场景的交互入口，可以根据中心的最新进展生成内容，而不仅是接收桌面端提前写好的草稿。

### 浏览器配置、Principal 与登录态

- 浏览器配置应关联所属 Principal 和授权范围，不因团队共享 Agent 而默认共享网站账号。
- 网站 Cookie、令牌等凭据默认保留在对应 Edge，不作为聊天记录或模型上下文上传。页面内容的读取和回传也必须服从授权范围。
- Morphz 对话 Session 与 Electron 的浏览器 Session 是不同概念。前者关联对话，后者管理 Cookie、缓存等网站状态；不能混为一套身份对象。
- 登录网站不等于授权 Agent 执行账号下的全部操作。任务转交、模型切换和会话切换均不能隐式转移账号权限。
- 浏览器存储分区是实现工具，不是完整的 Principal 安全边界。配置访问、浏览器控制和结果交付还需执行身份与授权检查。

### 人机交接

用户与 Agent 操作同一个页面状态。用户接管后，应暂停 Agent 对该标签页的输入；恢复前重新读取页面与任务状态，避免继续执行接管前已失效的动作。

动作应区分计划、已发送、已执行和结果已确认。对无法确认是否已提交的外部操作，不应盲目重试。发布、支付等有实际影响的动作遵守任务授权和相应确认策略，不把逐次确认每次点击作为所有工作的默认方式。

密码、验证码、恢复码等敏感信息不应进入常规页面采集、截图记录和操作日志；验证与授权环节应提供清楚的用户接管路径。

## 隔离与维护要求

- 将 Morphz 应用的可信应用界面与第三方网页分开。第三方页面不获得应用管理、本机命令或任意文件访问接口。
- 对远程内容关闭 Node 集成，启用上下文隔离、进程沙箱和 Web 安全机制，并实现页面权限、导航、弹窗、下载及外部协议的检查。
- 浏览器自动化通道属于特权接口，应由受认证的 Edge 控制，不暴露无认证的远程调试入口。
- 网页内容是任务数据，不是用户或团队的授权指令。浏览器沙箱不能代替 Agent 对网页诱导指令和越权请求的处理。
- Electron／Chromium 更新和依赖安全维护属于持续交付责任，不能把初次配置安全开关视为完成全部安全工作。

这些是设计与验收要求，不是已经达到的安全保证。

## 登录兼容性与扩展路径

内嵌 Chromium 不保证所有网站允许登录。网站可能限制嵌入式浏览器、要求特定认证环境或触发额外验证。例如 Google 的 OAuth 政策禁止将授权请求定向到开发者控制的嵌入式用户代理。

在外部浏览器完成登录，不会自动把该网站的登录态带回内置浏览器。对不能在内置环境完成的流程，应提供受支持的替代路径，例如由用户在外部浏览器完成登录，再通过扩展在该浏览器中继续获准的工作。不通过伪装浏览器或复制凭据规避网站限制。

需要针对目标网站记录验证过的登录与操作路径，区分能力不支持、需要用户验证、授权不足和暂时失败，不能对外承诺通用登录兼容性。

## 与分发方案的关系

Web App 的按需获取和客户端更新分别设计。下载独立 Web 发布包的方案，不意味着可向桌面特权界面或浏览器扩展任意注入远程可执行代码。

Runtime 二进制仍仅内嵌 Dashboard；完整 Web App 独立分发。Desktop 为额外安装的客户端，不应默认创建另一套孤立的 Agent 状态。具体安装、签名、更新、兼容范围及卸载规则见[应用架构与分发](./05-application-architecture-and-distribution.md)。

## 首轮技术验证

在正式功能开发前，用实际工作流程验证以下项目，并记录平台、版本和结果：

1. 用户登录目标网站，正常退出并重启客户端后，网站允许持久化的登录状态仍可使用；注销与过期行为正确。
2. 两个浏览器配置使用不同账号，Principal、操作目标及结果不串线。
3. Agent 填写内容，用户接管修改，Agent 恢复后依据新页面继续；旧动作不会覆盖人的修改。
4. 重定向、新窗口、中文输入、文件选择、下载和网站验证有可理解的处理路径。
5. 未获授权的页面、Principal 或任务不能访问另一浏览器配置，也不能调用应用的特权接口。
6. Edge 离线、页面导航、标签页关闭或外部操作结果不确定时，不误报成功或重复提交。
7. 内置浏览器不兼容的登录流程可以切换到经验证的外部浏览器与扩展路径；不能假设账号状态跨浏览器同步。
8. 多标签页与持续流式对话下测量响应、内存、启动和恢复行为，形成实际的资源目标。

首批桌面操作系统、架构与最低版本，以及移动端框架、前端框架、SDK 和自动化适配层，仍需在实现准备阶段明确。当前没有已通过的原型或测试结果。
