# 认知应用：共享业务能力、聊天与界面

日期：2026-09-22。状态：共享操作接口与剧本聊天准备链已实现；自动化及原 Desktop 真实模型验收通过。完整 Human 决定桥接尚未实现。

本设计回应“认知应用除了按钮，还必须能通过纯聊天完成业务”的要求。
它取代“先由按钮准备执行范围，普通聊天只负责讨论”的产品限制，
不是给剧本工具增加一个例外，也不是宣布新的 Runtime 或 HNS 标准。

## 1. 核心决定

认知应用先提供可读、可调用的业务能力，再提供专业工作方法和可选界面。
聊天与 GUI 是同一业务能力的两个入口，不各自实现一套行为。

| 层             | 负责什么                                               | 不负责什么                               |
| -------------- | ------------------------------------------------------ | ---------------------------------------- |
| 领域对象与操作 | 对象、版本、业务规则、授权、真实写入及回执             | 不依赖当前页签、DOM 或按钮点击           |
| Agent 能力接口 | 发现可用操作、读取状态、校验参数、调用操作、查询结果   | 不能因模型传入身份或权限声明而提权       |
| Harness        | 工作方法、意图判断、多步骤执行、检查、修订、阻塞与恢复 | 不替代真实操作，不用提示词假装保存或批准 |
| GUI            | 浏览、编辑、直接操作和呈现结果                         | 不独占业务能力，不创建另一套数据和执行器 |

“纯聊天完整功能”指能完成同样的业务结果，不要求把拖拽像素、焦点或动画也做成业务工具。
在普通聊天里操作已有内容不应要求先打开对应应用；是否打开编辑器由阅读、编辑需要决定。

## 2. 实施前审计：已有基础与实际缺口

以下是本轮实施前的审计，不是当前完成清单；本轮实现与边界见第 9 节。

| 范围       | 已有基础                                                                         | 缺口                                                                                                     |
| ---------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 应用声明   | `packages/core/src/applications.ts` 声明界面、权限和精确 Harness 版本            | 没有完整的业务能力目录；当前界面包要求 `ui`，不能直接视作完整认知应用定义                                |
| Agent 工具 | `packages/application/src/agent-tools.ts` 已有内容、事项、项目、收藏、剧本等操作 | 操作和用法集中在大工具描述中，与应用声明分离，无法从一个注册源核对 GUI/Agent 覆盖率                      |
| 共享命令   | `packages/core/src/model.ts` / `store.ts` 已有领域校验、版本冲突与持久回执       | 并非所有界面行为都通过完整的 Agent 入口暴露；不能把现有测试数量当作能力对等证明                          |
| 剧本生成   | Yao 已有生成、自审、修订、受控提交                                               | `script/read-workflow` 依赖输入的 `scriptGeneration`；没有它就强制讨论，缺少从真实聊天请求准备执行的路径 |
| 剧本操作   | `script-studio-commands.ts` 有候选、修订、审阅、锁稿、导出命令                   | 多处把“需要人的决定”直接实现为“调用者必须是 Human”，尚未区分通过聊天作出的决定和 Agent 代办              |
| 沙箱应用   | 宿主支持读取对象、执行受限命令、准备输入与保存视图状态                           | 任意 UI 包不自动获得领域能力；业务内容如果只藏在 UI 状态里，就无法脱离界面使用                           |
| Runtime    | `morphz/src/harness_tool.rs` 已有按需列举、精确选择 Harness 的能力               | 应用侧尚未把能力发现、目标准备与这些入口连成完整路径；一个 Evaluation 的 Primary Harness 不可随意重绑    |

因此，不采用以下方案：

- 只改提示词，让模型声称“现在可以了”，却没有可调用操作。
- 给每个按钮添加一个点击工具，继续依赖当前页面。
- 把全部命令、参数和方法常驻每次模型输入，扩大首字延迟与误调用面。
- 为聊天另写一套业务逻辑，或在 TypeScript 中重建 Yao 的编剧流程。
- 把普通输入改写成“人工已批准的生成输入”，或伪造另一条 Human 消息。

## 3. 统一能力契约

以共享应用层的**有类型操作注册**为单一来源。每项操作需要：

- 稳定的操作标识、版本、所属领域及用途；模型可读的简短使用条件和反例。
- 输入与结果 Schema，由实际类型定义生成并由 Host 校验，不另写一套宽松工具参数。
- 查询、变更或工作流程的分类，以及真实副作用，例如只整理、写入候选、替换正文、外部发布。
- 可操作对象与版本前提、所需授权、是否需要业务决定；不把“能力存在”当成“当前可执行”。
- 实现处理器、重试/结果未知时的处理规则、返回的对象/版本/执行引用。

应用引用已注册能力及精确 Harness，而不是再复制能力文档。GUI 和 Agent 适配器调用
同一处理器；领域校验和事务继续留在共享业务层。已有处理器抽取复用，不增加平行实现。

发现接口按需提供三类信息：应用与能力摘要、某项能力的完整参数/结果结构、当前对象的实际
可用操作及阻塞原因。能力索引必须与真实处理器一致；没有实现或当前不可用的能力不能伪装成
可执行工具。分页、过滤和完整性标记是状态查询的一部分，不能靠模型猜测未返回的对象。

本轮已实现的接口为 `host_morphz` 的 `operations/list`、`operations/describe`、`operations/invoke`，具体格式见第 9 节。上文完整契约是目标，不代表全部字段均已实现。

第三方 HTML 不能通过声明一个操作名获得任意宿主代码执行权。第一轮将内置能力及受限共享
对象操作贯通；新领域处理器的安装、隔离和信任仍是单独的宿主边界，不借此引入应用市场、
任意代码加载器或新的远程服务。

## 4. 状态、目标与执行准备

需要分开四件事：

1. **工作上下文**：发送时可附带当前应用、选中对象、版本和选区；这些是理解“这个”的线索，不是授权。
2. **可读业务状态**：应用关闭也能查询对象、结构、候选、检查结果、执行进度和可用操作。
3. **执行准备**：根据请求解析目标，读取依赖，固定对象版本、资料范围、执行目的和预算。
4. **执行授权**：Host 独立验证真实发起人、执行者、对象权限和当前规则；模型不能自己授予权限。

明确名字的请求可在已授权范围内查找对象，不以当前页签作为唯一检索范围。
同名或指代不清时询问一个决定性问题；找不到时说明缺口，不自建同名替代品。
跨项目操作必须检查真实权限并固定目标所属范围；跨私有 Context 的资料不能直接注入原执行。
不得以全局目录可见或模型提供的 projectId 代替执行授权。

准备结果单独持久化，关联原始输入、真实执行和版本读取集，不改写原输入。GUI 已明确选择
目标时可以提交相同的准备请求；聊天时由 Agent 取得这些信息。两条路径进入同一校验。
准备不是授权，不是启动，也不是成功。执行和提交前仍检查撤权、取消、锁稿和版本冲突。

未发送草稿默认仍是用户本地草稿，不因 Agent 可读应用状态而被后台读取或覆盖。用户明确
要求处理当前草稿时，通过宿主提供明确版本的快照或保存操作；不能直接猜 UI 内存或偷读 DOM。
已提交正文、目录和候选等业务状态不得只存于界面实例或 localStorage。

## 5. Harness：从意图到完整工作，不是固定按钮分支

简单查询、改名、排序等直接调用领域工具，不强制套一条长工作流。
复杂工作由 Harness 描述方法，并用现有 Yao 表达可恢复的执行步骤：

- 讨论与探索：直接交流，不因为提及某个应用就创建对象或启动生成。
- 明确操作：解析目标和操作，补充必要状态，调用真实领域能力。
- 专业创作：准备版本与资料，再进入生成、检查、必要修订和持久交付。
- 决定性信息缺失：提出具体问题，保留待续信息；回答后重新校验，不重做已成功的步骤。
- 取消、权限变化或冲突：停止相应写入并给出实际原因，不能退回聊天假装交付。

工具说明回答“如何调用、会改变什么”；Harness 回答“何时用、怎样组合、怎样判断质量”。
创作领域知识可放在 Harness 的 Contract/Mind 中，控制流使用 Yao，不另造一套 Skill 执行引擎。

按需发现与选择复用 Runtime 的 `harness_list` / `harness_select`。不能要求用户打开应用再发
第二条同义消息，不能静默改绑当前 Evaluation。若跨应用任务确需不同专业流程，应使用 Runtime
已有的执行组合能力；具体绑定、上下文隔离及恢复必须专项验证，当前不声称任意 Harness 已可自由切换。

## 6. 人的决定也可以发生在聊天里

执行者、发起人和业务决定者是不同概念。Agent 可以执行用户要求的操作，但不能把自己的
判断记作 Human 的审阅意见。

- 普通已授权操作按实际请求执行，不为每次读写增加确认弹窗。
- 需要明确业务决定时，创建绑定具体对象、候选/版本、操作、影响和权限的待决定记录。
  用户可以在聊天中回应，也可以用 GUI；两者写入同一种决定。
- 聊天回应由宿主的真实 Human 输入及其关联的待决定记录提供来源；Agent 只能提出或解析
  请求，不能提交一个 `approved: true` 就获得批准。回应含糊、同时存在多个待决定事项，或
  对象版本已经变化时，不能自动批准。
- 决定只允许绑定的操作消费，重试不得重复生效；权限撤销、有效期或版本变化必须重查。
- 登录、系统文件授权、付款或外部发布等仍遵守相应权限规则。聊天可以发起和继续流程，
  但工具存在不代表可以绕过 OS 或外部服务要求的本人授权。

这使“采用第二版”“批准这一版并锁稿”有可实现的聊天路径，也保留真实决策责任。
不能把所有 Human-only 检查简单删除，更不能让 Agent 冒用 Human 身份调用。

## 7. 一个实际验收场景

用户没有打开工作室，在普通聊天输入：“把《废火》第一集写成候选稿。”

1. 发现已安装且可执行的编剧能力，需要时选择专业 Harness。
2. 在授权范围内找到这部剧与第一集，读取结构、要求、依赖和当前版本。
3. 准备并持久化本次目标、资料和版本，不让用户去寻找“生成候选”按钮。
4. 同一 Yao 流程生成、自审、修订，通过真实领域操作保存候选；不覆盖正式稿。
5. 聊天返回保存回执与直接打开此候选的入口，内容目录和工作室显示同一个结果。
6. 用户说“采用这版”，通过明确决定与同一领域操作采用；有新修改时报告冲突。

“我们聊聊第一集”只讨论；“把刚才说的设定保存”保存指定业务对象；“再改一下”根据
已交付对象或本次明确上下文解析，不沿用另一条并发执行的目标。
这些区别应由意图和业务状态决定，不由输入是否附带按钮专用字段决定。

## 8. 实施与验收门槛

实施顺序：

1. 从全部现有用户业务操作建立覆盖清单，标出共享处理器、Agent 入口、所需决定和状态查询。
2. 抽出能力注册/发现/调用的共享约定，连通原有权限、版本与持久回执；删除错误的按钮前提。
3. 剧本作为首个完整参考：创建、导入已授权原文、结构编辑、生成、修订、检查、候选决定、
   审阅、锁稿、导出、整理项目，逐项验证聊天与 GUI 路径。未支持的文件格式明确列出。
4. 用相同契约覆盖内容、事项、项目与浏览器，不能将剧本跑通等同于所有应用完成。
5. 固化能力对等测试及应用作者说明，避免新增按钮再次产生聊天缺口。

验收按业务场景执行，而不是只检查工具注册或按钮存在：

- 不先打开应用的完整纯聊天流程；多轮指代、同名目标、新建后继续操作、跨已授权项目定位。
- GUI 和聊天得到相同对象、版本、权限及副作用；交付链接可直接打开准确结果。
- 候选采用/批准的真实 Human 决定，拒绝 Agent 伪造批准及过期决定。
- 并发编辑、撤权、取消、超时、未知结果、相同调用重试及中断恢复；不重复创建或覆盖。
- 闲聊不误执行，查看不修改，安排不自动启动，收藏不自动访问网页。
- 剧本 Yao 的讨论、目标准备、生成、检查、修订、阻塞、恢复均经实际 Runtime 执行。
- 最后在用户原 Morphz Desktop 验证真实模型、可见进度、操作记录、结果入口和原内容保留。

本设计文档完成不等于上述实现完成。剧本执行准备已补齐，但候选采用／批准等 Human
决定的聊天桥接仍未完成，不能据此宣称所有认知应用的全部功能已经支持纯聊天。

## 9. 本轮实现：共享操作发现与剧本准备

操作注册位于 `packages/application/src/application-operations.ts`，参数引用实际领域
Zod Schema，调用转换回原有请求并经过原 Host 权限及版本检查，不建立第二套执行器。

```json
{"action":"operations","operations":{"action":"list","domain":"script","limit":20}}
{"action":"operations","operations":{"action":"describe","operationId":"script.prepare-workflow"}}
{"action":"operations","operations":{"action":"invoke","operationId":"script.list","parameters":{"query":"剧本名称"}}}
```

目录覆盖已有内容、表格、事项、项目、会话、应用、文件、浏览器、收藏与剧本能力；
可按领域／文字过滤并分页，返回总数及完整性标记。`describe` 返回真实参数结构、副作用
类别、权限说明，剧本还返回精确 Harness 引用。`invoke` 解析严格参数，再走原领域处理器。
不接收调用身份、任意 inputId 或“人工已批准”声明。仅支持当前真实可用的 Host 能力；
目录项存在不等于任何对象都可以操作，对象权限仍在执行时检查。

剧本 `prepare-workflow` 使用与 GUI 同一个 `prepareScriptGeneration`：校验目标、
创作要求版本与文稿版本，收集递归依赖，排除重复／冲突引用，检查资料上限及原文授权。
准备结果单独保存在 `scriptPreparations`，关联不可变的真实 Human 输入；不改写输入文本、
Session IO、原应用绑定，不发送第二条伪造请求。工具重试返回同一回执，不重复准备／提交。
版本、取消、撤权和锁稿在后续读取与写入仍会复核；准备不代表创作已完成。

1.4.0 Harness 的 Yao 先区分讨论与执行。普通执行请求经有工具的准备 infer 查找和绑定，
再进入既有无工具的创作、自审、有限修订和受控提交。只是讨论不会保存；目标含糊才追问，
不能让用户去点击生成按钮来完成系统本可自行完成的绑定。已有按钮请求仍进入同一生成链。

Yao infer 子执行工具的原始输入归属由 Runtime 的 `plan_infer` Thread 和 Runtime-Yao
`infer_request` 持久事件逐级验证；核对 Plan、Session、Context、Agent 和 principal，
限制深度并拒绝循环。不能使用模型 captures 中的 inputId 代替授权证据。个人单 Agent
可在发起人已有的相同成员边界内定位目标；团队／私有 Context 不借全局目录提权。

自动验证：365/365 单元集成、17/17 剧本与交付界面回归、真实 Runtime＋固定测试模型
13 条 Yao 场景（68 次模型请求）及原 16/16 中断恢复点通过。新增普通聊天场景确实执行
能力发现、精确 Harness 选择、目录查找、准备、生成、自审和保存；没有 `scriptGeneration`
或应用实例输入，候选和消息交付关联同一原输入。准备重试、撤权、取消、跨范围冲突有
专项测试；16 个恢复点是既有生成链，不冒充新增准备阶段的强制中断专项。

原 Desktop 使用实际 `gpt-6-astra` 从普通对话完成两次查找、准备、创作、自审、保存，
均未附应用实例或按钮生成字段。消息卡片分别打开准确候选。首次暴露回执缺少 UI 交付
信息，造成模型误称“没有链接”；补齐真实 `deliveries` 和卡片说明后复验，最终回复与
可点击卡片一致。原文稿与输入保留，两次只新增 TEST 候选。详见实施记录，不扩大为
全部领域的真实模型验收。

仍未完成：通过聊天记录并消费 Human 候选决定／批准／权利确认；所有能力的统一结果
Schema、对象级可执行性描述及版本化注册；第三方领域处理器安装；各领域逐项真实模型
能力对等验收。现有大工具参数尚未全部收缩为按需描述，不能声称已优化全部模型输入长度。
