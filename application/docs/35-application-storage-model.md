**Morphz 是产品整体，不把 Morphz Platform 当作整个系统的别称。** Runtime 负责 Agent 的认知与执行；Platform 负责项目、事项、内容目录、授权和应用接入；Cognitive Apps（认知应用）各自决定专业对象的保存方与存储实现。Desktop／Web／Mobile 是 Clients（客户端），不是 Cognitive Apps。这是逻辑职责划分，不规定必须分成不同进程或数据库实例。**本阶段不制定 Apps 通用数据库／对象存储规范，也不为第三方托管私库；未来是否提供内置存储，根据具体应用需求再决策。**

## 0. 先给结论

1. **云端服务的 Platform 权威在云端。** 它保存项目、事项、授权和应用内容目录；Runtime 保存 Agent、Session、Target 身份与在线状态及执行 Job。Platform 不保存节点普通文件目录或字节位置索引。
2. **认知应用自己负责专业数据。** 剧本正文、版本、候选等由剧本工作室决定保存方和领域接口；Platform 只持有目录引用与授权。内置应用也遵守这条边界；本阶段不托管第三方应用私库。
3. **节点文件通过 Execution Target 按需访问。** Agent 的文件操作已走执行节点；未来 Human 文件浏览也沿同一身份、授权与节点路由设计。Client 不自动扫描、上报、复制节点文件；应用如需访问节点文件，不必先将它变成 Morphz 受管对象。
4. **只有明确接收的字节才进入中心受管存储。** Morphz 自己接收并承诺保管的消息附件、导入书籍原件、应用包等，物理上保存在中心部署域（本机中心目录或中心对象服务，可与 Platform 共置），不在执行节点之间建立 Store 通道。Runtime 消息链、Reader 等所属领域仍分别决定这些字节的授权、版本和删除；共置不等于把它们写进 Platform 业务表。认知应用的其他专业文件继续由应用自行选择文件系统、对象存储或 SaaS；普通节点文件不自动进入中心。
5. **逻辑隔离，物理可共置。** Runtime、Platform、内置应用域和各自受管字节元数据守自己的权威；可信组件可同机、同安装包或共用 PostgreSQL 实例，但不共写对方的业务表。Morphz 自有关系存储支持 SQLite／PostgreSQL；不强制第三方采用任何数据库。
6. **先建立权威边界，再谈性能。** 以增量事务、稳定对象身份、版本前提、按授权范围分页索引和明确的失败恢复为基础；性能目标通过真实负载基准确定，不做未经测量的承诺。

[具体存储模型与事务、字段](./36-storage-implementation-model.md)

```text
Desktop / Web / Mobile ──► 云端 Platform ──► 项目／事项／授权／应用内容目录
                                  ├──► Cognitive App ──► 应用自行选择的专业数据与字节保存方
                                  └──► Runtime ──Job──► Execution Target ──► 节点普通文件

普通文件由执行节点按授权请求实时访问；Morphz 明确接收的受管字节保存在中心部署域，并由所属 Runtime／应用域管理其语义。
第三方应用自管专业数据，Platform 只保留获授权的应用对象引用。
```

图中的连线表示接口或引用，不表示跨库原子事务，也不表示 Cognitive App 必须使用 Morphz Store。Runtime、Platform、内置应用域与节点能力可以物理共置，数据权威、身份、授权和迁移边界仍独立。“应用域存储”是应用自己的数据层，不是应用商店。

### 本文术语

| 术语                                | 准确定义                                                                                                                                                                                                                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Morphz Runtime**                  | Agent 的认知、Session 和执行引擎；Agent Cell 是 Runtime 的一种云端部署形态，不是应用数据库。                                                                                                                                                                                                       |
| **Morphz Platform**                 | 项目、事项、授权、应用接入及已登记内容的全局目录业务层。云端服务中由云端承载；独立本机／自托管部署可以另行嵌入 Desktop。不是必须独立的进程，不拥有 Cognitive Apps 的专业正文。现有 `application/` 及 `morphz-application` 是工程目录／包名，不能据此把 Desktop 客户端或某个认知应用叫作 Platform。 |
| **Cognitive Apps（认知应用）**      | 剧本工作室、阅读器等提供专业对象和领域操作的应用。内置应用由 Morphz 开发和运营；第三方应用由提供者负责其私有服务与数据。两者以相同的接入边界与 Platform 协作，不因内置身份就把专业表并入 Platform。                                                                                                |
| **Clients（客户端）**               | Desktop、Web 和未来 Mobile，负责界面及有限的本地草稿／缓存；不是 Cognitive Apps，也不因呈现某个应用就拥有其原件。                                                                                                                                                                                  |
| **界面宿主**                        | Client 中加载、隔离和呈现 Cognitive Apps UI 的容器；它不是 Platform，也不因显示某个应用就取得该应用私有数据的所有权。                                                                                                                                                                              |
| **Platform 存储（共享工作空间库）** | Platform 负责的项目、事项、授权、操作回执和已登记对象的全局元数据目录；不保存 Cognitive App 正文或自动收录设备文件。                                                                                                                                                                               |
| **Execution Node／Target**          | Node 是设备上的提供者；Target 是稳定的逻辑执行目的地，一个 Node 可提供多个 Target。Target 的在线状态与 Job 由 Runtime 管理，不是文件持久化身份。                                                                                                                                                   |
| **受管 Artifact Store**             | 为明确接收的附件、导入原件或应用包等具体用途保存字节和校验元数据的实现，可使用中心节点目录或云对象存储；不等于 Target、普通节点文件目录或应用专业数据库。本轮不要求建立通用远端 Node Store。                                                                                                       |
| **应用内容目录**                    | Platform 保存经所属应用确认的对象引用、标题、项目归属和已观察版本；它只定位应用原件，不收录节点上的普通文件，也不是 Store 的文件位置索引。                                                                                                                                                         |
| **应用域存储**                      | 某个 Cognitive App 自己负责的专业对象、版本、索引与持久化策略。内置应用由 Morphz 作为该应用的开发者负责；第三方自管。应用可选择使用 Artifact Store 保存字节，但 Store 不接管应用语义。                                                                                                             |

部署方式与上述逻辑角色分开：云端服务由云端 Platform 和 Runtime 承载，Desktop／Web／未来 Mobile 作为 Clients 接入；Desktop 上的 Edge Node 可以另外提供 Target。独立本机或自托管部署是另一种部署，不是云端账号中的“本机空间”。Client 名称不决定数据库后端或应用数据位置。Cognitive Apps 经领域接口接入 Platform，但不是它的子类型或私有数据库表。

**现有本机入口的范围：**Desktop 显式文件引用／目录授权仍是该 Host 的 `LocalFiles` 能力，经真实持久输入、当前 Human 授权、路径和版本核验访问本机原文件；不是远端 Target 路由。上文执行节点指远端 Node 的通用文件操作与显式 Transfer，不以本机入口测试冒充远端证据，也不在本次存储切换中另建跨节点文件系统。未来 Human 节点浏览与 Mobile GUI 尚未交付。

## 1. 设计依据与现状边界

Morphz 的产品关系是：对话用于沟通；「内容」页面统一展示已授权登记的内容对象，供用户查找和打开；项目组织和筛选这些原件，不创建副本；工作台负责启动认知应用。**统一入口不等于统一保存正文。** 内容目录只保存对象的定位引用和必要的展示信息；打开、修订与读取精确版本时，由拥有原件的应用处理。不应因存储重构退回到“对话里一份、剧本应用里又一份、项目里再复制一份”。参见[认知应用与工作空间](./15-cognitive-application-host.md)、[共享应用层](./24-shared-application-host.md)和[Agent 可操作认知应用](./29-agent-operable-cognitive-applications.md)。

设计时的旧实现与目标必须分开看。下表是 2026-09-25 的基线问题，不代表当前正式入口；迁移后的实际状态以[实施记录](./13-implementation-status.md)首节为准。

| 已有实现（2026-09-25 代码核对）                                                                                                                                   | 为什么不足以作为长期模型                                                                                                                   |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 当前 Platform 实现的 SQLite `workspace(id=1, body TEXT)` 保存整个工作空间 JSON；写入时会更新整行，见 `application/packages/application/src/store.ts`。            | 项目、内容、版本和权限混成一个写热点；局部修改重写全体，无法可靠按实体建约束、索引和迁移。这里是结构判断，不是未经测量的性能结论。         |
| `assets.bytes` 为数据库 BLOB；PDF、出版物、OCR 另有专用表。                                                                                                       | 大字节与频繁变更的业务行混在一起；媒体、阅读解析与生命周期不统一。并非说数据库 BLOB 一律错误，而是当前规模和隔离目标下不宜继续作为主存储。 |
| `contentSchema` 是固定的内容种类联合，`artifactSchema` 把内容、版本信息放在应用模型中，见 `application/packages/core/src/model.ts`。                              | 每增加一种专业内容都要改中央类型；目录引用与应用拥有的专业 payload、版本需要拆分。                                                         |
| Runtime 已有自身的 SQLite／PostgreSQL 存储实现；Artifact Transfer v1 可用 `target_id + path` 定位、校验和传输用户文件或 Agent 产物，见 `morphz/src/artifact.rs`。 | 这是一次受权物理操作的位置与回执，不是应用原件的版本或备份契约；不能把 Transfer 成功冒充应用已保存。                                       |

当前 Desktop 内嵌 Platform 业务模块且本地使用 SQLite；Web 通过 HTTP 调用同一模块。Cloud Agent Cell 属于 Runtime 部署形态。现有 `morphz-app/v1` 是无任意网络权限的受限 UI 包，`saveState` 只允许保存窗口导航位置，不接受第三方正文、便笺或草稿；它既不提供第三方私有数据库，也不能直接连第三方自管服务。自管服务接入需要受权的领域 API；**共享目录只存应用对象引用、正文归应用**。远端 Node Store 不是当前接线门槛。

## 2. 数据权威：哪些数据由 Morphz 保管

| 权威域                                          | 关系数据归它所有                                                                                                                                                                                                | 对象数据归它所有／引用                                                                            | 不归它所有                                                                 |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Runtime 存储**（云端可由 Agent Cell 使用）    | Agent 身份与授权上下文、Session／Thread／Event、Context／Mind、Target 身份及在线状态、执行 Job、调度及其回执。                                                                                                  | Event 附件或执行产物可引用 Artifact；Runtime 调度受权 Target 操作和显式跨 Target Transfer。       | 项目目录、剧本正文和候选、书库、应用私有工作流。                           |
| **Platform 存储**（云端服务中的共享工作空间库） | 项目、事项、对话的项目归属／标题／归档状态、应用内容目录、应用对象引用、项目关联、Morphz 授权和平台命令回执。                                                                                                   | 不拥有节点原字节或应用私有文件；记录 `instance_id + app_object_id` 与应用确认的版本、可用状态。   | Session／消息历史、设备文件目录、应用正文和版本、Target 在线状态的权威。   |
| **内置应用域存储**                              | 剧本、阅读等各自的专业对象、正文、不可变版本、候选、草稿、批注／阅读位置、流程及专业索引；每个应用拥有自己的 schema、迁移及存储位置决策。阅读器也可在另一应用拥有的原件上保存阅读位置与标注，但不因此接管原件。 | 应用可以自管 SaaS 字节，也可按合同使用节点／云 Artifact Store；应用对象是目录条目指向的**原件**。 | 全局项目、其他应用私有状态、Runtime 认知状态；Store 不替应用决定正文位置。 |
| **第三方应用自管存储**（Morphz 域外）           | 第三方应用自己的专业数据及版本；数据库选型、备份、恢复和迁移由其负责。                                                                                                                                          | 私有文件留在其存储；目录登记只保存引用，只有明确导入的新副本才由 Morphz 保存。                    | Morphz 不托管其私库，不承诺私库离线可用、备份或卸载后保留。                |
| **受管字节保存方**                              | Runtime 消息链或具体应用域决定哪些字节被明确接收及其授权、版本、删除和恢复规则；所用 Store 的 manifest 保存摘要与字节状态。普通节点原文件不自动进入受管存储或 Platform 文件索引。                               | 字节由所属 Runtime／应用域选择的本机或云对象后端负责；应用按自身契约保存精确引用。                | Platform 项目权限、其他应用专业版本、第三方私库。                          |

**为何这样分：**共享工作空间需要统一的项目、事项和内容入口，却不需要拥有每种应用的正文和专业版本。内置应用与第三方应用都通过稳定的应用 ID、对象 ID、版本引用和领域操作接入目录；目录投影若落后，以应用对象为准并可重建。内置应用的专业状态不塞进共享 schema；第三方数据无需迁入 Morphz，避免为尚未验证的托管业务建设数据库服务。Runtime 仍专注认知与执行，并可提供 Artifact 等通用机制。

Artifact 是通用数据对象，不是把所有字节写进 Agent Cell 的同一物理库。Runtime 管 Execution Target 身份与受权路由；实际接收字节的 Runtime 消息链或应用域负责版本、摘要和恢复契约，所选 Store 的 manifest 负责其物理字节。`target_id` 是执行目的地，不是应用版本 ID、文件目录或通用持久字节保存方。普通节点文件的实时访问仍须 Runtime 与节点本地授权；不建立第二份云端文件目录。

## 3. 关系模型：共享目录与应用原件分开

以下是**逻辑模型**，不是把一份工作空间 JSON 换成另一份大 JSON。Morphz 自己维护的表有明确租户范围、稳定 ID、唯一约束和可审计的变更；具体 SQL 类型由 SQLite／PostgreSQL 适配。

| 归属           | 表／聚合                                                                                                       | 关键约束与用途                                                                                                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 共享工作空间库 | `projects`、`project_members`                                                                                  | 项目 ID、所属范围、成员与修订；项目是归属／授权范围，不是内容副本。                                                                                                                                                                                      |
| 共享工作空间库 | `conversations`                                                                                                | 只保存对话的项目归属、标题、修订与归档状态，用于跨端导航；默认对话沿用项目 ID。Runtime 保存 Session／Event／消息，Platform 不复制聊天正文，也不以导航记录代替 Session 身份。                                                                             |
| 共享工作空间库 | `tasks`、`task_order`                                                                                          | 事项 ID、项目或个人范围、状态、负责人、跨项目共享的语义优先顺序与顺序修订；项目列表过滤同一顺序。事项不因排除在「内容」目录之外就丢进 JSON。                                                                                                             |
| 共享工作空间库 | `app_installations`、`app_instances`                                                                           | `app_id` 标识应用类型；稳定 `instance_id` 标识实际拥有对象的应用数据域及其可变化的路由。同一种应用可有云端和节点实例，不能仅凭 `app_id` 寻找原件。                                                                                                       |
| 共享工作空间库 | `content_entries`                                                                                              | `content_id`、`app_id`、`instance_id`、`app_object_id`、类型、标题、project、已观察到的版本标识、可用状态和元数据修订；唯一 `(tenant_id, instance_id, app_object_id)`。**不含正文和专业版本历史。**                                                      |
| 共享工作空间库 | `work_relations`                                                                                               | 事项与内容目录间、或同类对象间的类型化关系；端点明确区分事项 ID 与内容 ID，可记录精确版本，不复制原件。                                                                                                                                                  |
| 共享工作空间库 | `command_receipts`、`outbox`                                                                                   | 平台命令记录真实 Human、执行 Actant 与 Runtime 输入 ID，并保留幂等回执及待投递事件。输入及其发起者的权威仍在 Runtime；Platform 每次通过受信入口核验，不复制一张会过期的输入绑定表，也不复制聊天文本。                                                    |
| 内置应用域     | 剧本工作室自己的 `scripts`、`script_revisions`、`script_heads`、`scenes`、`workflow_runs` 等                   | 剧本、候选、采纳、分场和流程在剧本域提交、授权并迁移；其他应用不能凭目录引用直接改表。                                                                                                                                                                   |
| 内置应用域     | Objects 应用自己的 `objects`、`object_versions`、`object_annotations` 等                                       | Markdown、PDF、图片、交互对象等普通内容的原件和不可变版本属于 Objects；Platform 只保存入口和项目归属。原文件字节由该应用声明的字节提供方保存，不因目录登记进入 Platform 数据库。                                                                         |
| 内置应用域     | 阅读器自己的 `books`、`book_revisions`、`reading_sources`、`reading_positions`、`reading_marks`、`ocr_jobs` 等 | 阅读器导入书籍的原件版本归阅读域；在其他应用原件（如 Objects 的 Markdown 文档）上的阅读位置、高亮、OCR 派生结果也归阅读域，但 `reading_sources` 仅绑定拥有原件的应用实例、对象和精确版本，不复制或改写原件。高亮创建、取消和恢复必须是阅读域的真实操作。 |
| 第三方域       | 第三方自行定义的表、文件和版本                                                                                 | Morphz 不规定其表结构或后端；只能通过受权领域 API 读取与操作，不能假设它支持我们的事务或备份。                                                                                                                                                           |

可执行 UI 包与认知应用的**专业数据**不是一回事。安装 UI 包是 Platform 的安装／授权行为：`(tenant_id, app_id, package_version)` 唯一标识不可覆盖的包版本，安装记录保存签发者、权限快照、状态、安装时间、字节摘要及精确 Store 版本引用；`app_instances` 仍只标识实际提供专业对象的服务实例，不能拿界面窗口充当数据实例。包的 HTML／脚本字节不放进 Platform 关系表，而由明确配置的受管对象 Store 保存。Host 在 Human 确认后校验包格式与大小、暂存并校验摘要，再以同一命令 ID 提交安装记录和回执；丢失回执时先查询同一安装和 Store 版本，不能重装覆盖。读取、启动和沙箱桥调用都重查当前安装状态与版本；Agent 不能安装可执行包。卸载或升级只改变安装指针／状态，旧版若仍被已打开窗口引用则按保留规则读取，回收须检查引用，不能为了测试数据增加旁路。SQLite／PostgreSQL 的安装关系语义相同；多 Host 部署必须配置所有 Host 可验证、可读取的同一对象 Store，不能依赖某台 Host 的私有目录。尚未提供这种字节存储和安装读取链路的部署应明确拒绝安装，不得写入旧 `workspace` 快照或假装已安装。

事项执行关系由 Platform 的 `task_run_links` 按事项版本和执行序号保存：原始调度请求、Runtime Session／Schedule／Thread 的稳定 ID，以及上次观察到的状态；依赖 Thread、关注来源和来源事件分别保留有序引用。它不是第二个调度器：Schedule／Thread 的当前生命周期和实际执行回执只由 Runtime 判定，Platform 的观察值不能批准再次执行。丢失跨库回执时，先用原请求 ID 核对 Runtime，再决定是否重试；不可根据当前事项重新拼一份意图。正式旧执行桥已删除，不为开发样本保留在线迁入路径；两个权威范围分别备份也不构成跨库原子事务。

`target_id` 的执行能力身份由 Runtime 注册并核验；具体保存方维护受管字节的 manifest。Platform 的 `app_instances` 只保存应用实例路由，`content_entries` 只保存应用对象引用；不登记普通节点文件，也不替应用选择字节后端。未被正式消费的 Runtime Store 登记试验接口已撤回；本阶段不交付通用跨节点 Store。

一个内容目录条目是指向**应用原对象**的稳定定位：`(instance_id, app_object_id, version_ref)`；目录中的“当前版本”只是上次经应用确认的投影，不是版本权威。`app_id` 仅标识应用类型，同类型不同服务实例可以有独立私库。正文、候选和完整版本历史留在所属应用。剧本加入项目只更新目录中的归属和授权，不创建第二部剧本。一个项目可以指向多部剧本；应用读取时必须重新核对该主体对目录条目及原对象的实际权限。

「内容」目录只回答**哪个应用对象属于哪个项目、用户可以打开什么**。受权 Target 上的普通文件由 Runtime 路由到节点实时访问，不因读取、写入或传输自动变成应用内容或受管 Artifact。若应用将其作为专业对象管理，由应用创建对象并向 Platform 提交目录回执；Platform 不扫描应用私库或节点文件。

节点原文件可能被外部程序修改、移动或删除。读取目录或文件时由 Runtime 根据当前身份、授权和 Node 在线状态发起实时请求，Node 本地重新核对范围、路径和版本；离线则明确返回不可用。Platform 不保存一份可能过期的普通文件清单，也无需文件变化上报、同步游标或重扫对账。

应用应提供可验证的对象定位、版本读取、类型化操作、幂等结果查询和变更通知／补偿查询。GUI 与 Agent 使用同一操作；当前打开的页面不是授权依据。应用不可用时目录显示“来源不可用”及最后确认的元数据，不能假装仍能读取正文。用户若**明确导入为 Morphz 自有文档**，那是有来源关系的新原件和一次可见的复制，不是暗中替换原应用对象。

## 4. 内置应用与第三方应用如何落位

| 内置场景   | 共享目录只保存                                         | 所属应用域保存                                                                       | 应用选择使用 Artifact Store 时的字节                 |
| ---------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 剧本工作室 | 剧本对象引用、标题、类型、项目归属与已观察版本。       | 剧本正文、分集／分场、候选与采纳版本、批注、连续性检查、创作流程和草稿。             | 正文分块、导入原作和较大检查报告；由剧本域持有引用。 |
| 阅读器     | 书籍对象引用、标题、类型、项目归属与已观察版本。       | 导入版本、阅读位置、高亮／批注、目录解析、OCR 作业与索引。跨设备进度写入权威阅读域。 | EPUB／PDF／Word 原件、按需生成的页图和 OCR 中间件。  |
| 文档／表格 | 文档对象引用及项目归属；不复制正文或表格记录。         | 正文版本；表格的可查询记录及编辑状态，不能整份塞入不透明 BLOB。                      | Markdown／Office 原件、预览、附件。                  |
| 浏览器     | 仅显式保存的页面快照形成目录条目；书签不因此成为内容。 | 个人书签、浏览状态、抓取作业及页面快照版本。                                         | 显式保存的网页快照与附件。                           |

Desktop 中正在打开的网页及临时控制授权不是已保存的浏览器应用对象。控制请求和结果按操作 ID 保存在执行该页面的 Host 本机关系日志；该 Host 只处理自己的页面，不向 Platform 上报页面目录，也不让另一 Host 接管投递。Runtime 输入证明发起 Human 与 Session，Platform 每次核验项目权限，Host 再核验页面所有者、epoch 和逐次确认。一次工具调用可有限等待结果；超时只返回待处理回执，不伪造 Human 消息来唤醒 Agent。旧版无所有者的回执保留在日志供审计，但不能凭项目成员身份冒领为新的 Agent 控制结果。

这张表描述 **Morphz 自己运营的内置应用**，最后一列是已有原件可能使用的字节保存方式，**不规定其数据必须进 Morphz 云端或节点 Store**。应用域里的已保存草稿也属于应用应备份、恢复的数据，不能称作“缓存”后删除。每个内置应用拥有专业 schema 和迁移，使用同一受限领域操作同时服务 UI 与 Agent。应用版本留在应用域，目录仅显示最近核对的版本状态。对于部署在第三方 SaaS 的应用，Morphz 不接管其专业字节和备份承诺。

第三方认知应用的私有剧本、资料、草稿或其他专业数据由第三方自行保存；Morphz 不替它建库、备份、迁移或清理。经用户授权，第三方对象可以登记为「内容」目录条目，但**登记只存引用，不转移正文所有权**。用户若另行选择“导入为 Morphz 文档”，才产生一份明确可见、可追溯来源的新原件。第三方服务失联时不能假装仍可打开或读到正文；权限撤销后也不能凭旧引用继续读取。

第三方必须提供可由 Platform 验证与调用的领域能力（对象定位、读取、操作、结果回执）；界面和 Agent 经同一受权接口访问，不能让沙箱 iframe 直连私库或把数据库凭据交给模型。现有 `morphz-app/v1` 尚无这种服务接入能力，因此本阶段的决定是**不建第三方托管库**，不是声称任意第三方自管应用今天就能完整安装运行。

这里的“不管理第三方私有数据”**不是**“不关心用户数据”：Morphz 仍须准确告知数据由谁保存，保护自己持有的安装授权、对象引用、消息、明确导入的副本和操作回执，并在调用第三方 API 时执行用户授权。不能把一个外部数据源的故障或删除伪装成 Morphz 已备份、可恢复的内容。

## 5. 物理部署、数据库隔离与 Cloud

**后端选择与组件部署是两件事：**Morphz Runtime 与 Platform 的自有关系存储支持 SQLite／PostgreSQL，并验证相同业务语义。认知应用无统一后端要求；内置或第三方应用分别决定专业数据保存于自己的服务、用户节点或未来可用的受管 Artifact Store，不能由 Platform 的数据库选型推断其落点。生产选型根据并发、HA、备份恢复和租户规模实测；不做运行中无边界的自动 fallback。

| 部署                     | Runtime 与 Platform 权威                                                                                                                                                                                                     | Cognitive App 专业数据                                                                                                     | 节点文件与 Artifact                                                                                                                                       | Client                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Morphz 云端服务**      | Runtime 的 Agent／Session／Target／Job 与 Platform 的项目／事项／授权／已登记目录分别在云端持久化，可共用 PostgreSQL 实例但隔离 schema、角色、迁移；远端 SQLite 需按租户／分片和单写者划分，**不是一份 D1 装全部租户内容**。 | 应用自己声明保存方、域接口、可用性和备份责任。内置应用若选择云端存储，仍由该应用域拥有正文与版本；第三方 SaaS 留在第三方。 | 用户电脑可运行 Edge Node 提供 Target；原有文件留在节点。明确接收的附件、书籍等由各自所属服务或应用选择的中心字节后端保存，不要求节点之间建立 Store 通道。 | Desktop／Web／Mobile 接入同一云端 Platform；只持有界面缓存、偏好、未提交输入和明确标记的离线暂存，不拥有云端项目或应用对象的第二份可写正本。 |
| **独立本机／自托管部署** | 可在用户选定的主机部署 Runtime 与 Platform，逻辑职责不变；SQLite 可用独立文件保持 Runtime 边界，PostgreSQL 可共用实例但隔离数据库／schema。它不是云端账号附送的“本机空间”。                                                  | 内置应用在自己的域维护数据；第三方仍自行负责。是否与 Platform 共用受信数据库实例是该部署的物理安排，不改变所有权。         | 本机或其他节点可提供 Target；原文件与受管原件按各保存方声明的授权、备份责任处理，不因同机就自动进入 Platform。                                            | Client 连接这个被选定的部署；不因此与另一套云端 Platform 自动双写或合并。                                                                    |

“同一数据库实例”在 PostgreSQL 指共用服务器／集群，不指共用业务表或权限角色；在 SQLite 没有常驻服务器实例，物理共置须具体说明是同目录不同文件，还是同文件不同表。受信内置应用若共用 SQLite 文件，只能靠模块访问层、迁移边界和测试隔离，不能假称拥有 PostgreSQL 式表级角色权限；第三方代码绝不能取得该文件的 SQL 句柄。`tenant_id`＋强制授权或 RLS 隔离租户，应用 schema／访问层隔离专业数据。只按对象 key prefix 不构成权限隔离。

Cloud Agent Cell 承载 Runtime 的认知与执行状态；它通过带身份的领域工具访问 Platform、Cognitive App 或获授权的 Target，不保存应用正文。云端服务中 Desktop 是 Client；同一台电脑运行的 Edge Node 是可另行登记的执行节点，不使 Desktop 自动变为本地 Platform。一个应用对象只有一个应用域负责；切换专业数据权威是应用明确执行的迁移，不是云端与本机无声双写。

### 5.1 执行节点与跨端可用性

Node 是执行提供者，`target_id` 标识逻辑执行目的地；一个 Node 可以提供多个 Target。Target 在线状态由 Runtime 的心跳、Route 与租约决定。**Target 在线不证明某个应用对象或受管字节仍存在**；应用对象的版本与可用性仍须所属应用核验。Node 更换连接或 Route 时，不改变 Target 身份。

Platform 的云端目录只保存 Cognitive App 已确认的对象引用，不承担普通节点文件目录。Client 若要浏览某个节点的受权目录，通过 Runtime 将请求路由到在线 Node，由 Node 即时列出并校验本地授权；节点离线则无法列出。这个按需请求不建立持续扫描、增量上报或云端文件名副本。

| 手机端要继续的对象             | 取决于谁保存原件                                                    | 节点离线时                                                                                     |
| ------------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Cognitive App 的剧本／书籍对象 | 应用自己的领域 API 和存储策略；它选择在中心、节点或第三方保存原件。 | 中心或 SaaS 原件可继续；若应用只在离线节点保存原件，则由应用报告不可用，不能由 Platform 猜测。 |
| 节点上的普通文件               | 文件由所在 Node 按授权实时提供；不预先变成 Morphz 对象。            | 目录与文件无法实时读取；Platform 不显示一份伪装实时的文件副本。                                |
| 项目、事项、授权与 Session     | Platform／Runtime 各自云端权威。                                    | 可以继续访问云端状态；依赖离线 Target 的物理任务等待或按实际 Job 状态处理。                    |

项目可关联不同节点及不同应用的对象，不绑定唯一 Target。Agent 要同时在多台机器工作，由 Runtime 为各 Target 建立独立绑定的执行 Thread／Job；跨节点没有隐式共享文件系统。需要交换字节时使用显式 Artifact Transfer，记录源、目的、摘要与回执；不能因路径同名、项目相同或同一 Agent 而推定数据相同。手机续写本机文件的能力必须明确受 Node 在线、权限及应用接口约束；不把“登录成功”当作文件可用的证明。

远端 Client 不持有节点文件系统路径，也不直接把本机文件服务暴露到公网。Runtime 应凭当前身份与节点授权建立受保护的请求路由，由 Node 在本地重新解析请求范围并核对真实路径、符号链接和文件版本；节点位于 NAT 后时可使用主动连接或受权中继。请求超时不能推定写入失败，必须查询同一命令的持久回执。

## 6. 写入、并发与跨域一致性

**内置应用创建或修改原件：**① Platform 校验真实用户／Agent 身份、目录范围和平台授权；② 所属应用重查专业权限、目标对象及基准版本，并决定自己的持久化后端；③ **若应用选择受管 Artifact Store**，字节先流式暂存、核验摘要／大小并发布为不可变版本，应用只引用已可读版本；若应用自管 SaaS，遵循其自身的提交与回执契约，不假装字节进入 Morphz Store；④ 应用在自己的事务中写专业版本、CAS 更新当前指针、记录命令回执与目录变更事件；⑤ Platform 凭应用回执幂等更新目录投影。若域表与目录表位于同一受信数据库，可把④⑤放进一个事务；若分库则用 outbox 恢复，不能冒充跨库 ACID。Store 已发布而应用事务失败的字节按明确引用／回收规则清理，不能提交悬空版本。

**节点文件：**普通文件经 Target `write` 创建后仍是原文件，不自动成为受管 Artifact、剧本工作室对象或「内容」条目；目录读取按需路由到 Node，不预先报告。断线重试用同一命令 ID 查询执行回执；原文件由外部程序改动时，写入前重查版本或返回冲突。应用若把节点文件作为自己的原件，其版本、可用性和备份契约由应用负责，不由 Platform 或通用 Store 推断。

**剧本候选采纳：**候选是剧本域的一份确定版本，携带 `base_revision`。剧本域比较当前 `main_revision`；若正文已变，返回冲突并保留候选，不自动覆盖，也不生成新剧本副本。采纳成功只更新剧本域的 `main` 指针并产生审计回执，再通知目录更新已观察版本。不同候选状态仍归剧本域，不靠“候选 7 看起来最大”推断最新正文。

**应用域与共享目录协作：**目录是可重建的定位投影，不是应用正文的第二权威。应用操作的持久回执包含 `instance_id + app_object_id + version_ref + command_id`；目录登记、设置项目、撤权与可用性更新按这份回执和实际权限执行。索引暂时落后时，回执仍可直接打开原对象；后台补偿修正目录，不能重发模型请求来“恢复内容”。

**第三方目录登记或导入：**第三方提供稳定对象／版本和幂等操作回执；经用户授权可登记**外部引用**，没有正文上传，也没有跨库 ACID。若用户明确选择导入，目标内置应用先接收并校验字节，再创建一个有来源关系的**新对象**；失败不改第三方原件，成功后也不偷偷双向同步。普通阅读与修改仍由第三方 API 执行，Agent 不能绕过授权直接访问其数据库。

**Runtime 与 Platform 协作：**Agent 工具调用绑定 Runtime 持久输入、实际发起者和授权范围；模型参数只能表达目标与意图，不能自称身份或项目权限。Platform 每次重查授权、版本和幂等命令 ID，返回持久回执；Runtime 记录工具结果。跨两个库不能承诺分布式原子提交；超时用回执查询与同 ID 重试确定结果，不能盲目重新生成。会话附件仍是 Event 关联的 Artifact，用户明确导入／交付前不会自动成为「内容」原件。

**访问链必须逐层成立：**读取应用对象要满足 Platform 目录可见性与所属应用的真实对象权限；读取节点文件还要满足 Runtime Target 使用授权以及 Node 本地文件范围、审批与沙箱。目录条目只是应用对象定位，**不是**节点文件读取令牌。应用对象权限、项目成员身份、Node 在线状态彼此不能替代；同一 Agent 在三个 Target 并行工作也必须让每个 Job 固定发起者、目标、权限快照与执行回执。跨 Target Transfer 必须检查源和目的两侧权限，并核对摘要。

**删除与撤权：**“从项目移除”只改目录关联，不删除应用原件；撤销节点文件访问权不删除原文件；“删除原件”必须调用所属应用或 Store 的明确操作，再让应用内容目录写墓碑／失效状态。项目删除不级联抹去 Runtime Session、节点文件或第三方原文件。每次在线读取重查目录、应用及节点侧的真实权限。**已经交付到离线客户端或第三方的字节无法远程追回**，不能把撤权描述成清除这些副本。删除导入副本不默默删除外部原件，反过来也一样；界面显示实际保存方、是否有副本及删除范围。

## 7. 查询与性能设计

- 项目与内容目录使用有界分页／游标查询；候选、批注和正文由所属应用分页。索引从真实过滤条件设计，例如目录 `(tenant_id, owner_scope, updated_at, content_id)`、应用域 `(tenant_id, object_id, revision)`。打开一个对象不应反序列化整个工作空间。
- 共享目录只索引应用已登记的对象元数据，按租户、主体、项目及应用分页；应用全文搜索由应用域提供受权查询或可重建投影。普通节点文件只在用户请求且授权成立时实时访问 Node，不建 Platform 副本。第三方私库和聊天附件不自动进入 Platform 内容目录。
- 当前正式搜索将 Platform 目录标题匹配与 Objects 应用域的 Agent 原创、非导入原件正文索引合并；正文只在 Objects 私库，返回的命中、数量与摘录均先核对 Platform 当前目录授权、所属实例和确切版本。SQLite／PostgreSQL 使用各自的应用域索引。人工创建及外部导入原件仅按标题查找；其他认知应用正文不因此自动纳入。原 `search-panel.spec.ts` 已改用隔离 E2E 中心里的新原件／目录链路，旧通用命令入口不再参与该测试。此项不代表存储切换的其他缺口或原版 Desktop 人工验收已完成。
- Runtime 单独维护 Node／Target 在线状态；各受管字节保存方核验自己的 manifest 和字节。应用内容目录可显示应用对象的最近确认状态，但打开正文必须重新核对所属应用及其保存方。性能基线测目录分页、应用读取和按需 Node 请求；不设计节点文件上报游标、云端文件索引或启动时全盘扫描。
- Artifact 原件和预览分块读取／范围请求；PDF OCR、EPUB 解析等重任务异步执行，解析结果以原件摘要和解析器版本作为缓存键。无正文提问不触发全书读取；阅读当前页与选文读取按需、有界。
- SQLite 采用 WAL、忙等待、外键与单写者策略并实测竞争；PostgreSQL 使用连接池、事务隔离、行级锁／CAS，必要时分区。两端必须保持相同冲突、幂等和权限语义，不能用“SQLite 最后写入覆盖”做简化分支。
- 基线先测当前真实工作负载的 p50／p95、数据库文件和内存增长、写放大、导入耗时与恢复耗时；再用多项目、多万对象、大书库、并发 Agent 交付与多租户压力数据对比。目标值按产品 SLO 单独批准，不在此文档虚构毫秒数字。

## 8. 备份、迁移和失败恢复

备份单位是**各实际保存方的权威范围**。云端 Platform 的项目／事项／授权／应用内容目录、Runtime 存储分别备份；Morphz 运营的内置应用按其自己声明的保存位置备份专业域和所引用字节。若应用原件或普通文件只在用户电脑保留一份，Platform 目录备份**不能**恢复其字节；产品必须标明备份责任，不能显示成“已云端备份”。第三方私库由第三方负责；Morphz 只备份自己的引用、授权和回执，不称其为第三方正文备份。恢复时向各原件保存方重新核对对象身份、摘要与可用性。

本产品尚未发布；当前 `workspace` JSON 等数据主要用于开发测试。**不以保留这些数据为由实现旧模型兼容、双写、双读、回执归档或在线切换框架。**新模型接线时可用全新隔离的开发数据库验收；需要保留的具体测试样本可另行导出、一次性导入。现有运行库和 Runtime 数据在实际切换前不由设计文档自动删除。

1. **确定唯一写入权威。** 每个在线业务操作只走 Platform 或所属应用域；Runtime 保持自身权威。旧 `workspace` 写路径在新入口启用时删除，不保留隐藏回退。
2. **验证模型和操作。** SQLite／PostgreSQL 都测试身份授权、修订冲突、幂等、候选采纳、目录分页；现有受管字节分别测试完整性与恢复，普通节点文件测试按需访问而非 Store 登记。
3. **验证真实入口。** Desktop／Web 的 UI 与 Agent 使用同一领域操作；重启后逐项检查项目、事项、剧本、阅读标注、文件引用和执行结果。只读夹具或离线导入不算用户可用。
4. **清理开发遗留。** 删除仅为错误设计或测试数据写出的兼容分支、迁移排练和失效表；若某份旧样本确需保存，用一次性工具处理，不让生产代码长期背负它。

本机既有数据迁往云端是单独的显式导入决定；部署更新不得默默复制用户文件或扫描全部目录。

**未来若决定托管第三方私有数据：**现在就固定应用自身稳定 ID、对象版本和来源引用，并定义可导出的版本化 manifest（数据模型、字节摘要、所有者范围和删除语义）及领域 API。这样能降低应用代码对存储位置的耦合，但**不能保证实际迁入成本低**：第三方可能没有可用导出、授权迁移或一致性快照，大数据搬运、加密密钥、停写和冲突处理仍需专项迁移。没有完成导出与回迁验证时，不把“将来容易托管”作为今天不托管的既成事实。本阶段不建设第三方托管库或其双写兼容层。

## 9. 实施顺序与验收门槛

| 阶段                        | 交付                                                                                                                                                                                               | 过门条件                                                                                                                                     |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 权威边界审计             | 每类正式业务对象、引用和字节的保存方、领域 API 与授权路径清单。                                                                                                                                    | 不把普通节点文件误当作 Platform 内容；不为开发测试数据增加长期兼容路径。                                                                     |
| B. 存储契约                 | Platform 共享业务关系模型、SQLite／PostgreSQL 双后端及授权／CAS／幂等一致性测试；内置应用各自定义专业存储契约。                                                                                    | 专业正文和版本只由所属应用负责；云端目录只保存稳定的应用对象引用；不使用整工作空间 JSON 写路径。                                             |
| C. 明确接收的字节与节点文件 | 对附件、导入书籍、UI 包等已有具体消费者，验证各所属保存方的字节读写、完整性、恢复和多 Host 可达性；节点普通文件通过 Execution Target 按需访问。**不建立通用跨节点 Store 服务或节点文件上报索引。** | 数据库与已接收字节故障注入后可恢复，没有悬空引用或静默损坏；未获授权的节点文件不可读取，节点离线如实报错；单节点独份文件不被显示为云端备份。 |
| D. 应用隔离                 | 内置应用域独立 schema／迁移与 Agent／UI 领域操作；应用自行声明存储方、可用性与备份责任；第三方仅有受权 API、外部目录引用与明确导入，不配置 Morphz 私库。                                           | 剧本与阅读应用不能越域写表；第三方不能取得共享工作空间库或内置应用域 SQL 句柄；应用对象、节点文件与已导入副本在 UI 可辨。                    |
| E. 接线和真实验收           | 将新域接入 Desktop／Web／远端 Client，清理旧权威路径并验证多节点契约。                                                                                                                             | 一个目录条目定位一份应用原件；手机能根据 Runtime 确认节点离线；Agent 可并行在多个 Target 执行并通过显式 Transfer 交换结果。                  |

以上阶段是**可验收的实现顺序**，不是已经完成的工作。底层 Runtime 存储不重写；现有 Artifact Transfer 保留。受管字节由其明确所属的 Runtime 消息链或应用域决定用途、版本与授权，不再为普通文件建立 Platform 登记层。本轮不引入第三方托管存储、通用跨节点 Store、跨端自动同步系统、通用分布式事务协调器或新的“中心”产品概念。

## 10. 决策记录：为什么不选看似省事的方案

| 方案                                                               | 取舍结论                                                                                                                                                                       |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Morphz Runtime、Morphz Platform 与内置 Cognitive Apps 共用物理部署 | **允许**同机、同安装包或同 PostgreSQL 实例；拒绝共写业务表或让一个模块执行另一个模块的迁移。SQLite 共文件仅限受信内置域与 Platform 存储的明确事务边界，不把第三方 SQL 放进来。 |
| 第三方应用的私有数据由 Morphz 托管                                 | **本阶段不做**：应用自己管理私库，Morphz 只管理安装／授权／目录引用与操作回执；未来迁入需导出与权限验证，不声称天然低成本。                                                    |
| 所有正文和版本都纳入共享工作空间库                                 | 拒绝：目录只定位原件。内置应用域保存自己的正文、候选和版本；第三方结构完全留在其服务。                                                                                         |
| 所有数据放 Agent Cell 或一个全局 D1                                | 拒绝：Agent Cell 的粒度与项目／内容所有权不一致；单库全部租户缺乏合理容量与故障隔离。                                                                                          |
| 要求所有应用文件先进入 Morphz Store 才能访问                       | 拒绝：普通文件由 Execution Target 按需操作，专业文件由应用选择保存方。只有明确接收的字节才按具体用途进入相应受管存储；现有 Transfer 不隐式改变原件所有权。                     |
| 云端索引节点文件或保存文件正文                                     | 拒绝：普通文件按需访问 Node；Store 自管受管字节；Platform 只索引应用提交的内容对象引用。                                                                                       |
| 因项目相同就认为多节点共享文件                                     | 拒绝：项目是组织与授权范围，不是物理卷。每个执行 Job 固定 Target；跨节点字节通过显式 Transfer 或应用自有同步协议交换并校验。                                                   |
| 继续整工作空间 JSON + BLOB，后面加缓存                             | 拒绝作为长期模型：缓存不能补出实体约束、隔离和局部事务。未发布的开发数据可按需导出或丢弃，不因此保留旧写路径。                                                                 |
| 默认本地＋云端两份可写，后台自动合并                               | 暂不引入：没有冲突、授权与引用语义前会制造双权威。需要离线写时另立协议和用户可见的冲突处理。                                                                                   |

本方案最重要的检验题是：**任何一本书、一部剧本、一个事项、一段对话及其字节，是否都能回答“哪个应用或模块拥有原件、目录引用在哪里、哪一版、实际保存方是谁、谁能读写、离线和设备丢失后由谁恢复”？** 若答案依赖当前打开的页面、Agent 猜测、重复的云端文件索引或跨库侥幸同时成功，模型就尚未成立。
