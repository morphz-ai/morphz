## Runtime 与应用边界

Morphz Runtime 提供认知、调度、执行和持久状态。Morphz 应用提供 Web、Desktop、Mobile 和浏览器扩展等用户入口。

应用通过明确的 API／SDK 使用 Runtime，不直接依赖其数据库和内部实现。各端共享同一个中心的会话、任务和相关认知；本机能力通过授权接入。

## Web、Dashboard 与 Desktop

- **Dashboard** 是内嵌在 Morphz 二进制中的管理、配置和诊断入口。
- **Web App** 提供完整应用体验，面向 Cloud 和自托管，不只是 Desktop 的试用版。
- **Desktop** 采用 Electron，提供桌面入口、本机集成和内置浏览器。浏览器支持用户登录与人机协作的设计要求，具体能力尚未实现。计划通过 `morphz install desktop` 额外安装；该命令当前尚未实现。
- **Mobile 和浏览器扩展** 同样连接中心，具体发布方式待决定。

Web 与 Desktop 的核心产品能力尽量一致；设备特有能力允许不同。安装 Desktop 不应默认产生另一份孤立的 Agent 认知和聊天记录。

内置浏览器与外部浏览器扩展并行保留。网站登录态默认保留在对应 Edge，浏览器配置受 Principal 与任务授权约束；共享中心认知不等于共享网站账号。选型理由和验证边界见[技术选型](./07-technology-selection.md)。

## Web App 按需获取

Web App 采用独立发布包，通过 GitHub 分发。CLI 提供获取、管理和启动入口，Runtime 二进制仅内嵌 Dashboard。

以下是待细化的可靠分发提案：

1. 使用已经构建的版本化发布包，不在普通用户机器上克隆源码并现场编译。
2. 发布包声明 Runtime API 兼容范围，选择兼容版本而非无条件使用最新版。
3. 校验发布包完整性和可信来源，保留可用的本地缓存。
4. 更新完成后再切换，保留恢复路径；更新失败或离线不应阻止已安装版本启动。
5. 如果技术选型允许静态前端，由 Runtime 提供其资源；是否需要额外服务进程尚未决定。

正式 Cloud 部署建议固定已验证的应用版本，在构建或部署准备阶段取得资源，不让服务启动依赖实时访问 GitHub。个人自托管可以提供更便捷的按需获取体验。两者共享产品协议，不必采用相同的更新策略。

动态获取解决更新与分发问题，不会取消接口兼容、身份认证或访问控制要求。

## 独立安装的边界

`morphz install desktop` 应作用于执行命令的本机，不能将 SSH 服务器误认为用户桌面。直接安装包入口、平台支持、签名验证、更新和卸载流程仍需设计。

Web App 用户权限与 Dashboard 管理权限需要区分。客户端安装、账户登录、连接中心和授予本地执行权限也是不同步骤，不能隐式捆绑。

## 兼容性与集成验证

- 维护可追溯的 Runtime、API／SDK 与客户端版本组合。
- 接口修改应记录受影响的客户端和兼容范围；不要求各端同时发布。
- 对新增或变化的接口运行契约与端到端集成检查，再宣布兼容。
- Runtime 构建和云端部署不应依赖 Desktop、Mobile 或扩展工具链。

联合开发与测试应明确所使用的 Runtime、SDK 和客户端版本，记录运行环境、验证步骤及结果。以上是集成验证要求，具体命令和通过的版本组合应由实现阶段的贡献指南和兼容清单提供。
