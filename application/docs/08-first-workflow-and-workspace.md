# 第一条完整工作流程与工作空间

日期：2026-09-07  
状态：交互提案；原型使用模拟数据，不代表客户端、团队权限或浏览器执行已实现

## 这轮要验证什么

用户把一件工作交给 Agent，Agent 自主安排其中可以执行的部分，把确实需要人参与的事项交给合适的人。人从 Inbox 进入实际操作的地方，完成后把结果交还中心，Agent 继续后续工作。

这轮验证的不是任务列表好不好看，而是三个具体问题：用户是否知道此刻需要自己做什么；进入网页后是否还要重新解释背景；人完成操作后是否还要回到聊天框提醒 Agent 继续。

以发布一篇技术文章为例，但不把产品限定为内容发布工具。相同结构也适用于代码交付后的上线确认、采购中的选型与授权、研究中的资料收集与专家判断。

## 首轮流程

| 时点 | 用户看到什么 | 谁在行动 | 应保留的关联 |
| --- | --- | --- | --- |
| 提出需求 | 在对话中说明要完成的工作和约束 | 人提出目标，Agent 理解并安排 | 发起 Principal、Session、工作目标 |
| 自主推进 | Agent 正在核对文章与演示材料；另一项发布工作需要本人参与 | Agent 执行独立工作并分派事项 | 事项身份、责任人、依赖、最新进度 |
| 接到事项 | Inbox 中显示“发布技术文章”，说明为什么需要本人、完成标准和所需时间 | 人查看或调整安排 | 负责人、截止时间、优先级、分派修订 |
| 进入浏览器 | 打开发布页面；当前事项仍可见，旁边可以继续与 Agent 对话 | 本人在自己的浏览器配置中工作 | 当前 Principal、浏览器配置、标签页、事项、Session |
| 请求填写 | 人要求“根据最新进展填写”；Agent 此时获取获准的最新上下文和页面状态，再生成内容 | 同一个中心 Agent 经此入口执行 | 本次生成依据、当前输入框、页面版本 |
| 接管与提交 | 人可修改输入，Agent 不覆盖人的编辑；发布动作遵守既有授权，本例由本人确认 | 人或获准的 Agent 执行提交 | 操作身份、授权范围、动作标识、提交回执 |
| 后续推进 | 事项记录确认结果，Inbox 更新；Agent 接到结果后继续依赖它的工作 | 中心更新工作状态，Agent 继续 | 外部结果、有效事项修订、后续依赖 |

不要求用户批准每一次规划、每一项任务或每一次点击。本例由人发布，是为了验证人参与的交接；预先获准的其他工作应能自主执行。

“等待人”不能暂停整个 Agent。只有依赖这次交付的工作等待，其他工作仍可推进。

## 工作空间的初步组织

### Inbox：围绕参与者，而不是只围绕 Agent

Inbox 呈现当前 Principal 需要处理、需要决定和与其相关的更新。它是中心事项的参与视图，不是本地另存一套待办。

列表先显示行动信息：需要做什么、谁负责、何时需要完成、为何此刻出现。打开后可以查看上下文、产物和责任变更。已读不等于已完成，收到分派也不必然等于接受分派；直接指派还是需要接受，由团队规则决定。

### 工作：查看完整安排

工作视图包括人的事项、Agent 正在推进的事项和后续依赖。人可以调整负责人、模型、优先级或时间，不必通过一轮对话猜测设置是否生效。

界面要区分“已经保存的新安排”与“当前正在执行的安排”。原型中的模型选项仅表示示例策略，不代表真实模型目录；针对运行中事项的切换先显示“下一次调用生效”的提案，正式实现前需要验证其与 Runtime 绑定点是否吻合。

### 对话：不是另一套孤立状态

用户可以在工作空间中讨论具体事项，也可以发起不绑定事项的普通对话。不能要求所有想法都先变成任务。

事项侧边的对话与浏览器入口，需要关联正确的 Session 和获准共享的上下文。换端后既同步聊天历史，也接续工作，不只同步一份任务快照。多个人与同一个 Agent 对话，不代表可以互看所有私密内容。

### 浏览器：在当前页面参与工作

浏览器和事项放在同一工作空间里。打开一个输入框后请求 Agent 协助，它根据当时的进展填写；不是自动展示桌面提前生成的草稿。

内置浏览器和外部浏览器扩展保留相同的交接语义：知道正在操作哪个页面、哪个账号、哪件事，明确当前由谁控制，完成后结果归到哪里。浏览器 Cookie 不随任务转交给协作者。

原型中的发布页面是本地模拟，不加载第三方网站；“模拟提交”不会发布内容。实际网站登录、浏览器隔离和操作可靠性不由这个原型证明。

## 几个必须明确的动作

| 动作 | 产品预期 | 不能隐含发生的事 |
| --- | --- | --- |
| 转交给协作者 | 保存修订，对方按团队规则收到事项，保留原有进度 | 转移原用户的网站登录态或授权 |
| 改为 Agent 负责 | 重新检查 Agent 是否具备所需权限和执行位置 | 因为负责人变成 Agent 就自动获得发布权限 |
| 切换模型 | 检查能力与数据范围，显示生效点 | 改掉同 Session 其他事项的模型，或重放已完成的外部操作 |
| 人接管页面 | 停止该标签页的后续 Agent 输入，保留已发生操作 | 把尚未确认完成的旧动作当作未执行 |
| 交还 Agent | 重新读取页面和事项修订后继续 | 继续执行接管前保存的过期定位和输入 |
| 完成事项 | 按完成标准保存结果，并解除匹配的依赖 | 仅凭“已点击”或一条聊天消息认定外部发布成功 |

## 失败时如何继续

- **中心断线**：允许保留未提交的编辑；不把未确认的操作显示为中心已接受。重连后重新核对事项修订和动作回执。
- **两端同时修改**：出现冲突时显示当前有效安排，由人或 Agent 重新决定，不能静默覆盖。
- **协作者拒绝或暂时无空**：说明原因和可用时间，回到 Agent 的规划过程；无关工作继续。
- **网页已提交但回执丢失**：显示“结果待核对”，先查结果，不盲目再次点击。
- **身份或设备权限撤销**：停止新的读取和执行；在途动作的迟到结果按原动作身份核对，不能借结果回传恢复权限。
- **页面变化或登录过期**：定位失效就重新获取页面；需要人处理的登录和验证放回 Inbox，不把凭据交给模型。

这些是验收要求，不是原型已经模拟或真实验证过的全部情况。

## 第一轮实现范围提案

先验证 Web／Desktop 的同一条工作闭环，以及 Desktop 内置浏览器的人机接管。浏览器扩展随后用同一契约做一个最小接续验证，Mobile 继续保留在产品架构中。

这是建议的验证顺序，不是已批准的发版范围、平台列表或时间承诺。仍需决定首批桌面系统、目标网站与前端框架；不在这轮原型中冻结。

Principal、事项身份和多端同步从第一条流程就进入契约。团队管理界面可以逐步建设，但不能先让所有客户端持有管理员令牌，再把它包装成多用户支持。

## 进入正式开发前的验收清单

1. Agent 能创建和分派事项；人能调整安排；身份、修订和变更原因保留在中心。
2. 至少两名 Principal 和两个 Session 接入同一中心，验证可共享内容与不可共享内容，而不只是切换显示名字。
3. 事项等待人时，无依赖的 Agent 工作仍继续；正确结果只能解除对应等待。
4. 模型调整的保存状态、生效点和实际调用一致；并发事项互不误改。
5. 浏览器入口可使用最新进度生成内容，用户编辑不被旧动作覆盖。
6. 外部成功、失败和结果不确定三种路径能区分；重连或重复请求不重复提交。
7. 刷新或换端后恢复聊天历史与事项状态，不依赖某一客户端一直开着。
