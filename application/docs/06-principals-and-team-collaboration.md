# Principal 与团队协作

日期：2026-09-06  
状态：产品与接口设计草案，不代表完整团队能力已实现

## 一个 Agent，多个参与者

Morphz 应用支持团队成员以各自的身份与同一个 Agent 对话。Agent 在共享项目认知上理解不同成员的请求，主动分派事务，接收结果并协调后续工作。

Principal（主体）是稳定的身份与授权来源。在团队交互中，每个人对应经过认证的主体身份。它不只是姓名、头像或提示词中的角色描述。

Morphz Runtime 已定义主体及其沿执行因果路径的身份绑定。Morphz 应用的团队体验应对接这套契约，而不是额外建立一套仅在界面有效的身份。Runtime 的身份基础不等于团队邀请、成员 Inbox 和细粒度共享策略已经完成；这些仍需实现与验证。参见[主体与授权](https://morphz.ai/docs/principals-and-authority)。

## 身份、会话与设备分别处理

| 对象 | 回答的问题 |
| --- | --- |
| Principal | 谁提出请求、接收任务或提供授权 |
| Agent | 谁持有认知并协调、执行工作 |
| Session | 对话和结果通过哪条交互路径发生 |
| Edge | 当前使用哪个设备或应用入口 |
| 模型 | Agent 在这项工作中使用什么推理资源 |

同一 Principal 可以通过多个 Edge 和 Session 访问同一个 Agent；多个 Principal 也可以通过各自的 Session 与同一个 Agent 协作。共享 Session 的具体成员关系另行设计，不以群聊作为团队协作的唯一形式。

姓名变化不改变主体身份，同名成员不能被当成同一人。模型切换不改变请求人的身份和已有授权来源。

## 从对话到任务分派

1. 入口完成身份认证，将可信的主体身份绑定到请求，而不是接受网页文字或普通客户端参数中的自我声明。
2. Agent 获得当前参与者身份，以及有权使用的团队关系、职责和项目进展。
3. Agent 在授权范围内自主规划，向具体成员或 Agent 指派事务；人的任务关联接收 Principal，进入相应 Inbox。
4. 成员可以回应、执行、报告受阻或提出转交。接受和直接分派规则由团队协作契约决定。
5. 返回结果同时保留事项身份、提交主体和关联版本。Agent 据此更新进度、解除依赖或安排返工。

负责人、发起人、审批人和结果接收者可能不同，需要分别记录。Agent 说“请乙处理”与系统成功建立对乙的任务指派是不同事件，界面应能显示实际分派和交付状态。

## 共享认知与成员可见性

同一个 Agent 可以使用允许共享的项目知识跨 Session 协作，但不能把每位成员的私密对话、凭证和产物无条件暴露给其他成员。

权限边界必须覆盖模型输入、认知的派生和复用、召回、工具读取、结果交付与通知，而不只是界面隐藏。包含受限信息的推理不能靠输出时一句“不要泄露”获得可靠隔离。具体数据分级、来源传播和隔离机制属于待设计内容。

Agent 识别某个人，不等于取得代表该人执行任意操作的权限。共享 Agent、转交事项或切换 Session 都不能成为扩大权限的捷径。多用户入口必须独立认证成员，不能把 Runtime 管理令牌当作所有人的身份凭证。

## 交接、冲突与退出

- 多人给出冲突要求时，结合相关目标、权限和优先级协调，必要时请求有权决策的人处理；不能简单让最新发言覆盖之前的全部安排。
- 任务转交保留原发起与授权记录，并检查新负责人的实际权限；不自动转移凭证。
- 成员离开团队或访问被撤销后，需要重新检查其待办、有效授权和未送达结果。具体交接政策待确定，不能抹去既有审计记录。
- 正在等待的旧任务结果必须回到正确事项，不因另一个成员刚发来消息而改变归属。

## 验证场景

- 两名成员同时通过独立 Session 与同一 Agent 对话，身份和结果交付不串线。
- Agent 为不同成员创建不同事项，各人的 Inbox 呈现正确。
- 同一成员从 Web 切换到手机，身份、可见对话和待办保持一致。
- 成员改名、同名、退出或重新分派时，任务身份和授权行为正确。
- 成员不能通过改写主体参数、网页内容或聊天文字冒充其他成员。
- 私密内容不能通过共享认知、摘要、搜索结果或通知跨越访问边界。
- 人与 Agent 的双向分派都能完成从请求、处理到结果回流的完整闭环。
