## 产品行为

用户提出要求，Agent 创建或修改实际文稿并保存为当前版本。用户可以继续指导、
直接编辑、查看版本和回退；不需要逐篇点击“采纳”。保存不等于批准、锁稿或对外
发布，这些是明确启用的专业生产操作，不能成为普通创作的前置条件。

回退是把某个确切历史版本的完整内容保存为新的当前版本；不倒退版本号、不删除
后来的版本、不覆盖未发送草稿。日常路径不生成等待人决策的候选，也不是后台
自动执行一次旧的采纳命令。

2026-10-10 用户进一步明确要求：已有候选直接转成正文。这个明确授权取代前版
“仅保留旧候选、不迁移”的过渡安排，不改变新创作直接写入版本的核心方案。
迁移前核对并备份原资料；每个条目选择最新待定候选，基准正文未被后续编辑、
不存在拒绝／锁稿冲突时，复用已验证的原件版本事务追加当前正文，并保留旧
正文、候选原字节、创作作者及关联。迁移回执记录真实执行者，不伪装为原作者。
不删除旧版本、不把保存冒充人工批准／锁稿、不替用户丢弃本机脏草稿。多候选
或基准正文已变化时单独核对，不静默覆盖。

这是本次明确授权的一次性旧资料过渡，可以复用旧候选决定命令保证回执和
投影一致；不把自动采纳作为新 Harness 的日常步骤，也不在数据库升级时替所有
用户默认采纳。旧在途输入仍按其冻结契约结束，新输入使用新契约。

## 冻结生成契约

准备与结果不是新增工作流调度器。Runtime 仍执行持久 Plan；应用只保存本次输入
的确切目标、创作上下文和引用闭包，以及实际结果回执。

唯一新增持久字段为 `script_preparations.submission_mode`，取
`candidate`／`current`。迁移默认 `candidate`，使已存在的准备、旧回执和在途
输入保持原意。新 Harness 和新 Client 明确选择 `current`，同一 input 后续
调用不能改变模式、目标集、预算或任务解释。旧客户端缺字段仍按旧冻结契约处理，
不能在 schema 解析中给旧 generation 添加默认字段而改变旧请求 hash。

当前结果模式每个目标只有一个交付，不使用 maxCandidates 生成多份待选文稿。
一次最多 12 个目标，同一 production／contextRevision。每次模型创作之前重读
固定材料；提交时在同一应用事务中重新检查所有目标 head、创作 epoch、权限、
取消及来源，陈旧或撤权不得静默覆盖。

多目标写入使用一个原子应用事务：全部正文、版本、事件、自审报告、命令回执及
outbox 一起提交；任一目标失败则本批新版本全部回滚。批内目标可引用其他本批
结果的 `baseRevision + 1`，但只能是本批实际交付的目标、完整 payload 所依据
的结果；领域层核对版本并按依赖拓扑提交，拒绝循环／重复／自身依赖。旧引用
仍保留确切历史版本，不自动改成新 head，不伪造已读证据。

Platform 投影不宣称跨库原子性：应用提交后按 outbox 顺序投影。响应丢失时核对
原回执，重试同命令只恢复投影，不重新生成或追加版本。原件已保存、投影待恢复、
未知和实际未写入分别报告；不能把目录失败称为原件已回滚。

## 写入、回退与接口

Human 编辑、Agent 类型化创建／修订／回退与生成提交复用同一 app-domain
版本写入原语。保留期望版本、来源读取、依赖合法性和目录投影校验，去掉仅因
`actor.kind=agent` 而禁止有内容创建／修改正文的规则。锁稿不能被普通写入绕过；
真实安全审批、应用 ACL 和原件授权不被创作方向变更扩大。

`prepare-workflow` 明确冻结 `submissionMode=current`；`read-workflow` 返回该
模式及输出 schema。`submit-workflow` 按冻结模式提交当前正文或继续处理旧
候选。`read-results`／`read-result` 返回本次确切版本、实际文本、创作说明和
自审报告，不再把当前结果冒称“待采纳”。

`command/create-item` 允许完整文稿；`revise-item` 基于 expectedRevision 修改；
`restore-item` 从所属应用读取历史版本再追加新 head。Host 解析实际调用来源，
不接受模型指定 principal、root 或另一个 input。固定生成中的子 infer 仍不
自行写入；提交由外层 Plan 统一执行，不绕过固定范围。

回退只能恢复早于当前 head 的确切版本，保留历史结构和来源；若其原件已撤权、
结构不存在或当前 head 冲突，保留草稿并报告，不用新 ID 强制重试。恢复内容
不自动复活旧批准，受影响下游按原依赖机制失效。

幂等边界：tenant＋commandId；hash 包含真实身份、输入、完整参数及冻结模式。
生成整批再按 input 保证唯一提交，换工具调用 ID 不重复生成已保存版本。
回执检查先于取消守门：可读取已发生的事实，但取消后不能产生新写入。

## 存储升级、查询与生命周期

SQLite 用现有写事务；PostgreSQL 用生产级 advisory lock／行锁和同样的 CAS，
保持双后端行为一致。schema v7 → v8 只增加模式列；先核对旧 schema SHA 和
结构，在一个事务中升级及更新版本账本，旧 draft／candidate／receipt 字节不改。
保留更早的受审迁移链，未知或损坏的数据库拒绝升级。不创建业务资料测试回退。

不新增删除操作；production 的现有生命周期、项目归档、旧版本及候选的保留
策略不变。生成报告沿用 `script_check_reports`，每项版本写入沿用原回执和
`script.item-revised` outbox；批回执用现有 command ledger，不另存正文副本。

新增结果读取通过 `script_command_receipts` 的现有 input 索引关联 exact item
version；历史仍用 editor 的 item／revision 和分页索引。交付投影按真实回执
关联确切版本，旧创建与候选交付仍可读，不根据回复文字猜对象。
