# Morphz 存储模型：实施设计

状态：**本轮存储切换目标已完成。原 UI／Agent 使用唯一写入权威；退役写处理器、旧测试依赖及 114 个旧编译文件已清理，最终构建成功；全量单测 945 项中 942 通过、0 失败、3 项仅 S3 跳过。Store v2 原版升级／独立恢复、Runtime 双后端独立恢复与节点请求基线均取得实际终态。冻结源码后的界面回归 362 项和 2 项原生补验分两轮全部通过，无跳过。最终原版已正常重启，原件、完整未保存草稿、标注与附件经实际窗口和前后只读摘要核验保留**（2026-10-01）。当前已接通的操作、证据与限制以[实施记录](./13-implementation-status.md)首节为准；下列带日期的“尚未切换”段落是此前阶段记录，不代表当前入口。具体关系字段以本目录的 SQL 为准；本文不授权删除正在使用的用户数据库。正式 Platform 对话由 Runtime timeline 保存已接受消息，Host 只保存本机待投递请求和处理游标，不新增已接受事件的本机正文镜像。

**2026-09-29 范围修正：**本轮存储切换不要求通用跨节点 Artifact Store。节点普通文件由 Execution Target 在授权后按需访问；Human 文件浏览若实现，也复用这个节点请求边界。Morphz 明确接收并承诺保存的消息附件、Reader 导入原件、UI 包等，在中心部署域使用本机目录或中心对象服务；中心可以与 Platform 共置，读写不经任一 Execution Target，也不建立节点间 Store 通道。Runtime 消息链和各应用域仍分别拥有其授权、版本、删除和备份契约，Platform 关系表不存这些字节。现有 `ManagedArtifactStore` 是这些具体用途的中心受管字节实现，不代表远端 Edge 能力。下文旧阶段对“必须接通远端 Node Store”的要求以此修正为准；不以额外 Store 通道阻挡 Desktop 主路径验收。

**事项前置依赖的投递契约（2026-09-30）：**开始操作先在 Platform 同一事务保存事项不可变版本、幂等回执和 `task.run_requested`；声明的依赖来自该版本，不能由 Client 或模型指定 Runtime Thread。Host 通过现有 outbox 等待人工有效答复或 Agent 的真实执行关联。有效人工答复必须来自当前负责人，且答复后没有重开、改要求或换负责人；改标题、日期不使答复失效。Agent 前置状态通过现有 Runtime 精确 Schedule／Thread 读取，失联、失败或取消不批准投递。最多读取 100 个依赖、4 并发，不展开 workspace。

条件成立后，Platform 在写事务重新核对权限、依赖版本和执行关联，并只提交一次确定的 `task.run_prepared` 事件。它复用已有 outbox，保存原事项／执行身份、有序人工答复引用和 Runtime Thread 引用；无新数据库或调度器。完整答复仍在 `task_responses`，Agent 可按确切答复 ID 读取，不重复把全部答复塞进模型。Runtime 请求固定后才允许 POST，重启或丢回执必须重用该请求；修改当前事项或前置结果不会偷换在途执行。实际时间和 Agent Thread 依赖仍由 Runtime Schedule 判定。尚未准备的执行可在同一事务撤回，不创建 Runtime Schedule；已准备的执行必须按原 Schedule ID 核对并停止，不能把超时当作未执行。SQLite／PostgreSQL 保持相同 CAS、撤权与重试语义；中心备份沿已有 outbox 覆盖固定请求和引用。

**事项关注来源的接续契约（2026-09-30，已接通）：**关注属于原事项的已授权执行，不创建 Human 消息或第二套调度器。Application 从所属应用读取确切版本和真实变更回执，不用目录的已观察版本冒充原件权威，也不读取全文来检测变化。Platform 在原 run、control revision、当前成员与来源权限仍成立时，将有限来源引用、真实命令 ID 和完整 typed Session IO 请求冻结为既有 outbox 的 `task.source_changed`。活动 Thread 使用真实 generation 定向接续；已完成／失败的 Thread 不复活，而在原 Session 继续一个新 root，保留原准入、模型及实际执行节点绑定。当前 Runtime Schedule 的排队、暂停、取消、实际 not_before 与依赖状态决定能否投递，不能凭旧准入日期越过当前安排。暂停不前移来源签名，恢复后一次处理当前版本；停止、改派、新 run 或撤权阻断旧执行继续取得领域写权限。

收到来源 IO 的工具调用必须核对 Runtime 的实际 Principal、Session、不可变完整请求与 Platform 已冻结事件，metadata 不是授权。跨库丢回执按原 client_message_id 查询／重试，不把新页面、当前事项或新来源重新拼入旧请求。来源确认、签名更新和真实命令引用在 Platform 同一事务提交；停止只在原执行以及实际接收的接续执行均已确认停止后完成。若一次投递是否发出／被接收仍未知，保持停止待确认，不凭 404 宣称停止，也不在停止时主动补发一个原本可能没有发出的新执行。当前 Runtime Session IO 没有按未知 client_message_id 原子拒收的接口；Platform 已记录尝试后、实际 POST 前崩溃的最终停止收敛仍是明确限制，不以删除尝试记录或伪造停止成功掩盖。正式 UI 的待确认文案与完整界面回归另行收口，后端安全门槛通过不代替可见状态验收。

执行检查器的读取与领域写权限分开：停止后的历史仍可读取，但不会重新取得写权限。原执行以准入版本的项目和实际 Runtime roots 固定；事项后来移项目时同时核对原项目与当前项目的真实成员资格，检查器只接受这两个合法选择，不接受第三项目。Jobs 与审批按该执行的原 Thread 和已证明接续 Thread 有界读取，不先取整个共享 Session 最近 100 条再猜测归属。领域移动、改派及重开共用原 run 的来源停止门槛；清掉当前执行引用不消除已接受或未知来源尝试。SQLite／PostgreSQL 联合 45 项和真实 Runtime 八阶段证据见实施记录。

**当前理解的正式存储契约（v8）：**Agent 的公开认知帧仍由 Runtime Context 持有；它不是内容目录原件。显式发布时，Host 从本次 Runtime 输入所属 Session 读取确切已提交的帧版本和 `public-summary`，Platform 在核对该输入的发起者、当前项目成员资格和来源目录引用后，保存一条不可变的项目公开版本。现阶段可点击的来源限于 Objects 文档，发布前检查其确切版本和完整性；其他领域版本尚无统一的精确打开入口，不能伪造引用。项目下最新版本是成员可读的检查器视图，历史版本可按修订读取；每条版本只保存有界 Markdown、帧身份／修订、来源内容 ID／版本引用、发布者与时间，不保存私有推理或整个 Context。发布使用稳定命令 ID、版本前提和帧修订单调检查；重复请求返回原回执，不同请求不能覆盖较新的公开版本。项目撤权立即阻断在线读取，项目删除不级联删 Runtime 帧或历史；备份 Platform 表可恢复已发布视图，不能据此声称恢复 Runtime 认知。此投影不进入 `content_entries`、内容计数、搜索或最近成果。SQLite／PostgreSQL 使用相同约束和事务语义，升级只增加独立关系表，不改已有用户对象。

**2026-10-01 清理完成：**`ManagedArtifactStore` 当前 manifest／根绑定／备份格式均为 v2，公开参数及当前 SQL 不含 `node_id`／`nodeId`。中心字节身份由 `store_id + root_binding_id + database/schema` 确定，不依赖执行节点。只在初始化保留精确 v1 结构核验和事务式 1→2 升级，保护实际运行 Store 的字节、配额、身份、版本与幂等回执；不保留旧业务接口、双写或跨节点路由。PostgreSQL 根标记与 SQL 不能共同原子提交：未发布成功时 Store 不开放业务读取，重开只接受原绑定的一致身份后补完发布。旧 Store 备份格式 1 明确拒绝，升级后生成新的格式 2 备份。原版三个 Store 已实际升级，原非空附件的 125,332 字节及摘要不变；新备份恢复到独立目录后，六库 121 张表／2,204 行及所有版本、回执、字节一致。恢复保留逻辑 Store ID，但为新物理目录生成新的根绑定及绑定创建时间。无调用的旧 `migrateContentOwnership` 文件已删除，类型检查通过。具体日志与范围见实施记录首节。

2026-09-29 实现收口：曾试验的 Runtime `artifact_store` 节点登记／观察接口没有正式消费者，且会把通用跨节点 Store 重新引入主线，现已连同独立 SQL、SDK、HTTP、应用桥接和测试入口一起撤回。Runtime 保留既有 Execution Target 与 Session 消息能力；应用域实际使用的受管字节 Store 不受此清理影响。节点型 Cognitive App 的领域服务路由只有在具体应用选择这种部署并定义授权接口后才实现，不因普通节点文件需要访问而预建。下文带日期的 Node Store 登记／节点应用路由记录仅用于追溯，不是当前存储切换的前置工作。

2026-09-29 保存方边界复核：应用原件的可用性与读写由所属应用的领域 API、权限和保存策略决定，不能仅凭 Morphz Edge 心跳裁决，更不能强迫第三方应用将领域命令经 Runtime 转发。先前未接入正式入口的心跳解析器及只为它增加的 Platform 节点所有者字段／v8 迁移已删除，`app_instances` 保持 v7 设计。当时拟接通受管节点 Store；此项已由上方范围修正撤出本轮。

2026-09-28 跨 Host 附件读取：已接受的消息附件以 Runtime 的不可变消息根和 Event 附件为原件，另一 Host 不读取发送 Host 的私有 Store。预览请求携带项目、对话和输入 ID，但这些只是定位线索；Host 重查 Platform 当前授权、Runtime 根与附件声明，校验类型、大小和摘要后返回有界字节。未发送草稿仍留在本机 Store；不因此将附件复制到 Platform 或为普通节点文件建立云端索引。真实 Runtime 和隔离双 Host 回归已通过；原版窗口及完整跨端验收仍未完成。

2026-09-28 Runtime 事件镜像纠偏：正式 Host 的 Bridge 启动只按 Session 读取关系行和索引尾部位置，不再装载或逐行扫描全部事件正文；历史列表从 Runtime 的授权 timeline 按页读取。Host 的本机事件行仍作为投递轮询镜像保留，v19 升级一次性将旧事件中的因果 Thread ID 与项目最近回复时间投影到各自的投递关系行。轮询取得的新事件与结算回执同事务保存，提交后释放事件尾部内存；旧历史只在明确调用旧接口时按需读取。本改动不把本机镜像提升为消息权威，亦未解决投递总量增长、旧历史显式全量读取或完整跨 Host 产品验收。下文旧阶段称“Host 启动仍将 Session 事件全量载入内存”的句子已过时。

2026-09-28 团队身份切换：Platform `team_identity_config` 与 `team_login_sessions` 成为多 Host 登录会话的唯一持久权威，登录、HTTP 入站、退出、热重载与成员授权均按配置摘要校验。配置变更时，登录绑定、项目成员关系、目录修订和失效会话在同一事务变更；旧 Host 的配置不能覆盖新状态。Host 本机只保留未绑定 Platform 前的缺配置拒绝启动标记，不再保存新会话。已有本机会话哈希可一次性迁入，同一导入中断重试不生成第二会话。SQLite／PostgreSQL 同义与双 HTTP Host 跨机撤销测试通过；这不代表 Runtime 消息历史有界读取或整个多 Host 产品验收完成。下文旧阶段称登录会话仍在 `workspace.sqlite` 的句子不再描述当前实现。

2026-09-28 跨 Host 会话缓存校正：已接受的输入与回复由 Runtime 的授权 Session timeline 按页读取；本机 Host 仅叠加自己尚未获 Runtime 接受的输入。当前选中会话的导航失效标识现在还包含 Runtime 持久事件序号：另一 Host 发送新消息时，不复制其队列或消息到 Platform，也能使本 Client 放弃旧历史缓存并重读。真实双 Host／Runtime 冒烟、Desktop／HTTP 传输、Web 定时缓存回归、SQLite／PostgreSQL 应用测试与生产构建通过；启用本机 PostgreSQL 的 687 项中 684 通过，3 项需 S3 测试端点而跳过。未解决全局项目活动的跨 Host 更新、本机事件镜像的启动全量加载、跨 Host 附件原件读取或原版窗口的人工验收；S3 仍不是已评审的必选 Store 方案。

当前 Host 传输进度在本机 SQLite 按投递、会话和事件分行保存；`runtime_state` 只留连接元信息。正式 Platform 会话的已接收输入和公开回复不在 Host 镜像，历史按 Runtime 持久 timeline 的索引有界分页，默认最近 100 条；本机只补充尚未被 Runtime 接收的输入。打开同一 Session 的另一 Host 可在 Platform 授权后读取同一持久历史，导航缓存用 Runtime 事件序号失效，不接管发送 Host 的投递队列。旧非 Platform 会话的本机事件投影仍有启动载入成本，不应把它说成正式 Platform 历史的读取实现。下文保留的早期“尚未跨 Host 读取”“投递仍为整行 JSON”等阶段记录均已被本段取代。

2026-09-28 消息根补充：Session IO 请求现可携带有界、非模型可见的 `client_metadata`；Platform 输入把原始输入正文和对话归属作为同一不可变请求的一部分交给 Runtime，随已接受的消息根持久化。Host 先检查 Runtime 的明确能力声明，旧 Runtime 不支持时保留原输入并提示升级，不发送残缺请求；旧的在途请求不会被重写。真实 Runtime 重启测试验证了该字段仍在消息根，投影测试验证它不进入模型输入。此字段是客户端来源数据，不是授权凭证；其后实现的跨 Host 历史读取还必须分页核对 Runtime 消息根与 Platform 当前授权。

Runtime 现提供 Session 授权后的客户端消息 ID 精确查询，直接使用已有持久准入索引，不扫描整段事件。发送 Host 之外的另一 Host 可据此取回不可变消息根，在核对 Session、实际 Principal、可见输入范围与 Platform 当前项目／对话权限后，还原该输入的选文引用来源；第二 Host 不复制或接管第一 Host 的待投递队列。隔离的双 Host＋真实 Runtime 测试覆盖读取、另一身份拒绝及未知 ID。此项是**精确单条来源读取**；完整历史另由上文 Runtime timeline 的有界分页实现，两种读取均不以 Platform 消息副本为权威。

流式回复在界面使用 `publication:<attempt_id>` 稳定标识，不能误当 Runtime Event ID。Runtime 的 Session 事件读取可同时按确切输入根与物理尝试筛选；SQLite 在 `(session_id, root_turn_id, json_extract(payload,'$.attempt_id'))` 建表达式索引，PostgreSQL 在对应的 JSONB 提取表达式上建索引，并保留只按输入根分页的索引。Host 只在该尝试范围内定位最终公开回复，再以 Runtime 已持久化的 `runtime/model_public_output.first_visible_at` 保持首次可见时间；不完整流仅能引用已持久化的公开前缀。查不到归属或当前授权失效便拒绝引用，不改写原消息。完整历史由 Runtime timeline 分页汇合已接受输入、公开回复及本机未投递输入；精确来源查询不替代历史页，也不在 Platform 复制消息。

Service Host 分别配置 Objects、剧本、Reader、Browser 的 PostgreSQL 连接与 schema：`MORPHZ_APP_{OBJECTS,SCRIPT,READER,BROWSER}_POSTGRES_URL`、对应的 `*_POSTGRES_SCHEMA`，以及共同的 `MORPHZ_APP_COGNITIVE_DEPLOYMENT_ID`；缺项即拒绝启动。四个 URL 可指向同一数据库的不同 schema，也可指向独立数据库。部署 ID 决定跨 Host 稳定的应用实例身份；每个私库 schema 保存独立的随机绑定 ID，并在 Platform 实例路由中固定。误连空库、换错任意一个 schema 或改部署 ID 都不能静默显示原目录却隐藏原件。已有本机应用 SQLite 库不会被新空库静默遮盖。各 Host 的本机投递只由所属 Host 重试，不要求其他 Host 接管。部署者须分别备份各应用 schema（包括实例绑定）与其实际字节保存方，`backup:center` 不涵盖这些 PostgreSQL schema。

2026-09-28 Host 身份补充：Service 使用 PostgreSQL Platform 时，部署配置必须明确给出稳定的 `MORPHZ_APP_TENANT_ID`（UUID）。每台 Host 用独立本机数据目录和投递库；新 Host 不复制旧 Host 的 `workspace.sqlite`，以相同中心身份连接同一 Platform、应用私库和云 Store。启动时若已有本机投递库绑定另一中心则拒绝，而不是改写其身份。两个真实 Service 进程的正式 HTTP 客户端已相互读取对方创建的项目、文档和剧本，且各自生成独立本机库；领域层测试也验证了旧 Host 的服务状态不会进入新 Host。云应用存储备份／恢复命令同样从部署的 `MORPHZ_APP_TENANT_ID` 读取中心身份，不再在命令行另收一份 UUID。当前 Host 仍依赖本机库保存投递与部分服务状态；这项验证不代表多 Host 在线消息入口已完成验收。

这不是把所有数据集中到一处，而是把**统一找到作品**与**拥有作品正文**分开。项目指向原件，不复制原件。Runtime 的 Agent Cell 是 Agent 执行和认知的部署单元，不是项目或认知应用数据库。Desktop 显示一部剧本也不意味着 Desktop 是这部剧本的权威保存方。

这里的“文件字节不进关系库”针对 PDF、图片、附件等原文件：关系库保存对象身份、版本、摘要和字节提供方引用，实际字节由所属应用选定的 Store／外部服务保存。可编辑的短文本不必伪装成文件；当前 Objects 的 Markdown 正文作为该应用自己的 `object_versions.payload_body` 保存，不进入 Platform 库。这是应用域的实现选择，不是要求所有认知应用把正文写入关系库。

## 2. 物理库与实例身份

Morphz Cloud 的 Platform 数据库在云端；Runtime 数据库仍按现有机制独立。每个 Cognitive App 有独立应用域：一个应用类型 `app_id` 可以有多个拥有不同数据权威的 `instance_id`，例如云端服务实例与某台 Node 承载的实例。目录中不可只保存 `app_id + object_id`：不同实例可能使用相同对象 ID；正确定位是 **`tenant_id + instance_id + app_object_id`**。实例的路由可以因重连或迁移改变，但 `instance_id` 不能被复用给无关私库。**当前归属哪个项目只写 Platform 目录；剧本与阅读器私库不存一份“当前项目 ID”。**应用可保留创建者与来源，读取/修改时仍必须核对 Platform 当前授权和应用自身权限。

内置应用服务在每次原件读写时，除实例和用户权限，还核对 Platform 当前路由是否仍指向本服务实际绑定的私库；路由更新后旧 Host 必须拒绝继续服务。此校验只防止过时保存方继续接单，**不执行应用数据迁移**，也不代替所属应用自行提供跨端领域 API。迁移仍须先停止新写、处理在途命令及目录事件、验证新保存方拥有相同原件，再切换路由。

Platform 与 Runtime 的存储边界明确；认知应用的物理保存方由应用决定，以下文件／schema 仅展示内置应用选择对应后端时如何隔离：

当前内嵌 Host 为 Objects、剧本、Reader 和 Browser 四个实例保存 `application-instances.json`，各私库另存 `morphz_app_binding`，记录租户、应用类型和实例 ID。实例 ID 不是从租户或路径推算的；身份文件必须与四个应用私库一同备份和迁移。新中心先写“初始化中”身份，四个私库建成并绑定后才原子封存为“可用”；中断可用原 ID 继续，但未封存的组合不能备份或对外登记。已封存中心若私库缺失、被空库或其他实例的同类库替换，Host 与冷备份均拒绝使用。旧版身份文件首次升级时会在核对现存结构后补写绑定，不改应用原件；补写前无法追溯证明旧文件历史上未被同结构库替换。它是本机部署身份，不是第三方应用须采用的存储方案。

- SQLite：Runtime 与 Platform 保持各自权威库；若内置应用选择 SQLite，可另用应用文件与迁移。受管字节后端可使用自己的 manifest。它们可以在同一机器；跨文件不声称一个 ACID 事务。
- PostgreSQL：Runtime 与 Platform 可共用一个集群，但使用隔离 schema 与 DB 角色；若某内置应用选择同一集群，也须有自己的领域 schema／角色。第三方应用绝不获得 Platform 或 Runtime 的 SQL 句柄。单租户或多租户是部署策略，不改变主键中的租户隔离和每请求的真实身份校验。
- 第三方应用：保留其自有数据库和备份策略；Morphz 仅接入受权领域 API 与目录引用，不因“内置应用在同一进程”而给予第三方 SQL 句柄。

当前 Desktop 与 Service Host 默认使用独立的 `platform.sqlite`。Service 部署者同时配置 `MORPHZ_APP_PLATFORM_POSTGRES_URL` 和 `MORPHZ_APP_PLATFORM_POSTGRES_SCHEMA` 时，Platform 使用指定 PostgreSQL schema；缺一项即拒绝启动。认知应用私库可以另行整组选择 PostgreSQL，配置与现存本机私库冲突时同样拒绝启动，不自动搬运原件。仍在使用的 `workspace.sqlite` 没有迁入 PostgreSQL。现有 `backup:center` 仅备份本机 SQLite 组合，不能代替 PostgreSQL 的独立备份与恢复验收；云端正式切换前需补齐部署级恢复流程与对象字节后端。

在 Morphz Cloud，剧本工作室可以选择 SaaS、节点或其他符合自身承诺的保存方；Platform 不替它决定。手机能否在电脑关机后继续编辑，取决于该应用实际保存方和已验证副本，而不是云端目录是否存在。导出到电脑的 DOCX 是另一个明确产生的节点文件，不与剧本对象暗中双写。阅读器导入本地 PDF/EPUB 时，原书不静默上传；阅读位置和高亮也由阅读器选择保存方并说明跨端可用性。若唯一原件在离线 Node，手机可见目录元数据但不能读原文。

应用若自己选择 Node 承载专业私库，手机继续工作需要该 Node 在线或应用已建立**自己声明且验证过**的副本。Platform 的云端目录不会凭空令其离线可写。应用迁移数据权威时需停写、迁移、校验并原子换绑实例路由；不创建两个并行可写的正本。

## 3. 关系模型与字节模型

剧本域检查报告（v5）：`script_check_reports` 按租户与命令 ID 唯一保存实际输入、剧本、检查目的、发起 Human／Agent、说明和两条有界 Harness 检查；外键指向本域准备记录及命令回执，按剧本／输入／时间索引。报告与意见、回执和目录 outbox 在同一事务提交；零问题同样保存报告，不伪造审阅意见，不批准或改写正文。相同命令改变说明或检查记录必须拒绝；查询与重试重新核对 Platform 当前授权和固定输入。专业报告留在剧本私库，不进入 Platform 正文表。检查记录是一个固定大小的类型化报告 payload，不替代可分页、可关联的业务表。内置应用的现存 v4 库经精确结构校验增加本域报告表；没有 workspace 兼容或双写。

六份可执行 DDL 用于评审具体结构。Platform SQL 是 Morphz 自有关系存储契约；其余五份只有在对应应用或 Store 选择该实现时才作为实施依据，不能直接在现有用户库运行：

1. [Platform SQL](./storage-model-v1/platform.sql)：租户、项目、成员、对话组织元数据、事项、应用实例、内容目录、事项／内容间的类型化关系、命令回执和 outbox。**不含普通节点文件索引或 Store 字节位置表。**对话表只保存归属／标题／归档，不保存 Runtime Session 或消息。目录唯一约束是 `(tenant_id, instance_id, app_object_id)`；项目关联**只在目录中**，不是复制正文，也不在应用私库同步第二份“当前项目”。事项有独立表和租户级顺序修订。
2. [剧本工作室 SQL](./storage-model-v1/script-studio.sql)：剧本元数据、条目、不可变 draft、正文版本、候选、审阅、操作回执和 outbox。`creative_epoch` 在创作上下文每次变化时增加，**变更后恢复原值也不复活过期候选**。候选是提案，不因编号较大就成为正文；采纳成功才新增版本并移动 head。
3. [Objects SQL](./storage-model-v1/objects.sql)：普通内容原件、逐版不可变且有摘要的类型化 payload、历史来源、精确版本批注和含文件版本的字节提供方引用。只有这一原件的版本被读取或修改；没有整份工作空间 JSON。PDF 等文件原字节不写入关系库，引用不是读取许可；迁移必须由实际字节提供方核验并保存。Markdown、交互对象和图片的原有 Human／Agent 能力已走正式领域接口，PDF 的确切原件／页面读取也已接回原入口；不把已有 PDF 读取或一次性样本导入描述成新 PDF 创作器。
4. [阅读器 SQL](./storage-model-v1/reader.sql)：阅读器自有书籍及版本、绑定外部原件精确版本的 `reading_sources`、章节和分块文字、个人阅读位置、高亮／批注、OCR 版本与作业、命令回执。相同字节摘要可能对应两个原件，故旧 `sourceId` 只作文本定位，不作原件身份；位置与标注按原件绑定隔离。高亮通过 `deleted_at` 可取消／恢复；不会为了改一个高亮重写全书。按原件版本和位置取有限文本，不把整本书随每次聊天发送。v3 的 `reader_import_cache` 仅索引本阅读域既有的 canonical source，正文仍只在原 source 的章节／分块表。
5. [受管 Artifact Store SQL](./storage-model-v1/managed-artifact-store.sql)：Store 身份、受管 Artifact、不可变版本、校验后的内容寻址 Blob、1 MiB 分块摘要和命令回执。字节文件不放关系库；Store manifest 的备份不等于字节备份。未进入 manifest 的孤立 Blob 可先隔离，过保留期且仍无引用时显式清理。Artifact 逻辑删除仍保留历史版本与字节；其保留／物理删除策略尚未制定，不声称删除后立即释放磁盘。
6. [Browser SQL](./storage-model-v1/browser.sql)：个人收藏和删除墓碑、修订与作者、命令回执；活动 URL 在同一所有者下唯一。只保存 URL 元数据，不抓取网页，也不把收藏伪装成内容原件。

### Reader：位置与标注分开读取（Reader v4）

`reader.state` 只读取个人位置与偏好，不查询标注。`reader.marks` 在 SQL 内先过滤真实租户／Human、原件精确版本、删除状态及章节／相交范围，再返回每页最多 50 条；游标绑定完整查询范围。正文只读取实际可见范围与必要选文，密集范围逐页取得完整命中；零长度书签及从视口外开始的长高亮仍可定位。侧栏保留原样式，以正常滚动续页，不首次收齐整本书或删除历史。Agent 的 offset／limit 同样直接进入受权 SQL，不再从第一页循环跳过。

v3→v4 只在验证旧 schema 后事务内添加 `marks_by_section_user` 索引；v2 先执行原正式 v3 升级。缓存、来源身份、位置、标注版本、删除／恢复和 CAS 语义不变。Client 的同 CSRF 撤权代次和 Reader 的原件／章节／滚动代次防止迟到页回填；异步恢复标注时，首次点击待当前受权页完成再解析，不伪造乐观标注。聊天的原文情境预算与实际可见标注范围独立，不能用 3,200 字聊天预算截断高亮。

真实 SQLite／PostgreSQL 每后端创建 1,148 条标注，当前章节 1,003 条有效标注以 21 页精确取得；每页 SQL 返回最多 51 行、HTTP 最多 50 条，**不等于引擎物理只扫描 51 行**。跨章／另一 Human／删除、点书签与长范围、非法及换范围游标、读取后撤权、CAS／幂等／恢复／重开均通过。完整原 Reader 14 项、新分页 3 项及原 PDF 1 项 **18／18 通过**，日志 `/tmp/morphz-reader-marks-ui-accepted-20260930.log`；真实 Client 迟到专项 2／2 通过。此证据不代替后续消息修正后的整套或原版 v4 重开。

### 剧本编辑器：展示索引与精确正文分开（Script v6）

正式 Client 使用 `scripts.editor.head/page/detail`，不把部分结果伪装成完整 `ScriptProduction`。head 固定剧本身份、标题、元数据与活动修订；page 返回目录、候选、正文历史、事件、审改或导出的有界 header 与游标；detail 在选中后读取确切条目版本、候选及其基线、检查或导出上下文。翻页必须核对读取起点的修订，不能混合两个活动版本。五个本域索引支持对应目录／条目／候选／审改／导出查询；v5 到 v6 只在核对旧结构后事务内添加这些索引。

历史标题、生成材料和 Word 导出均使用固定版本 manifest 及精确引用，不为查名称载入全部正文历史。导出保存器逐条读取 manifest 指定版本、验证摘要和当前授权，保留原本的取消、冲突及原子发布语义。界面授权响应栅栏与导航共用 `protectedReadGeneration`；它阻止旧代迟到响应回填，不取代服务端的每次权限核验。领域、正式 HTTP、旧 schema 升级和精确历史读取已由真实 SQLite／PostgreSQL 34 项专项验证；原 UI 的全部流程仍须单独通过验收。

### 表格原件：按行存储，版本不丢失（Objects v5）

表格专业数据只在 Objects 私库。Platform 仍只持 `instance_id + app_object_id`、标题、所属项目及已观察版本。`object_versions.payload_body` 对表格仅保存类型、关系模型版本、精确表格版本和根摘要，不再保存整份列定义／记录 JSON。

| 关系表                     | 保存内容与不可变边界                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `interactive_versions`     | 精确对象修订的布局、说明、字段修订、记录数、容量和版本根摘要。                       |
| `interactive_columns`      | 不可变字段定义与次序；定义未改变时复用同一字段修订。                                 |
| `interactive_row_versions` | 稳定记录 ID 的不可变行修订、单元格摘要与容量；只为改变的记录新增。                   |
| `interactive_cells`        | 按字段保存 text／number／boolean／null；缺失字段没有行，区别于空字符串、0 和 false。 |
| `interactive_version_rows` | 一个对象版本的有序记录 ID＋行修订清单；保留删除前的版本和原次序。                    |

`interactive.rows` 经过当前 Human、Platform 目录和 Objects 原件权限核验，固定确切版本、过滤和排序，用 SQL 返回最多 100 条记录。游标只做查询一致性校验，不是授权凭据；继续翻页仍须重新核验权限。数字汇总来自该固定版本的整个匹配集合，不是本页或模型估算。读取页内记录核验行摘要，读取完整原件额外核验整体结构；坏根／行摘要不能伪装成可读内容。

`interactive.patch` 支持 insert／update／delete／从精确旧版 restore，每次最多 100 个操作。对象 CAS、变化行、版本清单、稳定命令回执及目录 outbox 同事务提交；撤权、字段错误或任一操作失败不产生半份版本。删除只让新版本清单不再引用该行，旧版本可读。原 GUI 的普通记录编辑发送局部命令；字段、视图、既有行顺序变化或超过单次操作容量时使用明确的完整修订契约，不移除既有编辑能力。Agent 的 `table.query`／`table.patch` 使用相同领域服务，不模拟点击。

成本边界：单元格只写变化行，但每个版本仍复制最多 1,000 条小型记录引用，读取页也要核验有界版本清单；不是 O(1) 或无限容量表格。已有全文搜索投影更新仍是有界 O(N)，不把关系化冒充所有成本均已消除。旧 v4 专业版本升级只在结构和原摘要验证后一次性转换，事务中重建所有历史引用并校验；错误回滚，不保留正式读取的 JSON fallback。该升级不恢复旧 workspace 业务路径。

单元格查询每批最多 100 行，每支 SELECT 使用租户、对象、记录 ID 和行修订四个完整主键，以 `UNION ALL` 合并后排序。实际查询计划证实原 OR 条件会按对象扫描历史单元格；新查询在两后端按确切键读取，仍逐行核验类型、容量和摘要，不跳过完整性校验。真实 1000 行 × 24 字段、当前及历史版本、冷重开和损坏边界联合 19 项通过。n20 正式 Human 领域 API 的 page50 p50／p95 为 SQLite 4.41／6.10ms、PostgreSQL 55.13／62.71ms；单字段 patch 为 56.28／61.22ms、182.54／196.82ms。它包含当前授权、对象校验和目录提交，不是仅 SQL 计时；字段响应约 22KB，patch 回执约 216B，全文约 435KB。记录 `/tmp/morphz-interactive-point-end-to-end-20260930.jsonl`；不把这些样本外推为多 Host 或无限记录容量承诺。

`TEXT` 正文用于规模有界、可直接编辑的剧本段落；大型原文件、导出文件和媒体字节由应用自己的文件后端或受权 Artifact Store 持有。数据库对每类业务记录建主键、外键、唯一约束、范围检查和查询索引，不再将整个工作空间序列化为一行。小型固定结构的回执／事件 payload 可用 JSON 文本，但不能用它替代查询主键、授权字段、正文版本或事务边界。

### 对象标识绝不混用

| 标识                                | 回答的问题                   | 不得冒充                                 |
| ----------------------------------- | ---------------------------- | ---------------------------------------- |
| `project_id`                        | 哪个项目组织、授权这个工作   | 文件位置、App 数据库                     |
| `content_id`                        | Platform 目录中哪条入口      | 专业原件的内容或版本                     |
| `instance_id + app_object_id`       | 哪个应用实例拥有哪份专业原件 | Node 的路由地址；`app_id` 单独不足以定位 |
| `target_id`                         | 哪个执行目的地运行这次 Job   | 文件的持久保存方                         |
| `store_id + artifact_id + revision` | 哪个 Store 提供哪版受管字节  | 普通本机路径、应用对象版本               |

## 4. 四条实际操作路径

### 创建剧本并加入项目

1. 受信 Host 从**已持久化的发起来源**取得 Human 身份、项目、App Instance 和稳定命令 ID；来源可以是聊天输入，也可以是 Platform 准入并由 Runtime 证明的事项执行。模型参数仅是意图，不是授权。
2. Platform 验项目成员、应用实例和目标项目写权限；把命令交给应用的领域 API。`Node` 承载的应用离线时返回“原件来源不可用”，不悄悄改写到另一个实例。
3. 应用在自己的事务中插入剧本、命令回执和 outbox 事件。事件可携带请求登记到哪个项目的**命令上下文**，但不成为应用私库的当前项目权威。若同一命令 ID 已有相同请求哈希，返回原回执；哈希不同则冲突，不创建第二部剧本。
4. Platform 消费事件，核对所属应用的精确提交回执、原始发起者、对象、版本和项目，再按 `(tenant_id, instance_id, app_object_id)` 幂等登记目录；若暂时失败，原件仍存在，事件重试即可修复目录。恢复不重新获取可能过期的 Human 凭据，也不重放应用写命令。提交之后的成员撤权不抹去已获授权的提交，但后续读取仍重新检查当前授权。目录不复制正文。
5. 客户端可凭应用回执立即打开原件，即使目录尚未完成投影；后台对账最终补齐。不能因为目录超时重发创作或模型调用。

### 采纳剧本候选

在剧本域事务中检查候选状态、目标条目的当前正文修订、剧本的 `creative_epoch` 和同一命令 ID；全部成立才以候选 draft 新增不可变正文版本，CAS 更新 head，标记候选已采纳并记录回执/outbox。任一版本不匹配则返回冲突，候选保留，用户可以比较或重生成。Platform 只异步更新目录“已观察版本”，不参与候选事务。

### 按需访问节点文件

普通文件不进入 Platform 的文件目录或增量上报链。用户从 Client 请求查看已授权节点目录时，由 Runtime 按当前身份、Node 在线状态及权限路由到 Node；Node 当次检查真实路径、符号链接与访问范围并返回有界结果。Node 离线则返回不可用。若某 Cognitive App 管理了节点上的专业对象，Platform 目录只保存该应用提交的稳定对象引用；打开正文仍经应用接口及实际文件保存方授权，不以目录条目代替读取许可。面向 Human 的跨端目录浏览是单独产品入口，当前存储切换不以它已发布为前提。

### 已接收字节的保存方实现

普通节点文件继续由 Execution Target 授权访问，不因读取或传输变成受管 Artifact。已接收字节由对应的 Runtime 消息链、Reader、Objects 或应用包安装域明确选择保存方，写入后以所属域的稳定版本引用和摘要读取。现有 `ManagedArtifactStore` 可以充当这些具体用途的中心字节后端；云部署若采用云对象服务，必须由所属域验证相同的发布、读取与恢复语义。**本轮不为它再建立远端 Store 命令、第二套节点连接或离线队列。**

保存方的写入保留稳定命令 ID；响应丢失时，以**同一命令和参数**查询其持久回执，再决定是否重试。受管字节先由保存方验证长度与摘要，所属域只引用已发布版本。跨节点传输仍使用 Runtime 已有的受权 Execution Target／Artifact Transfer，并核验源、目的、长度与摘要；它不承担应用专业版本或受管 Store 发布语义。未来若出现不能由这些契约满足的具体需求，再单独评审远端 Store，不以推测的通用能力提前扩展 Runtime。

本机文件型 Store 先把字节写入私有临时区，计算摘要与长度，`fsync` 后原子发布到内容寻址目录，确认可读；随后在 manifest 事务中新增受管 Artifact 不可变版本与回执。应用只能引用已发布且已验证的版本。若应用后续事务失败，孤立 Blob 可经完整性检查、隔离和保留期后清理；若断电发生在发布和 manifest 提交之间，同样按孤立字节处理。Artifact 删除先写墓碑，历史版本及字节不在孤立字节清理范围内。本机独份 Store 不是自动云备份。

PostgreSQL manifest 与字节目录使用同一随机绑定身份；目录还记录数据库名和 schema。另一 schema、SQLite manifest 或不同 Store 不能复用该目录；绑定缺失且已有字节时拒绝打开，只有空 Store 才能修复中断的绑定发布。两种后端的误配和 PostgreSQL 双 schema 测试覆盖这条边界。它只保证该保存方的本机字节身份，不代表客户端跨端访问已验收。

现有 Store 的备份格式不绑定 manifest 后端：SQLite 与 PostgreSQL 双向恢复同一 Store 的版本、分块字节、授权归属和幂等回执已有隔离测试。备份仍只是一组已验证的 manifest 与私有 Blob；恢复后还须核对所属 Runtime／应用域的引用、部署身份与保存位置，不能把库文件复制成功当成客户端可用。

Reader 解析缓存的 lookup 固定当前 Human、实际接收原件的 SHA-256、格式、解析器指纹与选项摘要。指纹包含实际解析模块及 Reader／PDF core、相关依赖版本，DOC／RTF 还包含运行系统和解析工具身份；文件名等会影响结果的选项进入独立摘要。Host 先验证当前上传字节与权限，再读取索引指向的 canonical source；缓存引用撤权、缺失或损坏时重新解析本次原件，不以裸 hash 接口授予他人书籍访问权。命中复用解析结果，但新导入命令仍建立独立书籍／标注身份；同一命令重试沿其原已提交 source／parser 版本，不把旧命令重新标成新解析器。索引与 Reader import 同事务，SQLite v2→v3 升级先核对完整旧结构，结构错误或 SQL 故障不留下半套新表。真实 Worker 的命中／失效和两种后端已通过联合 59 项；完整字节校验和新书提交仍有 O(N) 成本，不宣称重复导入零 IO。

### 导航失效边界（Platform v9，专项已验证）

保留全局 `catalogVersion`，在既有 `navigation_heads` 上增加项目、对话、事项及访问权限四个事务内修订计数。文档正文、通知和窗口状态变化不使三份无关导航列表全部失效。项目生命周期、对话组织、事项正文／顺序／未准备执行撤回，以及成员和身份配置变化必须分别影响对应计数；幂等重放与回滚不增加计数。计数按租户维护，不是一份按用户复制的对象数据库，也不覆盖 Runtime 的执行状态权威。

客户端仍从真实授权分页接口取得完整列表，按已核对的修订复用未变部分；分页结束再次核对对应修订与访问权限修订，变更期间的跨页混合结果不作为同一版本缓存。访问权限改变即清除受保护的目录、正文与历史投影，不删除当前 Human 的未提交本地草稿。首次完整导航树仍有按页收齐成本；此改动只消除无关业务变化造成的重复全读，不声称已实现按展开节点分页。

真实 SQLite／PostgreSQL 与既有 Platform／Client／事项事务联合 106 项通过，覆盖连续文档修订的无关列表调用计数、112 项目跨页完整性／页间变更拒绝缓存、成员撤权、身份凭据轮换、未准备执行撤回、幂等与冷重开。四列与全局修订在业务事务中更新；旧 v8 只按固定结构升级，不保留双权威或原工作空间读取。原界面行为由 Client 完整列表保持，不能为了减少读取而丢失未展示的授权项目。

撤权时 Client 递增本地 `protectedReadGeneration` 并清除受保护投影。旧代请求即使原来已完成服务端读取，也不能在迟到返回后重新填充缓存；清理 pending 必须比较原 Promise 身份，不误删后来同 key 的请求。该代数仅是展示响应栅栏，不替代服务端授权。真实 SQLite／PostgreSQL 先读、再撤权／清代、随后释放迟到响应的竞态专项已通过；其他新页式读取也必须使用同一栅栏。

### 查询目标

- 项目列表：按 `(tenant_id, principal_id)` 读成员，再按项目键分页；不是加载所有项目／剧本／书籍到一个对象。
- 内容入口：按 `(tenant_id, project_id, deleted_at, updated_at, content_id)` 游标分页。点开时只读取**一条目录 + 一个应用原件的选定版本**。应用可独立为候选、章节、高亮分页。
- 事项：租户有一个语义优先顺序及全局顺序修订；项目列表只是按项目过滤同一顺序。调整项目内可见事项时复用其原有全局顺序槽位，其他项目的相对位置不变；CAS 使用全局修订，只更新受影响的事项，不写整个工作空间。
- 正式事项页与 Agent 工具均读取 Platform 事项域；SQLite／PostgreSQL 同义测试覆盖排序、分页和撤权。Agent 权限来自实际持久输入或事项执行来源，不取当前 Client 页面作为依据；个人对话可在成员边界相同的获授权项目间查找和创建，项目会话及后台事项保持自己的项目范围。
- 归档项目仍允许成员读取其对话、事项版本、人工答复和执行引用以便恢复；日常跨项目事项总览只显示活跃项目。归档项目不接受新写入。正式 Host 的归档／删除现先在 Platform 建持久准入栅栏，再核验本 Host 已持久化的项目输入及 Platform 事项执行关联对应的 Runtime 实时状态；不确定的发送回执、旧输入来源、离线 Runtime 或非终态执行均拒绝退役。核验失败撤销栅栏，不改变项目状态；同一命令可重试。SQLite／PostgreSQL 栅栏语义、Host 空项目归档及 Runtime 精确引用已有测试。
- 本机模式下多个项目共用同一个 Runtime Context；Context 级运行计数不能代替逐输入核验。消息投递已按输入在所属 Host 独立持久化，由该 Host 自行重试；其他 Host 不恢复或重放这份队列。**多 Host／云端部署尚不能用其中一台 Host 的投递列表证明全局无在途输入**。跨 Host 项目退役必须分别核对 Runtime 的实际执行状态和各相关 Host 的未完成投递；无法核实时保守拒绝退役。当前共享 PostgreSQL Service 明确拒绝归档／删除，且不建立退役栅栏；单 Host 部署保留原逐输入核验。不以新增 Platform 消息库代替核验，也不宣称当前已通过多 Host 归档验收。
- 阅读：原件按段／页分块，文本位置、OCR 版本有索引；翻页不触发模型。PDF 原件按 Range 读取。搜索应用正文由该应用的授权索引负责，Platform 只检索获准登记的目录元数据。
- 并发：SQLite WAL + 单写者 + 忙等待；PostgreSQL 行级 CAS 和连接池。相同命令 ID、版本冲突和权限在两种后端得到相同结果。性能值需要实测，不能把“有索引”当成 p95 达标证明。

## 6. 备份、权限和迁移边界

Platform 数据库备份可恢复项目、事项、授权和应用内容目录，**不能**恢复剧本应用私库、第三方 SaaS 或用户 Node 的独份字节。内置应用由自身的保存方对专业私库和其引用的字节做一致备份；使用受管 Store 时其 manifest 与 Blob 必须一起备份并核对摘要。第三方应用私库由第三方负责。撤销授权使未来读取失效，但已交付给离线客户端或第三方的副本无法远程追回。

`backup:center` 要求先停止本中心全部写入者，一组备份现存的 `workspace`、Platform、Browser、Objects、剧本、Reader SQLite 库、应用实例身份，以及本中心实际存在的 Reader 原件、未发送消息附件、Objects 图片、UI 包四类受管 Store 的 manifest 和字节。恢复时校验各库及 Store 摘要、专业引用和实际字节，只写入新目录；不是只复制 manifest 或 SQLite 文件。自动测试覆盖四类原件的冷恢复、引用缺失及损坏字节拒绝发布；某类 Store 不存在且没有所属领域引用时不虚构一个备份。命令不能替代 Runtime、客户端草稿、PostgreSQL 私库、第三方存储或其他独立保存方的备份。分页前原版 Script v6／Reader v3 的最新冷备份恢复核对六个数据库 121 张用户表、2,120 行的结构及逐行摘要全部一致；未覆盖运行目录，不能替代 Reader v4 重开。若已有领域原件引用的 Store 缺失，备份拒绝生成。

独立中心恢复耗时另用原版最新 v2 冷备份实测：生产 `restore:center` 五次恢复到全新目录，六库 121 表／2,204 行、所有 Store 版本和回执、实例身份与 125,332 字节非空附件逐次核对一致；原备份摘要不变，本次临时恢复目录已清理。54,501,376 字节 SQLite 库的 CLI 过程（包括进程启动和内部校验）p50／p95 为 **430.443／681.104ms**，外部完整摘要审计另计，五次无失败且最终退出 0。日志 `/tmp/morphz-center-independent-restore-timing-20261001.jsonl`；同归档已有 OS 缓存，n=5 的 p95 是最大样本，不代表冷 OS、PG／Runtime 恢复或批准 SLO，不用 Host 重开时间冒充灾备恢复时间。

正式 Host 的项目、事项、内容目录、剧本与阅读主路径已调用 Platform 或所属应用域，Reader 导入的书籍字节保存在内嵌原件 Store；旧通用业务实现及快照回退已经删除。界面仍使用内存中的 `Workspace` 形状作为展示适配器，不代表旧数据库是新对象权威。消息附件发送前由发起 Host 的独立受管 Store 保存，投递记录只保存引用和摘要；Runtime 接收时分块传入，并由其消息 Event 保存已接受的附件字节。其他 Host 读取已接受附件时核对当前授权和 Event 原件，不读取发起 Host 的 Store；该 Host 的冷备份覆盖其尚未发送的附件。图片的正式上传、创建、修订和读取已接 Objects 私库与独立 Store；原 Agent 工具没有图片生成／上传能力，不能把未批准的新增能力当作存储切换缺口。尚未收口的真实缺口与当前测试以实施记录首节为准。开发测试数据不构成保留旧写路径的理由。

实施验收必须在 SQLite 和 PostgreSQL 上验证租户隔离、对象定位、CAS、幂等、目录 outbox 重试及现有受管字节保存方的完整性和备份恢复；在真实 Desktop／Web Host 验证 Human 与 Agent 使用同一领域命令和已发布的跨端结果。节点文件按需请求、原文件外部修改与 Human 浏览入口按 Execution Target 的独立功能验收，不以远端 Store 通道阻挡本轮。仅 SQL 可建表、离线夹具通过或 Store 单模块通过，都不算完成。
